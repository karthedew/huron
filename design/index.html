Huron Design Record

A datalake for scientific projects — immutable raw evidence on NFS, analysis-ready Zarr + Icechunk layers on object storage, one catalog, one authorization model. Version 2026-08-23. This is a greenfield design: it is the complete record, it stands on its own, and it owes nothing to any earlier prototype, plan, or codebase.

1. What Huron is

Huron ingests complete scientific artifacts — MCNP runs, RELAP outputs, instrument captures, simulation ensembles — as immutable Raw revisions, converts them into source-faithful Bronze arrays — by manual intake in v1, by automated builds where a project later adds an extractor, canonicalizes those into standardized Silver datasets that scientists analyze through Xarray without ever parsing native formats, and publishes scientist-derived results as versioned, fully lineage-pinned Gold products.

LayerMeaningStorageWritten by
RawOriginal submitted files, byte-exact, immutable NFS (POSIX)Contributors, through the API
BronzeSource-faithful Zarr representation of the same values Object storage (Zarr + Icechunk)Huron pipeline services only
SilverCanonical, validated representation; standard names, units, coordinates Object storage (Zarr + Icechunk)Huron pipeline services only
GoldScientifically derived, validated, published data product Object storage (Zarr + Icechunk; optional Iceberg for tabular products) Huron pipeline services, on behalf of publishers

Silver standardizes existing scientific meaning; Gold creates and publishes new scientific meaning. Layer names describe Huron's product status. Scientific processing levels (L1/L2/L3 or a domain's own scheme) are orthogonal metadata carried on the dataset or product.

2. Resource hierarchy

Huron platform
└── Organization                 tenancy and administration boundary
    └── Project                  the data pond: quota, retention, classification, membership
                                 a programme of work (e.g. modeling-simulation)
        └── Dataset              one body of data in that programme: one run, one
                                 acquisition, one contributor's deposit (e.g. run-0042)
            └── Revision         one immutable commit to that dataset (1..N, gap-free)

            Release              a named, immutable tag on one revision (v1.0) — a
                                 pointer, not a level

Three entity levels and one version axis. A dataset has a single linear history of revisions, exactly as an Icechunk repo has a linear history of snapshots; a release is a named pointer into that history, exactly as an Icechunk tag is. The versioning model is therefore identical in all four layers, and dataset@v1.0 means the same thing whether it resolves to raw bytes or a Silver array.

A new dataset means a new run or acquisition — the scientific inputs are different (different thickness, material, seed, geometry). A new revision means correcting or extending the same body of data (truncated output, missing file, corrupted packaging). A release means "this is the version to cite", and because citations must not move, tags are immutable once written.

Raw, Bronze and Silver all attach to the dataset, one repo each, so the four layers share a single hierarchy and the layer is the leaf of the path. Gold attaches to the dataset when a product derives from exactly one, and to the project when it fuses several; either way it pins the exact snapshots it was derived from. A canonical contract still decides which runs are comparable — it is what makes their Silver repos concatenable — but it no longer decides where they are stored. Every resource carries an immutable, URL-safe slug fixed at creation and a mutable display title; renames touch titles only, and no one — not an organization admin, not the platform owner — can move a slug, so storage paths never move.

3. Core decisions

Each decision names the live alternative it was chosen over, so a future reader knows the choice was considered, not defaulted into.

#DecisionInstead ofWhy
1 Greenfield build. Huron is designed and built from scratch: no API compatibility with, data migration from, or design deference to any earlier prototype. Anything reused must re-justify itself against this record. Evolving prior work incrementally Compatibility constraints shape architectures more than requirements do. Starting clean lets every mechanism earn its place.
2 Raw lives on NFS; POSIX is the authoritative raw store. Commit = staging directory + atomic rename(2); complete independent uploads; immutability = sealing. Details in Raw Layer. Object storage for raw too HPC runs are born on NFS; committing in place avoids copying up to 1 TiB per run. POSIX rename publishes a complete envelope atomically — a stronger primitive than any marker-object protocol.
3 Hierarchy: Organization → Project → Dataset, with linear revisions and releases as immutable tags. A separate Release level between dataset and revision The old Release level conflated two different ideas — "one instance of a study" and "a version worth citing". Making the dataset the instance and the release a tag gives one counter instead of two and makes raw versioning identical to Icechunk's, so scientists learn the model once.
4 Bronze, Silver, and Gold are Zarr + Icechunk repositories on S3-compatible object storage. One Bronze repo per dataset; one Silver repo per dataset; one Gold repo per product, stored under its source dataset when single-source and under the project when fused. Humans never write them; every publication is a validated Icechunk snapshot. Derived data as files beside raw on NFS Icechunk gives transactional snapshots and time travel on object storage; concurrent scientific reads scale on the object store; the raw filesystem stays reserved for evidence. The deployment target is Red Hat OpenShift with cluster-supplied object storage, so Huron assumes only the portable S3 core — never a vendor extension (the portability boundary).
5 Three catalog stores, one job each — and one search index for all four layers. PostgreSQL holds structural state only (identity, sequencing, locks, registry, RBAC, audit, outbox). LanceDB owns all text, tag, and semantic matching across raw, Bronze, Silver and Gold, with layer as a facet rather than a system boundary. Storage sidecars remain the authoritative metadata content. No PostgreSQL full-text search, ever; no search fallback — LanceDB down means /search is 503 while browse keeps working. A separate catalog per layer; OpenMetadata for the raw layer and for RBAC Two implementations of one capability drift, and the rarely-exercised one is broken when needed. A scientist searching "absorbed dose" does not know which layer holds the answer. OpenMetadata was evaluated and rejected: its policies govern operations inside its own catalog and cannot authorize a read on NFS or a scoped grant on the object store, so it would add a second RBAC system to keep in agreement with the first — see Catalog & Search.
6 Full logical copy per revision. Every revision directory is complete and offline-readable; every submitted file has an independent copy. Delta chains or content-addressed pools Evidence must remain understandable with ls and jq if the platform is lost. Also: no lakeFS, no git-like indirection — corrections are naturally new immutable revisions.
7 Apache Polaris is used targeted: it catalogs Iceberg-format tabular Gold products and vends credentials for external engines. Huron's catalog stays authoritative for everything; a one-way sync mirrors published tabular Gold into Polaris. Polaris as the central catalog for all layers Polaris is an Iceberg REST catalog. Entries for Zarr/Icechunk repos or NFS trees would be names no engine can read and a second catalog that drifts. See Polaris for the fit analysis and revisit trigger.
8 Programmatic access requires user-created API keys; the web UI uses OIDC sessions. Both resolve to the same principal; keys are scoped, expiring, hashed at rest, and never exceed their owner's live permissions. Ambient site credentials or shared tokens The Python client must work from HPC login nodes and laptops with an auditable, revocable identity per caller.
9 Scientists read Bronze/Silver/Gold directly from object storage via short-lived, prefix-scoped credentials vended by the API. The control plane authorizes and pins the snapshot; the data plane is the object store. Proxying array bytes through the API Array reads are bulk and parallel; a proxy makes the control plane the bandwidth bottleneck. RBAC is enforced at grant issuance and on every renewal.
10 Raw payload expires on a per-category TTL after Bronze+Silver are verified; reproducibility-essential inputs are retained by default. Expiration writes an EXPIRED marker and never touches sidecars, checksums, or metadata. All-or-nothing raw retention MCNP runtpe/ptrac files are huge and reasonably expirable; input decks are tiny and essential. The scientist sees the consequence before choosing the policy.
11 Only Huron services write published representations. Nobody overwrites committed raw files; pipeline identities alone hold write credentials to derived repos; every publication carries validation evidence. Trusting roles with direct storage access The integrity of every layer reduces to a small set of auditable service code paths instead of the discipline of every user.
12 Stack: FastAPI + Python backend, Svelte frontend, Python client for Aether, Go-free v1. Derived layers are built and read through Xarray + Dask over Zarr + Icechunk, so pipeline code and scientist code use one array API. OpenAPI is the published contract and generates the TypeScript and Python client cores; a breaking change fails CI. Polyglot services; a bespoke chunk-processing layer One backend language, one contract artifact, generated clients — the smallest surface that serves scientists on day one. Dask means the canonicalizer and the scientist's notebook parallelize the same way over the same objects.
13 Every layer is scoped by the dataset; a canonical contract decides comparability, not storage. One Silver repo per dataset, exactly as Bronze. The datasets in a project declaring the same (profile, contract_version) are combined by concatenating their repos along run at read time, or published as a fused Gold product. One shared Silver repo per (project, profile, contract_version), appended along a run dimension — the design this replaces A shared repo had no prefix a dataset-scoped RBAC binding could name, so any credential minted for one granted more than the binding allowed; purging one dataset meant region-deleting a slab other datasets were reading; and every dataset under a contract serialized on one Icechunk branch. Comparability is still a property of the declared contract — it now decides which repos may be concatenated rather than which runs share bytes.
14 Releases are immutable tags, not a hierarchy level. A dataset has one linear revision history; a release names one revision and is never repointed. Releases containing revisions (two counters), or no named versions at all Citation requires that dataset@v1.0 resolve to the same bytes forever. Modelling raw versioning as commits-plus-tags makes it identical to Icechunk's, so the versioning story is the same in all four layers and scientists learn it once.
15 A dataset declares an entry layer; Gold stays derivation-defined. Raw, Bronze and Silver each accept data that arrives already in that form from outside the lake — a streaming feed, an instrument, published reference data — carrying an external-provenance block in place of the lower-layer references, and rooting lineage where it enters. Raw is never a prerequisite for Bronze: the v1 intake path is a manual upload by a scientist — linked to a raw revision of the same dataset when one exists, external-provenance when none does — and the automatic raw→bronze builder is deferred, since a per-profile extractor is custom code Huron does not require of projects at this stage. Gold accepts no direct entry: every product version carries a derivation record (invariant K). "Trusted" and "shippable" are properties expressed by contract validation, release tags, classification and read grants — never by promoting bytes into a higher layer. Silver defined as "whatever Bronze canonicalizes into"; Gold redefined as the pool of trusted datasets shipped to external consumers Requiring descent would force a fictitious Raw and Bronze for data Huron never received in those forms, and the retention clock has nothing to count for them. Defining Gold by trust rather than derivation would mean copying validated Silver through an identity transform — storage paid twice, staleness tracked on a copy that adds no meaning, and the word "gold" no longer describing what was done to the data.
16 One schema registry governs every structured document. Envelope, manifest, provenance, extension metadata, science profiles and canonical contracts are all rows in a single PostgreSQL schema registry — immutable once published per (namespace, name, semver), mirrored to object storage, and scoped PLATFORM / ORGANIZATION / PROJECT, where a project schema enriches the organization base it extends and ingest validates against the composed effective schema. Core schemas versioned only in the repository, plus a separate extension registry, plus profile rows — three lifecycles for one kind of thing Organizations need org-wide metadata standards and projects need to enrich them without forking them; one registry gives every schema the same immutability, governance, deprecation and recovery story, and a revision can name exactly which schema versions it validated against — forever resolvable even after a database rebuild.
17 Five human roles, roleless service accounts, governance by inherited policy. reader, developer, project_admin, organization_admin, platform_owner are the whole role vocabulary — no steward role, no "no role" entry, and no roles for service accounts: an SA is a single-purpose, organization-owned identity whose authority is intrinsic — authenticate and CRUD its org's datasets at the silver and gold layers (RBAC §2). Any developer creates datasets and commits revisions; datasets are ACTIVE on creation; admins govern through policies attached at their scope that everything below inherits (org → project → dataset), and through publication approval. A dedicated data-steward role gating dataset creation and a DRAFT → ACTIVE activation checklist The steward's only capability delta over a developer was policy attachment, which admins already held — a whole role for one act taxed every project with a second governance seat and a human gate before ingest. Inherited policy applies the same governance automatically, at the scope where authority actually lives, and validation-gated publication keeps the quality bar.

5. The MCNP thread

One worked example runs through every document: the Reactor Shielding Parameter Sweep dataset in the Huron Shielding Study project of the Nuclear Engineering organization. A scientist uploads run-0042 (input deck, outp, meshtal, runtpe, scheduler log); Huron commits Raw revision 1, builds Bronze snapshot B182, canonicalizes Silver snapshot S117 exposing particle_flux(run, energy, x, y, z); the scientist derives an absorbed-dose product with ICRP-116 coefficients and publishes Gold shielding-dose-response@1.0.0 as snapshot G021. The lineage graph is:

Raw  run-0042 / revision 1          (NFS, immutable, checksummed)
        │  source parsing (mcnp-run profile extractor, container digest pinned)
        ▼
Bronze snapshot B182                (Icechunk, source-faithful: tally_4, mesh_104, …)
        │  canonicalization (mcnp canonicalizer, science contract v1)
        ▼
Silver snapshot S117                (Icechunk, canonical: particle_flux, standard axes/units)
        │  flux-to-dose derivation (scientist's transform, parameters pinned)
        ▼
Gold  shielding-dose-response 1.0.0 = snapshot G021   (validated, published, discoverable)

6. Glossary

TermMeaning
OrganizationTop-level tenancy unit; owns projects, members, delegated roles.
ProjectThe data pond and primary authorization/quota/retention boundary.
DatasetOne body of data within a project — a run, an acquisition, a contributor's deposit (run-0042).
RevisionOne immutable, checksummed commit to a dataset; corrections append revisions (1..N, gap-free).
ReleaseA named immutable tag on one revision (v1.0) — the citable version. The raw analogue of an Icechunk tag.
Canonical contractThe versioned Silver shape a dataset declares; datasets sharing one are the members of one array space.
EnvelopeA revision's directory: metadata.json, manifest.json, COMMITTED, amendments/, payload/.
Science profileVersioned, installable definition of a data kind (mcnp-run@1.0): expected files, extractor, Bronze mapping, canonical Silver contract, validations.
Icechunk snapshotAn immutable, transactionally committed version of a Zarr repository on object storage.
ProductA named, versioned Gold deliverable with pinned inputs, transform digest, and validation evidence.
Access grantShort-lived, prefix-scoped object-storage credentials plus a snapshot pointer, issued by the API after authorization.
AetherThe compute/analysis framework scientists use; consumes Huron's Xarray-compatible open paths and runs transformations.
AmendmentProject-admin-only, append-only metadata correction on a committed revision.
ProjectionRebuildable derived state (LanceDB search tables); never authoritative.
SealingRemoving write permission from a committed revision's files (0444/0555).
