Scientist Workflows

The end-to-end journey from data on disk to a cited snapshot — every step twice, as the web UI presents it and as the Python client (huron) drives it.

1. Two doors, one model

A scientist meets Huron through two surfaces that expose the same API and the same objects: the web UI (OIDC session; browse, search, governance, guided intake) and the Python client and CLI (API key; bulk transfer, analysis, automation). Nothing is possible in one that the API forbids in the other — the UI holds no privileged credentials, and the client is the same generated OpenAPI core. The journey below is the common path for a scientist with data in hand; governance journeys (policy administration, amendments, purge) stay in Frontend §3.

0. get access          role binding + API key
1. create dataset      declare the entry layer: raw | bronze | silver
2. ingest              path A: raw upload        (originals in hand)
                       path B: bronze intake     (arrays in hand — raw optional)
3. validate & publish  service-side; evidence either way; failure publishes nothing
4. tag a release       the citable name
5. open & analyze      lazy Xarray over a scoped grant; pin the snapshot id

2. Step 0 — access

Web UIPython client
Join A project admin or org admin adds the scientist on the project's Permissions tab — reader to explore, developer to contribute; the picker offers exactly the five roles, never a “none”. The scientist sees the project appear in their catalog tree — discovery is authorization-shaped (404-not-403). —
Credentials Account page → API keys → create (scopes, optional project restriction, expiry); the secret shows once. export HURON_API_KEY=… then huron auth whoami — principal, roles, key scopes; the first debugging step for every permission question.

3. Step 1 — create the dataset, declare the entry layer

The dataset is the unit everything else attaches to: one run, one acquisition, one deposit. Creation is where the scientist answers the one question that shapes the rest of the journey — what form is the data in?

Web UIPython client
Create Project dashboard → New dataset: slug (with the immutability warning — slugs are forever), title, science profile, and the entry-layer choice rendered as a plain-language question: "What are you depositing? Original files as they came from the code or instrument (raw) · Arrays already converted to an analysis-ready container (bronze) · Data already matching a canonical contract (silver)". Choosing raw also shows the retention-policy consequence text before saving. huron datasets create --project org/project --slug run-0042 --profile mcnp-run@1.0 --entry-layer bronze; or implicitly, first ingest against a new slug (dataset.create permitting; entry layer defaults to raw).
Result An ACTIVE dataset, immediately — there is no approval gate. What governs creation is the inherited policy chain (organization → project → dataset, RBAC §3): classification default, retention, and the required metadata schemas apply from the first byte.

4. Step 2, path A — raw upload

For a dataset whose entry layer is raw: the scientist holds the original files (input decks, outputs, logs), and Huron takes them byte-exact (Raw §4–5; step-by-step control flow in Raw §6.2, concurrent writers in Raw §6.4).

Web UIPython client
Upload New revision on the dataset page opens a guided dialog: drag-and-drop for browser-practical deposits, and for bulk data the pre-filled CLI command to copy (huron upload ./run-0042 --dataset … --infer --confirm) — the UI explains and hands off rather than pretending a browser moves a terabyte. HPC outputs use register-in-place landing directories (Raw §11). huron upload ./run-0042 --dataset org/project/run-0042 --infer --confirm — manifest built and hashed locally, every submitted file uploaded into an independent revision, resume on interruption. --infer shows what the profile extractor found; the human confirms only what Huron cannot know (campaign, purpose, quality state).
Metadata Both surfaces render the same envelope form, generated from the effective schema — org base composed with the project enrichment — so a project's required fields are enforced at ingest on either door, not discovered in review.
Commit Verify → commit is atomic (Raw §5): the revision appears with its manifest, checksums and extracted parameters, immutable from the first second. With the automatic builder deferred, the dataset page shows raw: committed · bronze: — until someone converts and runs path B against this revision.

5. Step 2, path B — manual bronze intake

For arrays in hand — a dataset entering at bronze, or Bronze for a raw revision committed via path A. Raw is never required to exist first (Bronze §4a).

Web UIPython client
Files Dataset page → Add bronze data: drop NetCDF / HDF5 / zipped-Zarr files — conversion to Zarr is automatic, part of intake, never a step the scientist performs. The wizard shows what xarray will see (groups, dims, dtypes) before anything is committed. huron bronze upload ./run-0042.nc --dataset org/project/run-0042 …; programmatic: client.layers.upload(dataset=…, layer="bronze", files=[…], …). Same transfer machinery as raw: streamed, hashed in flight, resumable.
Provenance One required choice: "Where did these arrays come from?" — a dropdown of this dataset's committed raw revisions (promotion, method upload), or "No raw in Huron" opening the external-source form (system, URI, digest). Exactly one; the form will not submit with neither or both. --link-raw-revision 3 or --external-source legacy-cluster --source-uri file://… — same rule, refused server-side with a structured error if violated.
Metadata The same effective-schema envelope form as path A — organization base plus project enrichment, extensions included.
Intake The intake service (a service account — the human never holds storage credentials) opens the payload, converts it to Zarr (HDF5/NetCDF in, Icechunk snapshot out — automatic, invisible), validates against the profile's bronze checks, and publishes on pass (Bronze §4a). Both surfaces show the same job: queued → validating → published, or FAILED with structured findings and nothing published.

Silver entry. A dataset entering at silver follows this same wizard with the canonical-contract check as the validator (Silver §4) — the step the scientist sees is identical; the bar the data must clear is higher.

6. Step 3 — validation and publication

Publication is always service-side and always evidence-bearing: raw commits atomically with checksums; bronze/silver snapshots publish only after the profile's validations pass. Both surfaces show the same truth — the dataset page's per-revision materialization state (raw: committed · bronze: B183 · silver: —) and the snapshot page's validation evidence. A failed intake is a FAILED catalog row with structured findings: the web UI renders them on the job and dataset pages; the client raises them as a typed error and huron jobs show <id> reprints them. Nothing broken is ever published, so "published" needs no asterisk.

7. Step 4 — tag a release

Web UIPython client
Tag Revision history → Create release on the chosen revision: tag (v1.0), title, purpose. The UI shows the tag as a pinned label against that revision forever. huron release create --dataset … --revision 1 --tag v1.0; client.releases.tag(…). Deliberate and separate — never a side effect of ingest.

Tags are immutable (invariant M): dataset@v1.0 resolves to the same bytes forever, which is what makes it citable in a paper. The control flow, and why a tag can only ever name a committed revision, is Raw §6.3.

8. Step 5 — open, analyze, cite

Web UIPython client
Open Every dataset and snapshot page carries an open-in-Python snippet pinned to the latest published (or this) snapshot — the UI's deliberate hand-off; no in-browser array reads. ds = huron.open_dataset("org/project/run-0042", layer="bronze") — lazy Xarray over a short-lived, prefix-scoped grant (Client §3). Chunk reads go straight to object storage.
Cite Reproducibility is ambient: ds.attrs["huron"] carries the snapshot id; huron.open_snapshot("B183") reproduces the exact view forever. Papers cite the snapshot id or the release tag, never "latest".

9. What this demands of each surface

  • Web UI: schema-driven envelope forms (JSON Schema → form, from the effective schema, both intake paths); the entry-layer question at dataset creation; the bronze intake wizard — file drop with an xarray preview, the one-of-two provenance choice with the raw-revision picker, job progress, validation-evidence rendering; per-revision materialization chips everywhere a dataset is shown. These land in the intake milestones of Roadmap §3.
  • Python client: the huron bronze upload verb (client.layers.upload) sharing raw ingest's transfer core; local pre-validation against the fetched effective schema (fail before uploading, not after); typed structured-finding errors; huron jobs show. The client remains the bulk-data door; the UI remains the guided door — same API underneath.
