Apache Polaris Integration

Targeted, honest, one-way: Polaris catalogs Iceberg-format Gold products for external engines and vends the credentials to read them. Nothing else.

1. Fit analysis

Apache Polaris is an open-source Iceberg REST catalog: namespaces, Iceberg table metadata, its own RBAC (catalog/namespace/table grants to principals and principal roles), and credential vending — an engine asks Polaris for a table and receives scoped, short-lived object-storage credentials for exactly that table's data location.

Huron assetPolaris fitVerdict
Tabular Gold products (Iceberg) Native. Spark/Trino/DuckDB/PyIceberg connect to Polaris and query directly. Register (the integration)
Bronze/Silver/array-Gold (Zarr + Icechunk) Not an Iceberg format. A generic-table entry would be a name external engines cannot read, duplicating Huron's catalog with none of its semantics (snapshots, validation, lineage). Stay out
Raw envelopes (NFS) Polaris has no concept of POSIX file trees, and raw access must stay API-mediated for RBAC anyway. Stay out
Catalog of record / search / lineage Would make Polaris a second authority that drifts from PostgreSQL + LanceDB — exactly the two-systems-answer-one-question pattern Huron bans. Stay out

Revisit trigger, recorded now. If the ecosystem shifts — Polaris generic tables gain real multi-engine read semantics, or Icechunk grows an Iceberg-REST-ish catalog protocol that Polaris federates — the "stay out" rows get re-evaluated. Until an external engine can actually read the entry, cataloging it in Polaris is decoration with a drift cost.

2. Integration architecture

Huron catalog (authoritative)                       Polaris (mirror, Iceberg only)
────────────────────────────                        ─────────────────────────────
product_versions row:                               catalog:   huron
  status = PUBLISHED,  shape = tabular    ─sync─▶   namespace: {org_slug}.{project_slug}
  iceberg_ref = s3://…/iceberg/…                    table:     {product_slug}__v{major}
                                                    grants:    derived from Huron RBAC
       ▲                                                     │ credential vending
       │ one-way; Huron never reads state back               ▼
   Svelte / Python client / API                      Spark · Trino · DuckDB · PyIceberg
  • Sync worker (single replica) consumes outbox events for tabular publications: creates the namespace if absent, registers/updates the table pointing at the Iceberg metadata location under the product's Gold prefix, applies grants, records polaris_synced_at. Idempotent; a nightly sweep re-converges drift (Huron wins).
  • Version mapping: the table tracks the latest published version per major (__v1, __v2…); minor/patch updates append Iceberg snapshots to the same table, so engine users get history via Iceberg time travel while breaking changes are separate tables. WITHDRAWN versions are rolled back; RETIRED products are dropped from Polaris (the authoritative Icechunk data remains in Huron).
  • Deployment: Polaris runs beside Huron in the namespace, backed by its own PostgreSQL database, exposed only to engine networks; bootstrap and principal management are Terraform/lakectl-driven, not hand-edited.

3. Authorization mapping

Huron RBAC remains the source of truth; Polaris grants are a projection of it, maintained by the sync worker:

HuronPolaris projection
Project role reader and above (may read published Gold) Principal role huron-{project_slug}-readers with TABLE_READ_DATA on the project's namespace
Classification gate on a product Products above a project-configured classification ceiling are not synced at all — engine-side enforcement is coarser than Huron's, so sensitive tables simply never appear there
Human/engine identity Users obtain Polaris engine credentials through Huron (POST /polaris/credentials), which checks Huron RBAC and returns short-lived Polaris principal credentials mapped to the right principal roles — one front door, one audit trail
Huron service identities A single sync principal with catalog-admin on the huron catalog; no human holds Polaris admin

The rule that keeps this safe: access granted via Polaris must never exceed access the same principal has in Huron. The sync worker enforces it constructively (grants are only ever derived from Huron bindings), and the nightly converge job alerts on any grant it did not derive.

4. Credential vending — division of labor

PathVendorScope
External engine → tabular Gold (Iceberg)Polaris Per-table storage credentials, engine-native flow
Python client / Aether → any Icechunk layerHuron API (see API — access grants) Per-repo-prefix STS credentials, read-only, short TTL

Two vending doors, deliberately: they serve different protocols and clients, both derive from the same RBAC, and neither hands out anything broader than one repo/table prefix. Consolidating on Polaris for Icechunk grants would put a non-Iceberg concept inside an Iceberg catalog; consolidating on Huron for engines would mean re-implementing the Iceberg REST spec. Skip both consolidations.

5. Failure posture

Polaris down ⇒ external engine access to tabular Gold degrades; nothing else in Huron notices — no Huron read path, publication path, or search path touches Polaris synchronously. Sync events queue in the outbox and converge on recovery. Polaris state is fully reconstructable from the Huron catalog (lakectl polaris resync).
