# P3 — original interview proposal

Historical input, preserved verbatim below. The settled contracts are in [P3_DESIGN.md](P3_DESIGN.md); this proposal is not an implementation instruction.

2. Record contracts. Three new document schemas, all JCS, all write-once, all self-identifying.
- PURGED, urn:huron:purged:1: schema, revision id, dataset id, manifest digest, purge record id, requester, approver, reason, executed instant, audit event id. Written before the first unlink.
- Expiry records, expired/0001.json and so on, urn:huron:expired:1: schema, revision id, dataset id, manifest digest, sequence, executed instant, audit event id, and a removed list of entries each with path, size, digest, category, and reason. Numbered because categories carry different TTLs, so one revision expires more than once.
- Amendments, amendments/0001.json, urn:huron:amendment:1: the fields the in-memory dataclass already has, plus revision id and schema, so a misplaced file is self-detecting.
Ordering is by sequence number only, gap-free from 1, exactly as the current fold enforces. Timestamps are descriptive. Expiry records have the same rule.
Invalid records are any file that is not its own canonical form, fails its schema, names a different revision, or breaks the sequence. The reconciler records a finding on that revision, stops importing at the first invalid record, and never deletes or rewrites the file. Decision for you: what the API serves meanwhile. I recommend serving the base document plus the valid prefix of amendments, with the finding visible on the revision, rather than refusing the read.
Conflicting records arise only with PostgreSQL present: a file whose digest differs from its row, or a row with no file. Storage leads for these as it does for commits, so I recommend P5 writes the file before the row. Then file without row is imported automatically, row without file is DEGRADED, and content disagreement is a finding with no automatic repair.
6. Lawful removal. The write-ahead ordering from question 1 gives the reconciler three states per marker: absent, in progress, complete. The rules:
- Marker present and listed entries still present: finish the removal, reseal, then update the row state. This is the interrupted-deletion path and it is fully automatic.
- Marker present and the row still says COMMITTED: update the row. The marker was written first by design, so the database is merely behind.
- Row says PURGED or EXPIRED and no marker exists: DEGRADED, never repaired automatically.
- Integrity checks skip entries a valid expiry record names and skip the manifest and payload entirely under PURGED. A purged envelope with a manifest still present is an unfinished purge, not a violation, until the reconciler finishes it.
Two shipped facts constrain this. Revision state vocabulary already has COMMITTED, EXPIRED_PARTIAL, EXPIRED, PURGED, DEGRADED. And the P2 verification sweep found that the in-memory adapter's latest-revision query ignores state while the PostgreSQL one filters to COMMITTED. P3 must make those agree before it writes PURGED or EXPIRED, or the two backends diverge in tests. I recommend latest means highest number regardless of state, since the allocator already numbers over every row.
3. Recovery authority. Automatic repairs are exactly those that add or restore without destroying:
- Import a row from storage evidence: orphan envelope, amendment file, release file, marker-derived state.
- Regenerate derived artifacts: INDEX.json, and repoint a torn CURRENT.json at the highest generation.
- Restore protection without changing content: reseal, fix directory modes.
- Finish a removal a valid marker authorizes.
- Resolve an abandoned COMMITTING session under the rules in question 4.
- Clear DEGRADED, but only after a full payload verification of that revision passes.
Everything else needs an operator: deleting any row, deleting any file outside staging, any content disagreement such as a digest mismatch or a row without an envelope, conflicting identities, and synthesizing missing parents.
4. Abandoned commits. The shipped code creates the gap deliberately: begin_commit skips the lease once COMMITTING, and the lapsed-session query never returns COMMITTING. So today a dead driver holds the dataset lock forever, and nothing distinguishes it from a driver mid-way through a long fsync of a 1 TiB envelope. The reconciler needs two things.
- A liveness signal during commit. Decision for you, and I recommend it: the commit path touches updated_at on a background heartbeat during the storage steps. Then abandoned means COMMITTING with updated_at older than a grace window of a few heartbeat intervals. Without the heartbeat, the grace window must exceed the worst-case seal and fsync time, which means hours, and the lock stays held that long.
- Storage decides the outcome. Final directory with COMMITTED present: import the row and mark the session COMMITTED. Staging with COMMITTED present: the envelope is complete by construction, so finish the rename, then import. Staging without a marker, or nothing at all: mark the session FAILED, which frees the number and the lock, and leave staging to the sweeper.
Every transition fences on the session etag, so a driver that wakes up late loses the race cleanly. The hazard the grace window guards against is real: a driver that renames after the reconciler failed its session publishes a directory whose number a retry may already have re-taken. That is the conflicting-identities case in question 8, and the heartbeat is what makes it improbable rather than merely rare.
5. Integrity verification. Two tiers, because payload rehashing is proportional to bytes and everything else is proportional to entries.
- Every run, always: directory names parse, the four documents exist and are canonical and schema-valid, document digests match COMMITTED and the row, markers agree with payload presence, every payload file's size matches the manifest by stat, mode is 0444 or 0555, owner is the storage identity, link count is 1. That last check is the independent-copy check: a hardlink is the one way a shared file could appear, and stat reveals it for free. INDEX.json staleness is a digest comparison against a rebuild from the rows.
- Payload digests, budgeted: a per-run byte budget, a rotating cursor, and a recorded last-verified instant per revision so every revision is rehashed within a target period. Never-verified and oldest-verified go first. Full rehash on demand for one dataset or revision. This needs a place to record the instant, which I would make a small table rather than a column on the immutable revision row.
Size mismatch by stat is already DEGRADED without hashing, which catches truncation cheaply.
7. Staging cleanup. Eligible directories are those whose session is ABORTED, FAILED, or COMMITTED and has been terminal for at least one grace period, plus directories with no session row and a modification time older than 24 hours. A COMMITTING session's staging is never eligible, since the reconciler owns it. Concurrent uploads are handled by two layers: the API already fences writes on session state before touching disk, and the grace period must exceed the longest possible part upload so a check-then-write straggler cannot land after deletion. Deletion itself should first rename the directory into a trash area inside staging, then remove it. The rename is atomic, makes deletion resumable, and turns any late write into a failure rather than a resurrected directory. The fraction guard compares eligible count to total staging count and refuses above a configured share, with an absolute floor so one of one does not trip it. Dry run lists every candidate and the guard's verdict, deletes nothing, and exits nonzero when the guard would have refused.
8. Rebuild boundaries. Reconstructed from the tree: organizations, projects, and datasets from generation documents; revisions from COMMITTED plus metadata.json, with state derived from markers; amendments from their files; releases from the release files; INDEX.json regenerated. From backups only, as the design already states: role bindings, API keys, audit events, idempotency records, outbox, jobs, open ingest sessions. Decision for you: purge records and holds. If the PURGED marker carries requester, approver, and reason as I proposed, the rebuild can synthesize the EXECUTED purge row. Holds cannot be rebuilt and I would not try.
Missing parents: metadata.json carries the full reference chain, so the rebuild knows the parent's slug and id, but not its title or other descriptive fields. It should refuse to activate and report, unless the operator passes an explicit flag that creates placeholder rows and records a finding on each. Conflicting identities are one slug with two ids, one id at two paths, two revision directories with one number, or a generation document disagreeing with its directory name. The rebuild imports everything consistent, reports every conflict, and refuses to activate while any remains.
9. Rebuild execution. The service is offline, which the scenario already implies since there is no database to serve from. The rebuild writes into a fresh migrated database and refuses a database that already holds structural rows. Reconciling into a live database is the reconciler's job, not rebuild's. It runs in phases, hierarchy then revisions then amendments then releases then indexes, with every write keyed by id so a rerun after a crash continues rather than duplicates. A validation phase compares the rebuilt inventory against the tree and produces a report. Activation is the operator pointing the service at the database after the report is clean. The first reconciler run after activation must report nothing the rebuild report did not already list.
10. Findings and operations. The findings table already exists with code, severity, path, subject id, detail, and a resolution instant, and the schema notes the severity vocabulary is undecided. I recommend three levels: REPAIRED for automatic fixes, WARNING for things like a stale index or an unsealed directory, and DEGRADED for anything that changed a revision's state or needs an operator. A finding is keyed by code and path. Re-observing an open one updates it, no longer observing one resolves it automatically, and operator-only findings resolve by command with a reason recorded as an audit event. Commands: reconcile with scope, verification depth, and dry-run flags; sweep with dry-run; findings list and resolve; rebuild with a validate step and an activate step; and a session-recovery command for one COMMITTING session. These run inside the namespace under the storage identity, not over HTTP. A read-only findings route for platform owners is worth adding, but the writes stay on the command line. Alerts fire on every DEGRADED finding, on a fraction-guard refusal, and on a reconciler run that did not complete. Scheduling matches the architecture page: sweeper every 15 minutes, reconciler nightly plus on demand.
11. Acceptance. The scenarios that must pass, each with a fixture rather than a live P5 workflow:
- Crash: every commit crash row from layer-raw §5 resolved by the reconciler; a COMMITTING session abandoned in each of the four storage states, with the correct outcome and the lock released; an interrupted purge and an interrupted expiry completed and reported lawful.
- Concurrency: reconciler racing a live commit retry, exactly one wins and no duplicate row; sweeper racing an in-flight part upload, nothing live deleted and nothing resurrected; two reconciler runs at once, identical findings and no duplicate imports.
- Corruption: a flipped byte, a truncated file, a hand-edited manifest, a missing payload without a marker, a hardlinked payload, a wrong owner, an unsealed directory, a torn CURRENT.json, a stale and a missing INDEX.json, an amendment with a sequence gap. Each yields its named finding, the repairable ones are repaired, and the rest change nothing.
- Database loss: drop, migrate, rebuild, and the inventory matches, with a purged and an expired revision reported lawful. Kill the rebuild mid-phase and rerun to the same result. Rebuild against a tree with a missing parent and one with conflicting identities refuses to activate. Fraction guard refuses, dry run deletes nothing.
