huron/core

Where authenticated Huron operations coordinate domain rules, storage, database transactions, and retry behavior.

This is a source-linked map of the six owners in src/huron/core/: Foundation, Security, Catalog, Raw, Metastore and Rawstore. It describes the verified domain-owned migration; delivery status and evidence remain in the roadmap. Source links are relative to this repository, so keep the HTML in design/ when opening it locally.

1. Orientation

Domain owners colocate rules and complete workflows. Injected adapters perform I/O. Raw's private IngestService coordinates commit through its own RawStore and HierarchyStore ports; the POSIX and PostgreSQL adapters live in core.rawstore and core.metastore.

Actor-bound operations

Catalog creation/collections, Raw ingestion/reads/releases and Security identity/governance use AccessPolicy bound to an authenticated actor. Authentication workflows establish that actor from credentials.

Protected implementations

Catalog, Raw and Security have protected _impl/ subtrees. Root exports publish operations; RawRuntime constructs private ingestion/reader mechanics. Source links into these files do not authorize cross-package private imports.

Consumer-owned interfaces

Each domain owns its ports and values. Foundation owns canonical JSON, identifiers/names, errors, time and retry primitives; Security owns narrow catalog-fact projections. Adapters can satisfy several ports without merging domain responsibilities.

Trusted maintenance

Raw's public expire_lapsed() is explicitly deployment-trusted; it is not a scientist operation.

The enclosing core.__init__ is minimal: Foundation imports do not initialize workflows or adapters. Operations are published by each domain root. Import contracts classify every Core sibling, include type-only edges in cycle checks, protect implementations, and forbid domain-to-adapter dependencies.

applications → public domain interfaces + adapters (composition/lifetime)
security     → foundation
catalog      → security, foundation
raw          → catalog, security, foundation, schema
metastore    → catalog, raw, security, foundation
rawstore     → schema.storage
foundation   → no Huron imports

Permitted direct package DAG; internal module cycles are a separate concern.
Domains never import adapters, FastAPI, application settings or database drivers.

4. Authorization: actor → discovery → capability

AccessPolicy owns the actor reference and uses Security-owned fact ports. Its visibility(), require(), and bindings() calls use fresh local binding caches rather than retaining grants across operations.

  1. visibility_for_principal() combines current bindings, project classifications, and the parents of dataset-scoped grants through RoleBindingAuthorizer.visibility().
  2. scope() calls resource_scope(). Hidden and absent targets fail discovery before capability denial. Metastore's SecurityFacts projects server-resolved ancestry through existing visibility predicates.
  3. require() calls check(), which accepts only Decision.ALLOW from security.rules.decide().
  4. require_claim() separately checks that an idempotency claim belongs to the authenticated actor.

bindings_for_principal() reads stored human/group bindings. For service accounts, it resolves the account and synthesizes organization-scoped authority; missing or disabled accounts get no bindings.

Read the operation’s actual rule. Upload mutation methods use _owned() / _owned_file(). An owner can abort without the normal Raw-write check; a different actor needs project-update authority. Policies.create_policy() and list_policies() admit any authenticated actor; attachment requires scope-specific authority. Raw retrieves full datasets through actor-bound DatasetCollection, while Security consumes only fact projections.

5. Catalog operations

Create identities: CatalogCreation

create_organization(), create_project(), and create_dataset() authorize, validate configuration, and claim the operation. A dataset is a stable identity; creation alone does not produce a Raw revision.

CatalogCreation.create_dataset()
  AccessPolicy.require() + require_claim()
  validate slug / entry layer; resolve authoritative parents
  CreationStore.transaction():
    claimed_result() → existing record on a matching retry
    writer.insert_dataset()
     _publish_created():
       await GenerationDocuments.write() → off-thread GenerationStorage.write_generation()
       writer.remember() → receipt kind derived from the created entity
  database transaction commits

DatasetCollection.describe(id, DescriptionChange)
  authorize → Dataset.describe(expected_version, ...)
  unchanged object? return without opening a transaction
  DescriptionStore.transaction():
    writer.datasets.describe() → compare-and-swap version check
     read committed ancestry → await GenerationDocuments.write()
  database transaction commits

GenerationDocuments.write() is asynchronous and owns off-thread serialization and durable storage. It adds the generation schema identifier and canonicalizes the record; storage writes generations/NNNNNN.json, then atomically replaces CURRENT.json. Creation's shared _publish_created() records the retry receipt only after that write succeeds, with the receipt kind derived from the concrete entity. Each creation operation retains its validation, parent resolution, typed insert and transaction. DescriptionChange distinguishes omitted values from empty replacements; slug changes are refused.

Discover, release and govern through their owners

The API's named hierarchy PATCH bodies share DescriptionPatch.to_change(); handlers parse If-Match after discovery/capability guards, then pass DescriptionChange into Core. Simple hierarchy, release and governance responses return typed Core objects through explicit FastAPI public response models, which filter internal fields. See the API contract for omitted/null/empty semantics.

  • Catalog's organization/project/dataset collections expose typed get(), browse(), and describe(). Browse checks parent discovery and returns visibility-filtered keyset windows.
  • Raw's Releases.create_release(), release(), releases(): tag creation resolves an exact registered revision without adding a state or payload-read predicate, inserts a row, and writes RawStore.write_tag_once() within the open transaction.
  • Security's Bindings.grant_role(), revoke_role(), get_role_binding(), bindings_at(): scoped role administration through BindingStore.
  • Security's ServiceAccounts: organization-scoped creation, discovery, listing and disablement.
  • Security's Policies.create_policy(), attach_policy(), list_policies(): persistence; attachment checks the target’s policy-attach capability. All stored attribution comes from the bound actor.
  • layers(): describes declared layer capabilities and current caller decisions. It does not execute Bronze, Silver, or Gold processing.

Two stores, ordered writes. Creation, description, and release-tag workflows perform filesystem I/O while a database transaction is open. A filesystem exception rolls back database work, but a database rollback cannot undo an already-durable filesystem write. This is different from the short, separated database transactions in Raw commit below.

The crash seam: publication may be durable before transaction B succeeds. A matching retry uses the frozen CommitIntent, verifies the exact stored evidence, and finishes the database work. Existing final storage is verified on replay; an index-write failure is logged without failing an already successful commit.

Values crossing the interfaces: Raw owns ManifestEntry, IngestFile, IngestSession, CommitIntent, and RevisionRecord. Its published types.SessionLedger pairs a session with files. Foundation's Clock is injected; blocking Rawstore calls run through asyncify(). The API schedules/cancels/logs expiry calls through RawRuntime.expire_lapsed().

RevisionReadService.payload_file(record, path)
  → _readable(record.id): freshly resolve identity + require Raw data.read
  → RevisionService.payload_file(authoritative_record, path)
    → validate_manifest_path(path)
    → RawStore.read_document(manifest.json) → decode_manifest()
    → compare manifest digest with database record
    → resolve a listed entry → RawStore.stat_document(payload path)
    → compare file size → PayloadFile(entry, location, stat)

manifest_file() returns a manifest location and stat after authorization. PayloadFile also contains a path and stat, not an open file descriptor or the payload bytes. The transport streams the returned location. Individual payload reads check the stored manifest digest and file size; they do not hash the full file on each download.

8. Identity operations

IdentityService consumes AccessPolicy, PrincipalStore, CredentialStore, SessionStore, ApiKeyWriter, and actor-bound ServiceAccounts, all owned by Security.

  • create_user(): require system user-management capability, create identity, hash the initial password off-thread, and persist its credential.
  • set_password(): _user() resolves an authorized human identity; persist the new credential, then _revoke() browser sessions and API keys.
  • disable_user(): disable the principal, then revoke sessions and keys.
  • issue_key(): create a key for the authenticated actor and return the record plus its one-time cleartext token.
  • issue_service_account_key(): _account() checks management authority and exact organization membership; reject disabled accounts before storing a new key.
  • disable_service_account(): disable through ServiceAccounts, then revoke programmatic credentials, with an early return for an account disabled before this invocation.

These methods sequence calls to individual stores. There is no shared transaction spanning principal, credential, session, and API-key adapters in this class. Several timestamps use datetime.now(UTC) directly; clock injection is not uniform across core.

Authentication, self-access and bootstrap

Security's root exports also publish PasswordAuthentication.login(), OidcAuthentication.begin()/finish() and CredentialAuthentication.resolve(). Password verification and optional rehash are bounded off-loop; OIDC owns signed state/nonce/PKCE checks, collision/disabled-user refusal, provisioning and persisted session issuance. Credential resolution accepts a transport-extracted bearer_token: None is absent, while a present empty token is refused without session/development fallback. The API owns raw header parsing, mapping missing/empty headers to None and applying removeprefix("Bearer ").strip() to nonempty headers. Constructors accept ports, clocks and plain configuration.

ApiKeyResolver and SessionResolver accept an optional Foundation Clock; explicit now overrides it. Otherwise they sample time after awaited lookup and matching-secret verification, defaulting to UTC wall time. API-key revocation precedes its sample; session revocation follows its sample, and both precede expiry. Session expiry, throttle and idle-extension arithmetic share that instant. The credential workflow passes clocks to the resolvers and performs key bookkeeping only after successful resolution. OIDC wiring passes login_flow_cookie(settings).max_age as flow_max_age, binding the validator to the issued cookie's lifetime.

terminate_session() checks self-session ownership (bearer logout is a no-op); self_access_summary() returns current sorted scope/capability results. bootstrap_platform_owner() is an idempotent, deployment-trusted configured SYSTEM grant. The API retains request extraction, cookies/CSRF, redirects, serialization and process lifetime. See the authentication atlas for the complete collaboration.

10. Reading and test guide

“How does an upload become durable?”

Read raw/runtime.py → raw/_impl/ingestion.py → raw/_impl/ingest.py → rawstore/store.py and metastore/ingest.py. Start with IngestService.commit(), then trace completion backward.

“Where is a dataset created or renamed?”

Read Catalog's _impl/creation.py and collections.py → types.describe() → _impl/documents.py → Metastore. Titles/descriptions change; storage slugs stay fixed.

“Why can this actor see this resource?”

Read Security's _impl/access.py → scopes.py/facts.py → rules.py and Metastore's visibility-filtered projections. Discovery and byte-read capability are separate decisions.

Behavioral evidence to inspect

  • Core workflow unit tests: reusable operations independently of HTTP.
  • Catalog-store contract tests; catalog creation and description integration tests.
  • Verified Raw ingestion integration tests; process-death contract tests; Raw acceptance gate.

These are source-navigation links, not a claim that the suites were run to produce this document. The Makefile and repository instructions define implementation gates.

Scope: observed core implementation. Search projection, Ray/Zarr execution, derived-snapshot publication, and full automated recovery are not implemented core workflows in this map. Consult architecture, Raw contracts, and delivery status for their design context.
