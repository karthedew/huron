Apache Polaris Integration

Huron beta wraps Polaris catalogs and its native Icechunk extension. Polaris owns catalog metadata and access grants; Huron owns human login and administration workflows.

Live catalog and Icechunk workspace

The catalog home at / lists authorized Polaris catalogs. Each Huron organization owns one or more Polaris catalogs. Organizations provide membership and administration; catalogs group programs or data domains with shared storage and governance. Dataset type is independent: Raw generic tables, Iceberg tables and Icechunk repositories can share a namespace. Bronze, silver and gold describe processing stages, not formats. No separate program entity is introduced in this beta. /browse?catalog=… shows only the selected catalog within its owning organization, with a filesystem-style namespace folder tree and repository leaves, preserving nested namespace boundaries and pagination tokens in stable, server-rendered URLs. /polaris redirects existing bookmarks to these main views.

Repository operations use Polaris's native list/register/load/unregister and read/read-write credential endpoints. Registration does not initialize Icechunk, and unregistering leaves storage intact. Icechunk initialization and commit/snapshot/branch/tag operations remain SDK responsibilities; those APIs are not supplied by Polaris.

Browse uses a compact full-height Explorer beside a dataset pane. The pane opens Overview, Schema, History, Permissions, Policies and Lineage through stable URL selections. Schema describes actual Zarr groups and arrays: dimensions, shape, data type, chunks and attributes. History reads actual Icechunk snapshots and references; branch selection changes the inspected snapshot. Repository operations are available in an explicit disclosure. Catalog settings remain in application navigation rather than the dataset body.

Managed Raw uploads

The browser uses a same-origin SvelteKit bridge. Each operation rechecks the active Huron account, organization ownership/membership, and current principal-role/catalog-role grants from native Polaris RBAC. Metadata visibility and the Huron admin label alone grant no file access. Data read/write and new-table creation are evaluated separately, with exact namespace-component ancestry. Other Polaris authorization modes fail closed.

The bridge signs a server-only, short-lived delegation bound to actor, upstream endpoint/realm/catalog/namespace/name, operation, request bytes and concurrency/idempotency headers. A dedicated Python router validates this delegation and maps the upstream target to a durable internal hierarchy. Request-scoped authority invokes the existing Raw workflow; it does not persist broad scientist grants or accept development identity headers. All session, file and revision IDs are checked against their mapped target.

Raw publication remains storage-first and uses the existing atomic database recording of revision, outcome, audit, outbox and retry receipt. Each revision owns exactly its submitted files. A stable Polaris registration follows commit under the actor's own upstream identity. These services have no shared transaction: a committed revision may have pending registration; retry registers the same dataset and acknowledges the same revision. Registration never drops/recreates a table or updates an unguarded latest-revision pointer. Browse history and file downloads require current Raw read authority.

The local launcher runs the Raw service at 127.0.0.1:8080, with separate PostgreSQL 16 huron_raw storage at port 5440 in the persistent huron-raw-local-data Docker volume, and .local/huron/raw files. Configure the server-only HURON_RAW_API_URL, a shared HURON_RAW_BRIDGE_SECRET and HURON_RAW_POLARIS_AUTHORIZATION=rbac when deploying. The persistent key is separate from browser credentials. Huron workspace organizations can regroup catalogs without changing their stored Raw identity.

Organization ownership and membership

Huron persists organization identity, catalog ownership and membership in a private, endpoint/realm-bound sidecar beside the account store (override with HURON_ORGANIZATION_STORE). Catalog names are unique within a Polaris realm and have exactly one Huron owner. Organization membership and the current user's own Polaris visibility are intersected for every browse/settings request and catalog mutation. Organization admin manages membership and descriptions but confers no Polaris catalog privilege.

On the first migration, the three existing science catalogs join NASA Science. Other existing catalogs join Huron workspace. Only people with pre-existing Polaris assignments gain ordinary membership; existing catalog admins are not promoted to organization admins. No data or Polaris grants change. New upstream catalogs remain unassigned and visible only to the global administrator until assigned. Catalog reassignment does not transfer memberships or grants. Removing an organization member requires revoking that person's Polaris roles in the organization's catalogs first.

Default Huron admin creates organizations and catalogs. Initial catalog onboarding also enrolls the person in the owning organization, while the actual Reader/Writer/Admin grant remains in Polaris. These are separate durable operations: failures report partial setup and can be retried. Organizational grouping is a Huron workspace control; direct Polaris clients are governed by Polaris roles. It does not add an independent upstream tenant boundary.

Mixed dataset types

The explorer lists native Icechunk tables, native Iceberg tables and generic-table registrations. Only generic format raw, huron.raw or an explicit huron.dataset-type=raw marker is labeled Raw; other generic formats retain their actual identity. Generic APIs expose registration metadata. Managed entries additionally carry huron.raw.service=huron-raw-v1 and a stable huron.raw.dataset-id; their detail page reads Huron revision history, manifests and authorized file bytes. External entries remain metadata-only. Raw registration does not upload files or publish a revision. Iceberg registration accepts an existing metadata-file URI through the native catalog register endpoint with overwrite disabled.

Layer filters derive from huron.layer and explicit bronze/silver/gold namespace segments. Conflicts are visible, and new Raw registration validates agreement. Existing namespaces and sample data are not relocated. Version-specific transformation lineage, previews and publication remain planned.

This beta decision supersedes the earlier Iceberg-only mirror and Huron-to-Polaris authorization projection proposal on this page. Polaris is the authority for the web catalog and its grants. Huron does not duplicate Polaris catalog-grant assignments; its separate organization-membership ledger controls workspace grouping and administration. The existing Huron scientific core retains its own Raw publication contracts; the Raw bridge connects immutable revisions to stable Polaris generic-table registrations. Scientific transformation validation, classification-policy mapping, lineage and compute integration are not claimed by repository registration.

Frontend server modules own HTTP transport, deployment settings and human authentication. Components receive typed page/action data through the API seam. Upstream client credentials, OAuth tokens and vended storage secrets never enter browser storage or serialized page data. Explicit creation/rotation of an external service principal displays its new secret once; Huron-managed account credentials are not exposed or rotated through that interface.

The read inspector checks the user's Polaris data-read authority before opening storage. A fixed Python helper uses Icechunk and Zarr to read metadata only, with bounded execution and response size. FILE locations must resolve inside configured repository mounts. Inspection does not download array chunks or write snapshots. An unavailable runtime, uninitialized repository or unsupported storage provider produces an explicit inspection state while registered catalog metadata remains usable.

Permissions project applicable catalog, ancestor namespace and exact table grants. Ordinary users see only their own role assignments; authorized access managers can inspect relevant assignees. Icechunk has no native Polaris policy attachment target in this checkout, which the Policies tab states explicitly. Source lineage shows committed source/import metadata; it does not assert a scientific publication or downstream derivation graph. Native Iceberg metadata, where present, comes from its own table endpoints and remains distinct from Icechunk.

Human identity and catalog membership

A durable local account store provides username/password authentication using salted scrypt hashes. Per-user Polaris credentials are encrypted with an independently persisted private AES-GCM key. An opaque HttpOnly, SameSite cookie identifies a process-local session. Sessions expire, terminate on restart, and are invalidated by password changes or account disabling. The default admin user uses deployment bootstrap credentials and manages catalogs and Huron accounts.

Self-registration defaults off. Administrators manually create a Huron user, which provisions its individual Polaris principal and principal role without catalog access. Catalog settings assign Reader, Writer or Catalog administrator in Polaris. Membership reads inspect Polaris assignments, not local account attributes. Fixed Huron roles carry an ownership marker; role/grant drift is reconciled when membership is configured. Their preset privileges and managed identities cannot be modified through advanced raw controls.

Ordinary users cannot call Polaris's realm-wide catalog directory. Huron uses bootstrap authority only to discover candidate catalog names and role assignments, then fetches catalog metadata using the user's own client. Only that authorized metadata is returned. Every namespace, repository and mutation is performed with the authenticated user's Polaris principal. Undiscoverable resources render as 404. Membership changes preserve an active catalog administrator and default administrator access.

Endpoint and beta deployment

Server configuration (web/.env in development) sets POLARIS_URL, POLARIS_REALM, bootstrap credentials and HURON_ACCOUNT_STORE; see web/.env.example. Client-selected URLs are unsupported. Each endpoint/realm requires its own account store, and mismatches fail closed. Persist the account document, organization sidecar, private encryption key, Polaris database and repository storage. Production uses the adapter-node build with a configured public origin and HTTPS.

The local launcher uses .local/polaris/ for PostgreSQL, private bootstrap credentials, package snapshots and repository storage. Huron initializes .local/huron/initial-admin.json with the generated default password. Changing the admin password removes that seed file. The launcher respects server environment and web/.env endpoint configuration.

HURON_ICECHUNK_PYTHON selects the inspector runtime; HURON_ICECHUNK_READ_ROOTS names approved FILE repository mounts. Both settings are server-only. The local stack mounts the existing example and NASA repository roots. Deployments must provide the fixed inspector helper and its SDK environment alongside the Node application.

Reproducible NASA examples

scripts/polaris-dev.sh samples imports bounded real scientific datasets into three disjoint FILE-backed catalogs: geoscience, heliophysics and international_space_station. Geoscience sources are public Zarr; ACE magnetic-field and ISS TSIS-1 irradiance CSV measurements are converted into Zarr arrays. Source coordinates, units, quality fields, packed-value scale/offset, object checksums and exact selection are preserved in committed Icechunk metadata. Import retries verify and reuse the existing snapshot; they do not overwrite it.

Sources: NASA JPL MUR, distributed as public Zarr by AWS Open Data; NASA POWER public Zarr. Heliophysics uses NASA CDAWeb ACE data; ISS uses TSIS-1 measurements from the station. Original mission downloads are retained under .local/polaris/source-files/. The Raw ingest page uploads selected files through the Huron Raw API and registers the resulting dataset in the selected organization's Polaris catalog. The external example Raw registrations remain unchanged; ingest their source files into a new managed dataset to publish Huron revisions.

Storage access

Polaris authorizes Icechunk credential requests at the repository root. The browser sees prefix, availability and expiration summaries only. FILE storage returns no vended credentials; direct SDK access is controlled by OS permissions and supports a single local writer. Deployments requiring enforced storage isolation or concurrent writers must configure a supported object store and Polaris's storage/STS settings.

Failure and recovery

Polaris unavailability is shown as an upstream failure rather than substituted fixture data. Catalog and user provisioning span several Polaris requests; interrupted operations may have persisted earlier steps. Catalog creation retries accept only the identical configuration and complete managed administrator setup. User provisioning cleans up newly created principals/roles on failure. Account changes use locking and atomic file replacement. Local data and grants survive launcher restarts; sessions do not.
