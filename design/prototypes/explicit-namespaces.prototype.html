Assessment: simplify placement first
Recommend evaluating manual namespaces + a catalog’s exact schema version when a catalog contains one coherent kind of scientific collection. It removes a real source of coupling: a descriptive field no longer doubles as a path component. It does not remove the difficult storage, security or concurrency work.
ModelPlacement and validationTradeoff
Current design: derived namespaces + catalog schemaMetadata drives namespace/name. Each collection pins identity config; current catalog schema drives descriptive validation.Standard paths, but slug collisions, placement vocabulary, frozen identity and two-config composition must agree.
Candidate: manual namespaces + catalog schemaExplicit namespace/name; catalog binds one exact immutable schema version for all collections.Simpler validation selection and metadata editing. Heterogeneous catalogs need a separate catalog or a deliberately designed future override.
Alternative: manual namespaces + per-collection schemaSame placement simplification; each collection selects and pins its own schema/version.Supports heterogeneous work, but adds per-collection selection, adoption, permissions and schema-filtered discovery. Catalog-wide enforcement becomes less direct.


The latest request favors catalog assignment; the earlier per-collection idea remains an alternative, not a settled requirement. There is no measured line-count estimate.


Complexity that can go
  • Slugification as placement, namespace_fields, collection_name field/generator rules and dependent placement vocabularies.
  • Pairing pinned identity layout with current descriptive schema during validation.
  • Automatic namespace attachment/pruning and their create/delete races.
  • Frozen metadata identity fields and metadata-to-path recomputation in moves.
Complexity that remains
  • Names, reserved paths, depth, uniqueness, foreign keys, authorization, version checks and concurrent creation.
  • Org-base schema composition, secure validation, immutable schema publishing and explicit adoption.
  • NFS permissions, server re-hashing, durable publication, audit and storage/SQL crash recovery.
  • Explicit collection moves still need permissions, collision checks and recoverable directory relocation.


New obligations: explicit namespace create/read/delete operations, persistent empty namespace rows, namespace-versus-collection name collision policy, and a clear navigation context. Namespaces need parent/child integrity rather than inferred existence. Do not remove catalog configs needed for other policy (for example snapshot class) or their version/ETag concurrency control merely because identity no longer needs a config pin.


Candidate policies used in this demo
  • Collections must live inside an explicit namespace, not directly at the catalog root. Namespace parents are created explicitly by --parents; empty namespaces persist. Namespaces and collections cannot share a path. Namespace rename/move is out of scope to avoid implicit subtree relocation.
  • Drafts hold a requested name and namespace; activation settles their path. Metadata edits never move a collection. Draft validation may be incomplete; activation needs valid metadata. Only draft, active and incomplete are modeled.
  • Publishing immutable schema v2 does not adopt it. Applying exact v2 to the catalog revalidates every settled collection; failures become incomplete, and a valid metadata correction restores active. File pushes still work for incomplete collections, consistent with the current design.
  • This candidate uses one staging context and refuses checkout while changes are pending. The existing DT-20 plan instead keeps per-collection staging and permits checkout while preserving it; that remains a valid alternative. Discard only clears staging. Metadata saves in this demo are direct server operations, not a simulation of the entire offline metadata/rebase workflow.
  • Delete refuses recorded files, staged changes and unrecorded mount bytes. Removing rows does not prove a directory is physically safe to delete. Empty namespaces survive collection deletion.
  • Role gates are intentionally not simulated. Namespace admin roles, draft-name reservation and catalog-root policy require decisions; this is no proof of production security.
