Bronze Layer

Source-faithful Zarr on object storage: the same scientific values as Raw, reopenable as arrays, with nothing renamed, rescaled, or reinterpreted.

1. Purpose and non-goals

Bronze answers one question: "give me the numbers that are in those files, as arrays, without making me parse the format." It preserves source-specific meaning — tally_4, mesh_104, relative_error, MCNP unit notation, original energy bins — and records exactly which raw bytes each array came from. It does not standardize names, units, or coordinates (that is Silver), and it does not merge datasets: there is one Bronze snapshot per build from a set of pins — or, for a direct-entry dataset, one per intake batch, with lineage rooting at Bronze (invariant N).

Raw pins. A Bronze build from Raw records each input as a pin (collection id, rel_path, sha256), copied from the collection's file listing when the build is planned. The build reads the bytes through the mount and refuses any whose hash differs from its pin. A pin names bytes, not a collection version. If a file has since been overwritten or removed, the collection's audit log gives the replaced hash and its time, and the bytes come back from an ONTAP snapshot taken before then. A pin keeps nothing alive: recovery lasts only as long as snapshot retention.

2. Storage model

{prefix}/
  organization/{org_slug}--{org_id}/
    project/{project_slug}--{project_id}/
      dataset/{dataset_slug}--{dataset_id}/
        bronze/
          repo/                   ← ONE Icechunk repository per dataset
  • One Icechunk repo per dataset. Snapshots within it are one per build from a set of pins. This keeps grant scoping (one prefix = one dataset's bronze), keeps repo count proportional to datasets, and lets Icechunk's history hold the full audit trail of rebuilds.
  • Branch/tag model. Writers commit on a working branch — build/{run_id} for Raw-derived snapshots, intake/{ingest_id} for manual intake — and after validation the publisher fast-forwards main. Every manual-intake snapshot, whichever provenance assertion it carries, is tagged intake/{nnnnnn} (monotonic per dataset); a Raw-derived build snapshot carries no tag and is resolved through its catalog row. Consumers resolve tags through the catalog, never by guessing.
  • Group layout inside a snapshot is defined by the science profile. For mcnp-run@1.0:
/
├── tallies/tally_4/{value, relative_error, energy_bounds}
├── tallies/tally_14/{…}
├── mesh_tallies/mesh_104/{value, relative_error, x_bounds, y_bounds, z_bounds}
└── run/{histories_completed, keff, completion_state}

Every array carries source references as attributes, and the snapshot metadata carries the full provenance record:

{
  "raw_inputs": [
    {"collection_id": "coll-0042-uuid", "rel_path": "meshtal", "sha256": "5e1f…"},
    {"collection_id": "coll-0042-uuid", "rel_path": "outp", "sha256": "b47a…"}
  ],
  "profile": "mcnp-run@1.0.0",
  "extractor_digest": "sha256:9a1c…",
  "built_at": "2026-08-23T17:40:12Z"
}

3. Science profiles and extractors

A science profile is the versioned, installable definition of a data kind. It is the single artifact that teaches Huron a format:

profile: mcnp-run
version: 1.0.0
required_files: [input_deck, primary_output]
optional_files: [meshtal, runtpe, mctal, ptrac, logs]
file_categories:                      # feeds Raw retention
  input_deck: essential_input
  primary_output: primary_output
  runtpe: bulk_intermediate
extract:                              # metadata extraction at ingest time
  [mcnp_version, nps, kcode, materials, tallies, source_definition,
   completion_status, warnings, scheduler_provenance]
bronze:
  extractor_image: registry/huron/mcnp-extractor@sha256:9a1c…
  layout: mcnp-source-faithful/1
validations: [bronze-mcnp-v1]         # see §4
silver:
  canonicalizer_image: registry/huron/mcnp-canonicalizer@sha256:44d0…
  contract: mcnp-transport/1          # see Silver §3
  • Profiles are published by organization admins through the admin API; a published (name, version) is immutable — fixes are new versions. Rows are mirrored to object storage (_platform/profiles/…) so recovery does not depend on PostgreSQL.
  • Extractor and canonicalizer images are referenced by digest. The digest is recorded in every snapshot's provenance; "which parser produced these numbers" is always answerable.
  • The same extractor serves double duty: at ingest it populates the metadata envelope's extensions block (so the scientist confirms rather than types); at Bronze build it produces the arrays.
  • The bronze.extractor_image field is optional. A profile without one supports manual intake only — which is the v1 posture for every profile. Writing an extractor is the opt-in cost a project pays later for automation, never a prerequisite for having Bronze data.

4. Ingestion paths

Bronze comes into existence one of two ways. Manual intake is the v1 path: it requires no per-project code — only the profile's declared layout and validations. The automatic raw→bronze builder is deferred: a per-profile extractor container is exactly the custom-code-per-project investment Huron does not ask of a project at this stage, and nothing else in the design depends on it. Raw is never a prerequisite for Bronze — a dataset whose entry layer is bronze has no raw at all, and a dataset that does hold raw may still receive its Bronze by manual intake.

4a. Manual intake v1 · primary

A scientist or engineer who already holds arrays — converted locally from instrument or code output, produced by an external pipeline, exported from another system — ingests them directly as a Bronze snapshot through the web UI or the Python client. The uploader supplies exactly one of two provenance assertions, and intake refuses an upload that supplies neither or both:

  • Linked to Raw: the upload names the Raw files it was converted from as pins (§1), copied from a settled collection's file listing. The snapshot's provenance is a promotion block with method: "upload" — same kind as a pipeline build, different builder.
  • No raw exists: the snapshot carries an external-provenance block naming the true source, and becomes a lineage root (invariant N).
scientist / engineer uploads NetCDF · HDF5 · zipped-Zarr files
  (web UI or `huron bronze upload`; same transfer surface as raw ingest)
  + metadata envelope, validated against the effective schema
    (org base + project enrichment — schema registry)
  + provenance assertion: Raw pins  -or-  external source
   │
   ▼
bronze intake service (service account — humans never hold storage
  credentials, invariant J) opens the payload with xarray;
  no extractor image, no custom code
   │  candidate snapshot on branch intake/{ingest_id}
   ▼
Validator runs the profile's bronze validations:
   ✓ structure matches the declared profile layout   ✓ file checksums verified
   ✓ dims/shapes/dtypes self-consistent              ✓ coordinate bounds monotonic
   ✓ NaN/missing-value behavior known                ✓ provenance assertion complete
   ✓ each Raw pin resolves (§1): its collection's current file row, or an
     overwrite/rm audit entry for that rel_path, carries its sha256 (when asserted)
   ✓ snapshot reopens through the client read path
   │
   ├─ pass → publish: fast-forward main, tag, catalog row (state PUBLISHED),
   │         outbox → LanceDB index
   └─ fail → catalog row state FAILED with structured findings; nothing published

Accepted forms, converted automatically: NetCDF, HDF5, and zipped Zarr stores — self-describing array containers xarray opens without format-specific code. Whatever arrives, the intake service converts it to Zarr automatically: an HDF5 or NetCDF upload is opened with xarray and written into the dataset's Icechunk repo as Zarr — the scientist never converts and never learns the storage format; a Zarr upload skips the decode and is written through the same path. Bronze storage is therefore Zarr + Icechunk without exception. Formats xarray cannot open self-describingly (CSV, proprietary binaries) are the scientist's to convert first (xr.open_dataset(...).to_zarr(...) is one line) — the intake service stays generic precisely so it never grows per-project parsers. The uploaded container is a transport form, discarded after the snapshot is published and verified; what Huron keeps is the Icechunk snapshot plus the uploaded files' digests in provenance.

Provenance, both shapes:

{                                          {
  "kind": "promotion",                       "kind": "external",
  "method": "upload",                        "source_system": "legacy-fluent-cluster",
  "raw_inputs": [                            "source_uri": "file://…/campaign-7/",
    {"collection_id": "coll-0042-uuid",      "source_digest": "sha256:0b71…",
     "rel_path": "meshtal",
     "sha256": "5e1f…"}],
  "uploaded_files":                          "uploaded_files":
    {"run42.nc": "sha256:aa10…"},              {"campaign7.h5": "sha256:cc32…"},
  "profile": "mcnp-run@1.0.0",               "profile": "cfd-run@0.3.0",
  "ingested_by": "user:kschmidt",            "ingested_by": "user:kschmidt",

Entry is orthogonal to the write rule, restated. ingested_by may name a human because a human initiated the intake and owns its assertions; the storage writer is still the intake service account, and the DB trigger that refuses human writers on derived layers is untouched. One field says where the bytes came from and who vouches for them; the other says who held the credentials.

4b. Automatic raw→bronze builder deferred

Deferred, not designed away. Automation requires a per-profile extractor_image — custom code written and maintained per data kind, which Huron does not ask of projects at this stage. The seams stay in place — the explicit build request, the jobs table, the working-branch/validate/publish flow above — so a project that later wants push-button raw→bronze adds an extractor to its profile and turns this on without touching the model. Until then, "bronze from raw" means a scientist converts locally and uses manual intake with Raw pins.

When enabled, the flow is:

explicit build request naming a set of Raw pins
   │
   ▼
Bronze builder claims job (PG jobs table, SKIP LOCKED)
   │  reads the pinned bytes through the mount read-only; extractor container, no network
   ▼
candidate snapshot on branch build/{run_id}
   │
   ▼
Validator runs profile's bronze validations:
   ✓ required outputs found            ✓ run completed successfully
   ✓ all expected tallies extracted    ✓ energy-bin bounds valid & monotonic
   ✓ mesh dims match array shapes      ✓ relative-error arrays match tally arrays
   ✓ NaN/missing-value behavior known  ✓ sampled values agree with source text
   ✓ snapshot reopens through the client read path
   │
   ├─ pass → publish: fast-forward main, catalog row (state PUBLISHED),
   │         outbox → LanceDB index + Silver canonicalization queued
   └─ fail → catalog row state FAILED with structured findings;
             dataset page shows "Bronze: failed"; retry after profile fix
  • Idempotent builds: a rebuild for the same set of pins replaces the working branch and produces a new snapshot; the catalog records the latest published snapshot per set of pins and keeps prior ones addressable (they are Icechunk history, not deleted state).
  • Corrections: an overwrite changes the hash, so a pin taken earlier no longer matches and a new build is requested; the earlier snapshot remains readable. Downstream impact is handled in Silver (region replacement) and Gold (staleness), not by mutating Bronze. With the builder deferred, the same holds manually: the correcting scientist re-uploads against the new pins, and the dataset page shows the gap until they do.
  • Failure is not publication: Huron never publishes a broken Bronze snapshot — on either path. Validation evidence (pass or fail) is stored as structured JSON on the catalog row and shown in the UI.

5. Access

Bronze is readable by the project's reader role and above (see RBAC layer matrices) through the standard grant flow: huron.open_dataset(..., layer="bronze") or huron.open_snapshot("B182"). Most scientists skip Bronze and read Silver; Bronze exists for extractor debugging, for auditing canonicalization, and as the earliest retained representation once raw bulk files expire.

Sizing note. Bronze roughly doubles stored bytes for array-heavy sources (raw + bronze) until raw TTL expiration, which is the economic argument for per-category raw TTL: after 90 days a typical MCNP run costs raw-inputs + bronze + silver, not two full copies of bulk outputs. The unchanged-byte and layer-size metrics from the instrumentation list make this visible per project.
