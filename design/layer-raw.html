Raw hierarchy and access target

Accepted target; implementation pending. Organization → Catalog → Namespace → nested Namespace(s) → Collection. Initially one Organization; namespace nesting has no fixed business-depth cap, subject to strict names and path safety. Empty namespaces persist; every collection belongs to a namespace, and directories within collections are not namespaces.

Administrator (administrator) administers the Organization and all its catalogs. Catalog Owner (catalog_owner), Catalog Contributor (catalog_contributor) and Catalog Reader (catalog_reader) apply only to their assigned catalog and all its descendants. Group grants are additive. Administrators appoint owners; owners manage only Reader/Contributor membership on their own catalog. There are no namespace/collection grants or creator privileges.

The server re-maps token groups on every request; the roles claim and CLI categories confer no authority. See N14 contracts and the migration sequence. Older five-role descriptions below apply to the legacy hierarchy or superseded Raw design, not this target. No new Raw history or versioning is introduced.

Explicit namespaces and collection lifecycle

Target contract approved 2026-10-25: a collection has an explicit namespace and name; metadata does not determine its path. Names use lowercase letters, digits, underscores and hyphens, start with a letter or digit, and contain at most 64 characters. Namespaces nest recursively without a fixed business-depth cap, subject to path safety, persist when empty, and are created and deleted explicitly by a Catalog Owner or Administrator.

A Draft reserves its name but has no directory or files. Activation validates metadata and provisions its directory. Active and Incomplete are settled states: explicit catalog schema adoption can change completeness, and a valid metadata repair restores Active. The catalog selects one exact immutable schema version for every collection; publishing a schema alone does not adopt it. Metadata edits never relocate a collection; an authorized move changes its explicit namespace/name.

Deletion refuses registered files, pending commits and unsafe mount content. There are no archive, closed or stored resolved states. See owner decision 13 and the binding replacement contracts. These capabilities remain planned.
