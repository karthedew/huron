Roadmap

The greenfield build: phases with mechanical gates, sequenced so every phase ships something a scientist or operator can use. Nothing here amends or extends any earlier plan — this is the plan. Two threads: the backend build phases (P0–P10, §2) and the frontend-integration tiers (T0–T6, §3), each row carrying its build status.

1. Greenfield stance

Huron starts clean. No API compatibility with any earlier prototype, no data migration, no inherited schema, no deference to prior decisions. Existing code and documents are reference material at most; any idea reused from them must re-justify itself against this design record. Practically:

  • A fresh domain model, fresh migrations from revision zero, and a fresh OpenAPI contract — nothing is shaped to accommodate what already exists.
  • Prototype endpoints, schemas, and plans are retired outright. No dual-running, no compatibility shims, no migration tooling.
  • Repository hygiene from day one: the three-surface layout below, with import-linter enforcing every boundary in it — no package imports a sibling package, no service imports a sibling service, and catalog/ and rbac/ know nothing of FastAPI, SQLAlchemy, storage SDKs, or LanceDB; a task is done when its gate passes in CI, not when the code is written; any change to a decision or invariant updates this design directory in the same PR.

The dependency rule is one-way and mechanical: service → pkg → schema. Never the reverse and never sideways. A package that needs another package's capability does not import it — it declares a typing.Protocol describing what it needs, and a service passes in a conforming object. Because Protocol conformance is structural, the implementing package does not import the declaring one either, which is what lets pkg/* be genuinely independent rather than merely tidy. mypy checks conformance at the wiring site, where the concrete object meets the Protocol.

Five import-linter contracts hold this in place, and all five are checked in CI: a layers contract for service → pkg → schema; an independence contract across the eleven packages; an independence contract across the twelve services; a forbidden contract keeping web frameworks, database drivers and storage SDKs out of catalog/ and rbac/; and a narrower forbidden contract keeping web frameworks and database drivers out of auth/ — an IO package that legitimately uses HTTP, JWT and password-hashing libraries. Data-modeling and validation libraries are deliberately not on that forbidden list: schema/ is built on them, and catalog/ validates against schema/ rather than restating formats.

Two consequences worth stating, because they are the ones that bite in review. Cross-cutting concerns do not get a shared import: a package that wants to log uses the standard library, and the service configures telemetry/ to capture it. And behavior two services both want becomes a package — never an import of the sibling that happens to have it already.

3. Integration tiers

The frontend thread: connecting the frontend to real backend functionality, planned as 25 gated milestones in seven priority tiers T0–T6 (distilled from the curated frontend feature inventory, 2026-08-31). The tiers carry their own prefix deliberately, so they can never be confused with the backend phases in §2; where a milestone rides on a backend phase, its row says so. Each milestone names what already exists in this checkout, what it adds, and a mechanical gate. Every listing rides milestone 3's visibility layer; every mutation writes an audit row and honors If-Match; frontend data access stays behind web/src/lib/api/ — a milestone that forces data-shape edits outside that seam has leaked and gets fixed at the seam.

T0 — Required integration foundation

Strictly ordered: the contract, then the session, then visibility — so every later listing endpoint is born authorization-filtered rather than retrofitted.

4. Sequencing rationale

  • P2 before everything derived: the evidence tier must be trustworthy (crash matrix, rebuild) before any pipeline consumes it. P3 follows immediately because the reconciler is what makes P2's crash-consistency gate fully checkable.
  • P4 early: search makes the lake usable to humans before derived layers exist, and the outbox/projection machinery it builds is the same event backbone P6–P9 consume.
  • P8 immediately after P7: the first Silver snapshot with no ergonomic way to open it would stall adoption; the grant flow is the product moment.
  • P10 last: Polaris mirrors published tabular Gold — there is nothing to mirror before P9, and nothing blocks on it (its failure posture is "degrade external engines only").
  • Cross-cutting, never a phase: FIPS smoke and the OpenAPI-contract check run from P0 onward; instrumentation (unchanged-byte ratio, layer sizes per project, ingest durations, projection lag, grant issuance rates) ships with the code that emits it, because the full-copy-vs-delta and TTL-length decisions get revisited with data, not opinion.
  • T0 in strict order (contract → session → visibility): the generated client first, then the browser session, then the visibility layer, so every later listing endpoint is born authorization-filtered rather than retrofitted.
  • Integration long poles start early: the search projection (milestone 6), the job runner (11), and the outbound-email path (12) each unlock several later milestones. The explicit cross-tier dependencies: 9→11; 18→8, 11, 12, 16; 19→20, 21; 22→11, 19, 20, 21, 24; 23→9; 24→11, 20, 23.
