READING CONTRACT

00 · How to use this guide

A reference for tracing causes and defending architectural decisions, not memorizing component names.

The working question is not “What is a control plane?” It is “Which component must decide this, which component must execute it, and what evidence would make that division safe under load?” Read the mental map first, then use a component chapter to examine a concrete failure or design choice.

This guide uses the revised Bloom taxonomy: level 4 is Analyze, and level 5 is Evaluate. Analysis separates elements and examines their relationships; evaluation judges alternatives against explicit criteria. The original taxonomy’s fifth category was Synthesis, so the revision matters here. [S01]

Reading modeWhat you should produceWhere to start
Mental mapAn account of intent, authority, discovery and bytes without treating them as one serial pipeline.The four paths and ownership matrix.
Level 4 · AnalyzeA causal chain explaining a bottleneck, race, stale result or authorization failure.Each component’s Analyze panel and the end-to-end traces.
Level 5 · EvaluateA decision with criteria, supporting evidence, a rejected alternative and a condition for revisiting it.Each component’s evaluation experiment and the review scenarios.
Evidence convention

Baseline means the supplied Huron architecture. Evidence means a documented external capability. Proposal means a Huron design recommendation, not an upstream guarantee. Analyze/Evaluate panels are original reasoning or proposed tests. Numeric workload targets are illustrative unless explicitly stated otherwise.

Scope: API and Python Client Package → Control Plane and Catalog/LanceDB → Data Plane. Raw and Zarr ponds remain in scope because they determine I/O and publication semantics. User interface design, a CLI implementation, Polaris, scheduler selection and scientific algorithm implementation are outside this guide. “Service” means a responsibility boundary; it does not require a separate network deployment.

Research date: 13 September 2026. This is documentation, not an audit of the current repository, installed versions, NFS export or benchmark results. Rolling documentation is linked directly. Record the actual dependency lock, server versions and mount configuration before applying a documented behavior to a release.

MENTAL MAP

01 · The mental map: four paths, not one pipe

Applications express intent. The control plane governs. The catalog describes. The data plane executes.

Baseline Your architecture separates application interfaces, a PostgreSQL-backed control plane, a Lance-backed scientific catalog and Raw/Zarr ponds. It explicitly assigns storage facts to the data plane and authoritative registration to the control plane. [H1]

PathQuestion being answeredTypical messagesNot its job
Intent / commandWhat operation does the caller request?Create dataset; begin ingest; complete; derive; expire.Transport handlers do not become storage or governance policy.
Authority / publicationMay it run, and which result is official?Authorize; allocate; validate policy; publish expected-parent update.A publication transaction does not transfer gigabytes.
Discovery / descriptionWhich products match, and how are they related?Search; metadata; lineage; snapshot descriptor.A search hit is not a new authorization grant.
Execution / bytesWhich bytes were stored or read?Stream file; verify manifest; finalize revision; read array slice.Writing bytes does not independently publish a product.

Keep these concepts orthogonal

Pond describes a storage and behavior domain. Layer describes scientific processing or governance state. The proposed Raw Pond supports Raw; the proposed Zarr Pond supports Bronze, Silver and Gold. Bronze means canonical machine-readable representation derived from raw; Silver adds scientific validation, standardization and quality control; Gold is a scientific derivation with provenance. Those are Huron’s meanings, not universal meanings imposed by Zarr or LanceDB. [H1]

Proposal Treat the API as the server-side application boundary and the Python Client Package as a remote application adapter. Both expose the same domain operations. The client calls server APIs; it does not carry a PostgreSQL password, open the internal LanceDB catalog directory or publish a revision by changing a file.

L4 Analyze the relationship

For client.open(dataset, layer="silver"), identify four separate decisions: authenticate the caller; resolve a specific published product version; choose an engine; fetch its bytes. A single SDK function may hide these steps, but removing their boundaries changes correctness.

L5 Evaluate the decision

Judge a proposed shortcut against three criteria: does it preserve current authorization, pin a reproducible version and stay inside the storage admission budget? Direct reads can be acceptable in a trusted compute environment only when storage permissions and workload controls enforce those criteria. Otherwise retain a gateway.

Review exercise · Is “API → PostgreSQL → LanceDB → NFS” an accurate execution pipeline?

No. It confuses stores with owners and suggests every request traverses all stores. A command can publish via PostgreSQL while catalog indexing is delayed. Search can operate on LanceDB without reading payloads. An authorized pinned reader can transfer data without sending its bytes through either database.

Three version numbers that must not be confused

Proposal A dataset ID names the logical dataset. A product version is a governed result in a particular pond and layer, backed by a raw revision or an Icechunk snapshot. A catalog table version is a version of the index that may contain descriptions of thousands of product versions. Updating an embedding can change a catalog table version without changing any scientific payload. LanceDB exposes table versioning; Huron must supply the product identities. [S29]

“current” is a mutable lookup.
A version_id or snapshot_id is the pinned reference used for one read/job.
Minimal registry is not an empty registry

Shrinking PostgreSQL’s role does not remove the product registration, publication status, current pointers or accepted lineage references needed for safe operation. The distinction is transactional authority versus rich scientific discovery, not “PostgreSQL knows nothing about products.”

L4 Analyze the relationship

A metadata-only amendment changes a description but not the stored data. Trace which identifier must change and which must remain stable. Then distinguish an amendment from re-running scientific validation under a newer policy.

L5 Evaluate the decision

Keep historical evidence tied to the policy that evaluated it. Revalidation should record a new assessment with its own time and rule version. Do not rewrite a past “passed” result to imply it satisfied a policy that did not exist then.

03 · Trace a write, a read and a failure

There is no atomic transaction spanning an NFS rename, PostgreSQL publication and a LanceDB update.

Write: an uploaded candidate becomes a governed product

Proposal The following expands the supplied plan → storage result → authoritative registration → catalog event flow. It is a contract sketch, not a claim that these endpoints exist. [H1]

Client → data-plane endpoint: transfer bounded, resumable file data
API → Control Plane: request completion(operation_id)
Control Plane → Raw Pond: seal + validate + finalize
Raw Pond → Control Plane: verified StorageResult

    recheck authorization/policy as required

    mark operation published; append outbox event
Outbox consumer → Catalog/LanceDB: idempotent projection update
Client ← operation status: published, with indexing status reported separately

Read: discovery is optional; authorization is not

Python Reader → data-plane gateway: read the pinned revision/snapshot

A client that already knows a product version can skip search.
The reader never re-resolves “current” for every file or array chunk.

Icechunk provides read-only sessions selected by a snapshot ID. A Huron reader can use that mechanism to preserve one array view while another product version is published. An Icechunk-backed store should be opened through the session-store integration, not by assuming its directory is an ordinary Zarr layout. [S42] [S45]

The NFS-specific rename ambiguity is documented: an error can follow a rename that succeeded on the server. This is why recovery reconciles operation identity and content instead of interpreting every error as “nothing happened.” [S36]

L4 Analyze the relationship

Draw the crash boundary between each durable transition. For each boundary ask whether a retry repeats bytes, repeats a decision, or only repeats a projection. These are different idempotency problems.

L5 Evaluate the decision

Accept the design only when every retry can identify the original operation and every unpublished candidate is distinguishable from a published revision. A catalog outage must not force re-uploading a successfully stored 9 GB payload.

APPLICATIONS · API

04 · API application: translate requests without owning the domain

Control the transport boundary and protect small requests from bulk-transfer work.

Proposal Boundary: accept authenticated HTTP requests, validate transport contracts, call control/catalog services and map results to stable responses. A router owns HTTP concerns; it does not decide whether scientific metadata is sufficient or whether a revision becomes current. Metadata and catalog endpoints can share an API deployment while bulk transfers use separate gateway processes.

Primary-source findings

Evidence Starlette exposes incremental request-body consumption through request.stream(). Its multipart upload abstraction uses a spooled temporary file. Reading an UploadFile in chunks therefore does not establish that the entire ingress path streams directly to NFS. [S02]

Uvicorn supports flow control and rejects requests beyond its configured concurrency limit. NGINX enables request buffering by default, so a proxy can spool data before the application sees it. Request-body buffering, response buffering and inactivity timeouts must be considered separately. [S04] [S05]

Synchronous Starlette work uses AnyIO thread capacity; its documented default limiter has 40 tokens shared with other users of that limiter. This is a framework resource, not a recommended NFS transfer limit. [S03]

L4 Analyze the relationship

Suppose API memory is bounded but the proxy’s temporary disk fills. The streaming loop is not necessarily defective: the proxy has accepted more body data than the backend can consume. Follow the byte path through every buffer. Separately, a responsive event loop can coexist with a saturated thread limiter, making file-related endpoints queue even while simple endpoints still answer.

L5 Evaluate the decision

Prefer raw-body resumable transfer endpoints for large scientific files, while retaining ordinary JSON contracts for metadata. Compare a combined API/gateway deployment against a separate gateway using metadata latency under sustained transfers, restart isolation and operational complexity. Split deployment when measurements show resource interference, not merely because the architecture has separate boxes.

Evaluation experiment

Hypothesis: a saturated transfer path must not exhaust metadata capacity. Run slow senders, fast senders and disconnected clients while issuing identity and operation-status requests. Measure proxy disk, resident memory, thread-limiter wait, event-loop delay, active requests and p95/p99 metadata latency. Hold total storage concurrency fixed when comparing worker counts. Reject a change that improves upload admission by allowing unbounded buffering or that hides overload in a proxy queue.

Review exercise · Does adding async to a function make NFS writes nonblocking?

No. The proposal requires filesystem calls to run through a bounded worker boundary. An async signature alone does not move synchronous file operations off the event loop. Inspect actual execution and limiter waits rather than judging by the function declaration. [S03] [S34]

APPLICATIONS · PYTHON PACKAGE

05 · Python Client Package and Reader: convenient, bounded, version-pinned

The SDK simplifies the workflow without moving authority into an untrusted process.

Baseline The Huron catalog describes the product, storage representation, revision/snapshot and engine. The reader opens the corresponding representation. The catalog is not the payload-reading engine. [H1]

Proposal The package should expose sync and async clients, typed request/result models, streaming upload/download helpers and a reader adapter. Keep FastAPI, database drivers and server secrets out of its required client dependency set. Optional reader dependencies can be installed only when a workflow needs array access. A local method that resembles a service method must still invoke server authority for governed changes.

Primary-source findings

Evidence HTTPX clients reuse connections. Its async guide warns against constructing clients inside a hot loop and requires streamed responses to be closed. Connection limits bound local pool usage; separate connect, read, write and pool timeouts distinguish waiting for capacity from waiting on a peer. [S07] [S08] [S09] [S10]

HTTP defines which methods are idempotent, but that does not establish the idempotency of an arbitrary multipart ingestion workflow. The tus protocol provides a concrete offset-based resumable model, including offset checks and an optional checksum extension. [S11] [S39]

# Proposed user-facing API, not an implemented package signature.
with HuronClient(base_url=service_url, credentials=credentials) as client:
    operation = client.ingests.begin(
        dataset_id=dataset_id,
        files=expected_manifest,
        metadata=scientific_metadata,
        idempotency_key=stable_key,
    )
    client.ingests.upload(operation.id, local_files, resume=True)
    product = client.ingests.complete(operation.id).wait_for_publication()

    # Resolve one official version and retain it for this reader's lifetime.
    with client.open(product.version_ref) as reader:
        subset = reader.read(selection=selection)

L4 Analyze the relationship

A download times out after the server sent data. A blind retry of “open current” can fetch another version and silently combine content from two snapshots. In contrast, retrying a range of the same immutable version preserves identity. A lost completion response similarly calls for querying the original operation, not allocating a second ingest.

L5 Evaluate the decision

Require stable idempotency keys for creation/completion, bounded retries with jitter and operation-specific retry rules. Persist upload progress so restarting a process does not erase the resume plan. Distinguish transient availability from a publication conflict: a conflict needs explicit caller action, not endless network retry. The server must bind an idempotency key to a canonical request identity and reject reuse with different intent.

ReadHandle contract

Proposal Return a product/version ID, raw revision or repository/snapshot ID, selected engine, permitted endpoint or trusted location, scope, expiration and optional retention-pin ID. Do not expose storage paths in untrusted responses unless required. The ordinary client uses data-plane endpoints. A direct NFS reader is an explicit trusted-compute mode, not a general browser or remote-Python capability.

For long-running lazy array computations, a handle’s lifetime includes deferred reads. Define credential renewal and retention-pin renewal; creating an Xarray object is not evidence that all its data has been read. Icechunk’s Xarray integration supplies the session-backed read path. [S45]

Evaluation experiment

Interrupt a 9 GiB transfer at several offsets, restart the client, expire its credentials and drop the completion response after publication. Measure retransmitted bytes, client memory and time to resume. Pass only when the final file and revision identity match, completed parts are not unnecessarily resent, and explicit version reads never drift. Test the same scenarios through both sync and async interfaces. Use separate local pool budgets for metadata calls and long-lived transfer streams so progress polling is not starved by the client itself.

CONTROL PLANE · POLICY

06 · Authorization and GovernanceService: decide what is allowed and what is sufficient

Authorization asks “may this happen?” Governance asks “does this result meet the agreed scientific contract?”

Baseline Required metadata belongs to governance, not to LanceDB itself. Your document makes requirements specific to pond/layer and distinguishes control metadata from scientific metadata. Raw, Bronze, Silver and Gold have different evidence requirements. [H1]

Proposal Separate AuthorizationService (principal, action, resource, scope) from GovernanceService (schema, scientific policy, required provenance, acceptable transition). Both return versioned decisions. The data plane still verifies operation ownership and target constraints; authorization is not permission to trust arbitrary paths or unchecked client fields.

Primary-source findings

Evidence JSON Schema defines schema identity, dialects, references and validation output. Pydantic strict mode changes coercion behavior; some JSON-type conversions have specific allowances even in strict mode. These mechanisms help validate structure but do not establish physical units, calibration correctness or the scientific validity of a method unless Huron implements those rules. [S12] [S13]

W3C PROV distinguishes entities, activities and agents, including derivation relationships. Those concepts fit product versions, processing runs and scientist/service identities without forcing a specific database layout. PostgreSQL row-security policies can restrict rows, but owners and privileged roles have documented bypass behavior. [S14] [S17]

L4 Analyze the relationship

A user had permission when an upload began but loses it before publication. Separate permission to complete transport from permission to make a new official product. Then separate a structurally valid metadata object from a valid scientific transformation. Neither a nonempty “algorithm” field nor a catalog embedding proves reproducibility.

L5 Evaluate the decision

Recheck publication authority and define the treatment of already-running operations. Pin the validation contract used for the operation and specify whether a newer policy blocks publication or requires revalidation. For high-assurance scopes, fail closed when fresh authority cannot be established. For caching, state an explicit revocation-delay budget; do not promise immediate revocation while serving stale positive decisions.

Performance and evaluation experiment

Proposal Cache parsed, immutable schema versions by digest; bound metadata size and validator execution cost. Push expensive file-based checks into governed jobs rather than holding an HTTP worker or database transaction. Batch authority lookups for a result page instead of performing one database round trip per hit. Test warmed and cold policy caches, high-cardinality memberships and a policy change during upload.

Pass criteria: schema coercion does not change scientific meaning unnoticed; every accepted result names the rule version; removed access cannot leak through search snippets, counts or open handles beyond the declared revocation semantics. A long-lived capability is an explicit security tradeoff, not equivalent to checking authority for every read.

Review exercise · Can a valid Gold schema prove the derivation is scientifically correct?

No. Structural validity checks the representation. Scientific validity depends on the specific method and evidence. Record machine checks, expert approval where required and the provenance that supports reproducibility as separate assessments.

CONTROL PLANE · OPERATIONS & REGISTRY

07 · IngestService and ControlRepository: short transactions around shared decisions

Parallelize preparation. Coordinate the transition that makes a candidate official.

Proposal IngestService coordinates identity, policy, operation ownership, storage plans and publication. ControlRepository stores those transitions in PostgreSQL. This moves logical check(), dataset creation and publication out of RawstoreService while keeping initialization, transfer and storage checks in the pond. It follows the supplied distinction between storage facts and lifecycle decisions. [H1]

Primary-source findings

Evidence At Read Committed, PostgreSQL re-evaluates an UPDATE predicate after a conflicting update has completed. That supports an expected-parent conditional update for a revision stream. Row-level locks and advisory locks have distinct behavior; advisory coordination only protects operations that participate in it. [S15] [S16]

asyncpg exposes explicit transactions and connection pools. SQLAlchemy Core represents tables and metadata independently of ORM mappings. Using Core to describe schema and asyncpg for chosen query paths is a design option, not evidence that one stack is universally faster. [S18] [S19]

Publication contract

# Proposed transaction boundary; long-running I/O has already finished.
BEGIN
    verify operation ownership, status and request/result identities
    verify publication authority using the chosen consistency rule
    lock or compare-and-swap the dataset/release/layer revision stream
    reject a changed expected parent (including first-revision races)
    register the verified product-version and metadata/lineage references
    update the authoritative current pointer
    mark the operation PUBLISHED
    insert its publication event into the outbox
COMMIT

No upload, checksum scan, embedding computation or remote catalog call
runs inside this transaction.

L4 Analyze the relationship

Two users start from the same parent. Their private uploads can proceed together because they modify different workspaces. Publication touches the same revision-stream state, so at most one succeeds under a reject-stale-parent policy. The second complete candidate is not corrupted; its intended parent is stale. Treating this as an I/O error obscures the actual conflict.

L5 Evaluate the decision

Use targeted conditional updates or short row locks for the initial linear Raw history. Reserve serializable transactions for wider invariants that require them, and retry whole transactions when the chosen isolation requires it. Do not promise conflict-free concurrent authorship: reject, queue or explicitly merge according to product semantics. For Raw full snapshots, silent last-writer-wins is not the proposed policy.

Model the constraint, not a preliminary check

Proposal Enforce unique dataset naming within its agreed scope, stable operation IDs, unique idempotency bindings and unique published version identities with database constraints. A “does it exist?” query followed by insertion is not the publication mechanism. Reserve revision IDs independently of successful publication; gaps in an allocated display sequence are preferable to reusing identities after a failure.

Treat each active upload/finalization as an owned operation, with a durable state transition preventing new writes after sealing. A lease record alone is insufficient when the old gateway can still access NFS. Before takeover, either exclude the old writer at an enforceable gateway/backend boundary or retain single ownership until its termination is established. PostgreSQL locking does not itself revoke an operating-system file descriptor. [S16]

Performance and evaluation experiment

Proposal Budget database connections across API workers, gateway control calls, indexers and background workers. Record pool-acquire wait separately from SQL time. Run a hot-dataset race and a many-dataset workload at the same request rate. The first exercises publication contention; the second exercises general capacity. Increasing pool size is not a solution when a single row is the bottleneck.

Pass criteria: exactly one winner per expected-parent race; retrying completion returns the same result; no transaction lives for the duration of a large file transfer; operation status survives process restarts. Examine database waiting and query statistics rather than attributing all latency to Python. [S47] [S48]

CONTROL ↔ CATALOG

08 · Publisher and CatalogIndexer: cross the database boundary deliberately

At-least-once delivery plus idempotent projection is the target; no cross-store “exactly once” claim is assumed.

Baseline The control plane commits operation/revision state and emits DataProductCommitted for the scientific catalog. The pond produces the manifest rather than inserting catalog rows directly. [H1]

Primary-source findings

Evidence AWS’s first-party outbox guidance explains the database/message dual-write gap and the need to handle repeated delivery. PostgreSQL documents SKIP LOCKED as useful for queue-like consumers, while warning that it gives an inconsistent view for general-purpose reads. [S21] [S20]

LanceDB provides merge-insert primitives for updating matched rows or inserting unmatched rows. Those are building blocks; they do not supply Huron event identity, cross-store atomicity or an ordering policy. [S28]

A recoverable indexing protocol

Publication transaction:
    product-version registration + current pointer + outbox row

Indexer:
    claim a bounded batch in a short PostgreSQL transaction
    release that transaction; load immutable publication descriptors
    apply idempotent version rows / ordered projection updates in LanceDB
    durably acknowledge only after the projection succeeds

Crash after apply but before acknowledge → replay the same event.
Do not mark delivery complete before the LanceDB commit succeeds.

Proposal Give events an event_id, operation_id, product_version_id, descriptor URI/digest, event-schema version and a revision-stream ordering key. Store metadata/lineage source documents durably so events are not the only copy of scientific meaning. A monotonic database ID alone is not proof of global commit order; allocate a stream version under that stream’s publication coordination or explicitly resolve ordering from authoritative state.

L4 Analyze the relationship

An indexer dies after LanceDB accepts version 44, then replays version 43. Appending an immutable version row is harmless only when duplicates are controlled. Updating a “current product” projection is dangerous unless stale updates are rejected. Distinguish a delivery ID, a product version and an ordered current-pointer projection.

L5 Evaluate the decision

Start with one coordinated writer per catalog table or partition as an operational simplification, not because LanceDB categorically lacks concurrent writes. Batch immutable version records; isolate ordered current/metadata projections. Increase parallelism only after tests prove duplicate handling, event order and lease takeover. Do not implement “check whether event exists, then add” as an unprotected two-writer sequence.

Batching and lag

Proposal Flush on either a row-count threshold or an elapsed-time threshold. Larger batches amortize write work, while long waits harm discovery freshness. Measure publish-to-index lag, oldest unapplied event, batch bytes, commit conflicts, retries and poison events. A permanently failing descriptor must be visible to operators and must not disappear behind a misleading “all indexed” status.

LanceDB’s performance guide explains that repeated tiny adds create versions/fragments and that compaction and index maintenance matter for long-lived tables. This supports testing batched projections rather than assuming one event should imply one table commit. [S24]

Review exercise · Should LanceDB downtime roll back a publication already committed in PostgreSQL?

Not in this proposal. The official version is available through its authoritative ID and storage result. Report delayed discovery, retain the outbox event and retry. Reversing publication merely because a derived index is unavailable would couple the correctness path to discovery availability.

CATALOG · SCIENTIFIC DISCOVERY

09 · CatalogService and LanceDB: scientific discovery with explicit freshness

A searchable projection can be rich and useful without becoming the source of transactional authority.

Baseline The Huron catalog exposes product lookup, search, lineage, provenance, versions and schema/metadata descriptions. Lance is the backing scientific index, not the owner of identity, RBAC or publication. The public API should remain a Huron contract rather than mirror the storage engine’s API. [H1]

Distinguish the three names

Proposal Huron Catalog is the governed domain interface. LanceDB is the database/query implementation behind it. Lance is the underlying table representation. Keep raw scientific files and Zarr payloads in their ponds; this design uses LanceDB for their descriptions and discovery. Do not infer that an engine capability automatically becomes an authorized user-facing feature.

Primary-source findings

Evidence LanceDB supports metadata filtering and hybrid full-text/vector retrieval. Scalar indexes provide alternatives for different field shapes. Its OSS FAQ supports concurrent operations but notes that excessive concurrent writers can exhaust finite commit retries. Storage selection therefore still matters. [S25] [S26] [S32] [S23]

For embedded tables, the documented default read_consistency_interval is unset: existing readers do not automatically check for another process’s updates. Zero checks on each read; a nonzero interval trades freshness for fewer checks. RemoteTable consistency is deployment-configured. These are refresh semantics, not a multi-table transaction or a fresh authorization guarantee. [S22]

Embedded storage choices and Enterprise’s remote-serving architecture are different deployment models. Creating multiple Python API processes does not automatically create distributed catalog storage or replicated table data. [S30] [S31]

Two kinds of lag, plus index coverage

publication ── outbox / indexer delay ──► committed LanceDB table version
           ── reader refresh delay ─────► version seen by a catalog reader

Separately: indexed rows versus newly committed but unindexed rows.

Report publication_time, indexed_at and the projection/read version.

DATA PLANE · SHARED RESOURCES

10 · Data-plane gateway and I/O manager: bound work where it consumes resources

A semaphore is an admission mechanism, not a lock service, bandwidth multiplier or cancellation engine.

Proposal The gateway enforces scoped transfer access, operation ownership, byte/part limits and cancellation semantics. A shared I/O manager limits filesystem work. The Raw and Zarr ponds implement representation-specific operations over it or over equivalently controlled backends. Budget by the physical storage pool: two ponds, a catalog and a pipeline may all contend for the same NFS server.

Primary-source findings

Evidence An asyncio semaphore limits participating coroutine acquisitions; it is not a cross-process or thread-safe synchronization service. FastAPI worker processes have separate memory. AnyIO can offload blocking work with capacity limits, but cancellation cannot forcibly stop already-executing thread code. [S33] [S06] [S34]

Linux NFS documents cache-coherence behavior and different hard/soft retry semantics. A stalled NFS operation is therefore not necessarily a CPU problem, and changing mount behavior is not a harmless way to make application timeouts disappear. The NFS protocol also distinguishes accepted writes from stable-storage requirements. [S35] [S38]

L5 Evaluate the decision

Initially allocate fixed per-process budgets whose total is below a measured pool capacity. Keep a singleton service/limiter per application process and bound waiting work, not just running work. Add a shared scheduler when dynamic replication needs coordinated allocation. Include maintenance, validation scans and pipeline traffic. A direct NFS writer that bypasses admission invalidates the budget.

Bandwidth, memory and fairness

Proposal Separate small reads from long uploads, and reserve headroom for control/manifest work. Use bounded per-project queues and fair scheduling of resumable transfer units; do not let one multi-terabyte ingest monopolize every slot. A stream buffer is a memory unit, an upload part is a retry unit, and an NFS request size is a transport setting. They do not need to be identical.

With 8 active writers, a 4 MiB application buffer and one queued buffer each, the application payload-buffer allowance is approximately 8 × 4 MiB × 2 = 64 MiB. This calculated allowance excludes HTTP/proxy buffers, interpreter objects, kernel page cache, compression workspaces and other readers. “Only 64 MiB” would be an incorrect whole-system memory claim.

Evaluation experiment

Sweep concurrent transfers through 1, 2, 4, 8, 16 and 32 while holding file sizes, readers and durability checks fixed. Plot useful bytes/second against p95 service time and queue wait. Find the point where more concurrency stops improving throughput. Repeat under a delayed NFS server and a lost client connection; count outstanding worker operations after cancellation. Reject any implementation whose memory or active work grows without a configured bound.

Do not confuse finalization with publication

Review exercise · Alice and Bob both replace the same Raw dataset from revision 42.

Level 4 · Identify what is independent

Their private workspaces and transfer streams are independent. Their expected-parent publication is shared state. Existing readers of 42 remain independent of both candidates. The distinction is spatial isolation during preparation and coordinated authority at publication.

Level 5 · Evaluate the conflict policy

Under the proposed full-snapshot policy, publish one candidate and return a conflict for the other without deleting its verified files immediately. Silent replacement discards an author’s intended lineage; an automatic merge invents semantics absent from the Raw model. Queueing all authors is another defensible option only when sequential authorship is an explicit product requirement.

Review exercise · Doubling API replicas doubles active writers but does not improve goodput.

Level 4 · Explain the causal chain

Independent process semaphores increased total admitted work. The NFS/backend bottleneck remained, so requests accumulated in storage or worker queues. Memory, retries and tail latency can rise without more useful bytes. Check the actual pool allocation and include validation/pipeline traffic. [S06] [S33]

Level 5 · Select the next experiment

Hold the global transfer limit constant while increasing replicas. If control latency improves but payload goodput stays unchanged, retain replicas for isolation only when worthwhile. Increase backend capacity or reduce operation amplification to improve the true bottleneck. Do not raise semaphore counts based solely on idle gateway CPU.

Review exercise · Catalog filtering is fast, but a revoked user sees a restricted project title.

Level 4 · Locate the authority leak

The title itself is protected metadata. The failure may be a stale positive authorization cache, direct catalog access, a replaced scope predicate or an unfiltered facet/snippet path. Rechecking only at byte-open time is too late to prevent metadata disclosure.

Level 5 · Evaluate the repair

Apply server-owned scope restrictions consistently, verify supported SDK predicate behavior and check current authority before returning protected results. State cache/revocation semantics and test each output channel. A search-latency optimization that changes the security scope must be rejected. [S26]

Review exercise · A semaphore ensures one Huron publication at a time; is Icechunk now safe on NFS?

Level 4 · Distinguish the commits

The repository commit happens before Huron publication. If two sessions already committed concurrently through an unsafe filesystem path, serializing the later database update cannot recover a lost repository commit. A per-process semaphore also cannot exclude writers in other processes. [S40] [S33]

Level 5 · State an acceptable release condition

Require enforceable single-committer control covering the actual repository operation and stale-writer failover, or select a supported storage configuration for the required concurrency. A successful local test is useful evidence but not a universal production guarantee. Include independent/direct writers in the threat and failure model.

Review exercise · Should catalog indexing wait for every embedding and quality enrichment?

Level 4 · Separate mandatory evidence from optional discovery work

Governance-required quality evidence must precede publication. A search embedding is normally a derived ranking artifact and can be produced later. Conflating them turns an embedding service outage into a publication outage without improving scientific validity.

Level 5 · Defend an enrichment policy

Publish only after required governance checks. Index a complete baseline description and expose optional enrichment status, then update derived search fields idempotently with model/version identity. Reject an asynchronous “enrichment” shortcut when the omitted field is actually mandatory scientific evidence.

Import direction is not the same as request direction. Application composition creates implementations and injects them through domain protocols. The client imports transport contracts and optional reader adapters, not server database/session implementations. Ponds return results through contracts; they do not import the CatalogIndexer or decide control policy. Shared data-plane interfaces must preserve backend-specific capabilities rather than pretend every store supports rename or identical commit semantics.
