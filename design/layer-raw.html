Raw Layer — NFS Store

Immutable scientific evidence on a POSIX filesystem: envelopes, manifests, the atomic commit protocol, retention, and the machinery that keeps all of it honest.

1. Why NFS for raw

Raw's job is to be the evidence tier: byte-exact, immutable, navigable by a human with ls and jq even if every Huron service is gone. Two backends were considered:

NFS / POSIX (chosen)Object storage (rejected for raw)
Ingest cost HPC runs are born on NFS; commit is a same-filesystem move, and register-in-place (v2) makes multi-TB ingest O(metadata). Every run — up to 1 TiB — copied through the API into the store.
Publish atomicity rename(2) is atomic within a filesystem: the whole envelope appears at once, marker included. Objects appear one by one; a marker-written-last protocol and reader discipline are needed to fake atomicity.
Dedup Hardlinks: free, instant, same inode. Requires sealing discipline (§6). Server-side copy: no shared inodes, but a real copy per revision.
Direct access None — all raw byte access is API-mediated, which is the RBAC posture we want anyway (RBAC). Presigned URLs possible.
Consistency caveats Close-to-open cache consistency; contained by the single-writer service model and fsync discipline (§5). Strong read-after-write.
Capacity Filesystem quotas per project; site NFS scaling limits apply. Effectively unbounded.

The deciding facts: the data is already on NFS when it is born; raw access should be API-mediated regardless of backend; and rename gives a strictly simpler commit protocol. What is given up — presigned downloads and object-store capacity economics — is acceptable for the evidence tier, because Bronze onward lives on object storage and carries the read traffic.

One spine, four layers. The organization/…/project/…/dataset/… hierarchy is identical for every layer, and the layer is the leaf: a dataset's raw, Bronze, Silver and Gold all hang off the same dataset directory, so "everything about run-0042" is one prefix. The substrates still differ — raw is files on NFS rooted at /data/, while Bronze/Silver/Gold are Zarr + Icechunk repositories on Ceph RGW rooted at the bucket prefix — but the path shape below the root is the same in both, which is what lets one RBAC scope name one storage prefix (RBAC). The single exception is a Gold product fusing several datasets: it has no one dataset to sit under, so it lives at project/…/product/… instead (Gold §2).

  • Three entity levels, one version axis. Organization → Project → Dataset, and beneath a dataset a single linear history of revisions. A project is a programme of work (modeling-simulation); a dataset is one body of data belonging to it, typically one run or one contributor's deposit (run-0042); a revision is one immutable commit to that dataset.
  • IDs are UUIDv7, lowercase hex without dashes in paths, with dashes in JSON. Slugs match ^[a-z0-9][a-z0-9-]{1,N}$ (N=62; datasets N=80), never contain --, so slug--id splits unambiguously. Revision numbers are zero-padded to six digits so lexicographic order equals numeric order.
  • Release tags match ^[a-z0-9][a-z0-9._-]{1,62}$ — dots allowed, because these are version labels (v1.0, 2026-q3) rather than path components.
  • The single .staging/ at /data/ guarantees staging and every dataset's raw/ prefix are on the same filesystem, which is what makes rename(2) atomic. Where classification demands physical separation, a security domain becomes its own root (/data-restricted/) with its own staging directory; nothing ever links or renames across roots.
  • pkg/catalog/paths.py is the single source of path construction and parsing; the reconciler and sweeper recover (org, project, dataset, revision_number, revision_id) from any prefix.

3. Core contracts

Metadata

metadata.json is a complete revision-time snapshot, never a pointer to current state: schema identifier, the full org/project/dataset reference chain (slug + id each), the revision number, title, creators, committed_by/committed_at (system-generated — a client-supplied value is a 400), classification, tags, source, coverage, manifest digest, and namespaced extensions per science profile (e.g. org.example.mcnp/1.0 carrying code version, input-deck path, parameter axes). The core envelope schema is versioned in the repository; extension schemas are published by stewards into a registry whose rows are immutable per (namespace, version) and mirrored to storage so recovery never depends on the database. Unknown extension namespaces are stored, not rejected; readers must preserve unknown keys round-trip.

Manifest

manifest.json lists every payload file with size, SHA-256, and media type, sorted by path. The document is canonicalized per RFC 8785 (JCS) and its SHA-256 is the revision's content identity; the stored file is the JCS form, so a recovering reader rehashes stored bytes directly. Integers in canonicalized documents are asserted below 253 so a future size-cap raise fails loudly instead of corrupting digests. Path rules, applied identically client-side and server-side (mismatch is a 400): relative, forward-slash, payload/ prefix, Unicode NFC normalization (macOS emits NFD), no ./../control characters/trailing slashes, ≤1024 bytes; only regular files; NFC- or case-colliding paths are 409 PATH_COLLISION; zero-byte files legal; empty revisions rejected; a manifest whose digest already exists on another revision of the same dataset is 409 DUPLICATE_CONTENT.

Releases

A release is a named, immutable pointer at one revision — the same relationship an Icechunk tag has to a snapshot, so the versioning model is identical in all four layers. Nothing lives underneath a release: releases/v1.0.json records {revision_number, revision_id, title, created_by, created_at} and is written once with O_EXCL. Creating one is a separate, audited operation after commit (POST /datasets/{id}/releases), never a side effect of ingest.

Tags are immutable because their purpose is citation: a paper that cites dataset@v1.0 must resolve to the same bytes forever. A tag that could be moved would make the citation meaningless. Retagging means issuing a new tag; a wrong tag is withdrawn (an audited tombstone), not repointed.

Amendments

Post-commit metadata correction is steward-only and append-only: numbered amendments/NNNN.json documents, each a whole-key replacement over an allow-list (title, description, tags, coverage, source system, extension documents — plus data_classification, which requires a separate permission and emits its own audit event). IDs, numbers, creators, timestamps, and the manifest digest can never be amended. Effective metadata = base folded with amendments in sequence; the fold is implemented once, in pkg/catalog. Contributors who want different metadata commit a new revision.

Limits and concurrency

Defaults: 10 GiB/file, 10,000 files/revision, 1 TiB/revision (oversized single artifacts are pointed at the Zarr/Icechunk path in the error detail). Idempotency-Key is required on every mutating POST and replayed requests return the stored result; If-Match ETags guard every descriptive-document mutation; no database transaction is ever held across file I/O or hashing.

4. Ingest session and locking

Sessions run a strict state machine — PREPARING → UPLOADING → VERIFYING → COMMITTING → COMMITTED, with ABORTED/FAILED terminal and every illegal transition raising.

  • The lock is per-dataset: one open ingest session per dataset (partial unique index in PostgreSQL), so run-0042 and run-0043 upload concurrently while successive commits to the same dataset serialize. The revision number is allocated at BeginIngest as max(committed)+1 under the lock — gap-free per dataset (invariant E), and the final path is known before any byte is written.
  • Dataset-scoped locking is the cost of collapsing the hierarchy. Two people depositing into one dataset queue behind each other. This is the right trade while a dataset is one run or one deposit; if datasets grow coarse enough that concurrent contributors are normal, the answer is finer-grained datasets, not a re-introduced level.
  • Creating a dataset is implicit in the first BeginIngest naming a new dataset slug (subject to dataset.create), or explicit via POST /projects/{id}/datasets.
  • The upload plan assigns every file action: upload or action: hardlink. Hardlink sources are resolved from the parent revision's manifest.json read from the filesystem — storage is consulted as the authority on every ingest, not only during recovery. Hardlinked files inherit the parent's verified SHA-256 and are not rehashed.
  • Session TTL 2 h, refreshed by heartbeat and by any successful part upload; a crashed client releases the dataset lock within the TTL; a project admin can force-abort (audited). Interrupted transfers resume via completed_parts.

5. The commit protocol

CommitIngest(ingest_id, manifest_sha256, If-Match, Idempotency-Key)

 1. Idempotency replay check.                                        [PG]
 2. Lock session row; assert VERIFYING, ETag, manifest digest.       [PG]
 3. Assert every file accounted for, every digest matched.           [PG]
 4. In .staging/{ingest_id}/: write manifest.json, metadata.json,
    COMMITTED (all JCS; fsync each file, then fsync the dir).        [NFS]
 5. Seal: chmod payload files 0444, dirs 0555.                       [NFS]
 6. rename(.staging/{ingest_id},
           …/revisions/{nnnnnn}--{revision_id})   ◀── durability point [NFS]
 7. ONE short PG transaction: revision row, session → COMMITTED,
    audit event, outbox event, idempotency record.                   [PG]
 8. Best-effort: regenerate INDEX.json (reconciler owns it).         [NFS]
Crash after stepStorage stateResolution
4–5Complete-looking envelope, still under .staging/ Invisible (readers never scan staging). Session expires → sweeper deletes the staging dir.
6Envelope published under revisions/, no PG row Orphan commit. Reconciler imports the row from COMMITTED. A retry of step 6 finds staging gone and the target present → treats the rename as done (idempotent).
7CompleteNormal; step 8 retried by the reconciler.

There is no distributed transaction between the filesystem and PostgreSQL, and the design does not pretend otherwise: ordering is chosen so every crash window is a state the reconciler can name. Storage leads; the catalog follows (invariant G) — a revision row is never published before the rename is durable.

Why keep a marker when rename is atomic? Because the envelope is complete by construction (invariant C), the COMMITTED file is not needed for visibility. It exists as the reconciler's catalog-reconstruction record — digests, counts, committer, timestamp in one small JSON — as the object site replication tools can key on, and as defense in depth if a partial copy ever lands under revisions/ by operator error.

NFS-specific discipline

  • Single-writer model: only Huron service identities write the filesystem. All API pods and workers mount the same export; close-to-open consistency suffices because no node reads a file until after the writer closed it and the rename published it.
  • fsync before rename on every file and the staging directory; fsync the rename target's parent after. NFS servers may otherwise acknowledge writes before stable storage.
  • No advisory locks on NFS. All coordination (sessions, dataset locks, generation numbering) lives in PostgreSQL. The filesystem is never used as a lock service.
  • Atomicity boundary checked at startup: staging and final trees must share a filesystem per raw root (st_dev compared); cross-device rename is a deploy-time error, not a runtime surprise.

6. Hardlink dedup and sealing

Unchanged files between successive revisions of a dataset are materialized by hardlinking the parent revision's payload into the staging payload (prepare worker, concurrent with client uploads). The new revision remains a full logical copy — every revision directory lists every file — while unchanged bytes are stored once.

The hardlink hazard, and its containment. Hardlinks share an inode: a write through any link would corrupt every revision sharing it. Containment is layered: (1) sealing — committed payload is 0444, directories 0555; (2) identity — only the Huron service user owns these files, and no user-facing code path opens payload for write, ever; (3) audit — a quarterly scrubber re-hashes a sample of payload files against manifests and raises DEGRADED on mismatch. Where site policy forbids hardlinks or trees cross devices, the prepare worker falls back to copy_file_range() (reflink where supported) behind the same action: hardlink plan entry.

7. Descriptive documents

Mutable descriptive state — org, project, dataset — is stored as immutable numbered generations plus a small pointer: write generations/{n+1:06d}.json with O_EXCL (never overwritten), then atomically replace CURRENT.json via write-temp + fsync + rename. Generation numbers are allocated under a PostgreSQL row lock, so two concurrent edits cannot pick the same n. Recovery: if the pointer is missing or points at a nonexistent generation, the highest existing generation wins.

8. Retention: TTL expiration, holds, purge

Per-category TTL

The science profile classifies each expected file into a retention category; the project sets the policy:

retention:
  categories:
    essential_input:      retain          # input decks, includes, environment specs
    primary_output:       retain          # outp — small, scientifically primary
    bulk_intermediate:    ttl_days: 90    # runtpe, ptrac, large logs
    scratch:              ttl_days: 30
  starts: after_silver_published          # clock starts only once Bronze+Silver are verified

The retention worker expires payload files whose category TTL has elapsed and whose revision has a published Bronze and Silver materialization. It writes an EXPIRED marker listing exactly which manifest entries were removed and why, flips the PG revision state to EXPIRED_PARTIAL (or EXPIRED if all payload went), and emits audit + outbox events. Everything else survives: filenames, sizes, checksums, extracted parameters, manifest hash, sidecars, lineage. The upload confirmation and the dataset page both show the consequence before the fact:

Raw bulk files expire: 90 days after Silver publication
Native MCNP replay after expiration: unavailable (inputs retained; outputs regenerable by re-run)
Earliest retained representation: Bronze Icechunk snapshot

Pins and legal holds

retention.pin (project owner) exempts a revision from TTL; retention.legal_hold (governance authority) freezes TTL and purge for its scope. Holds are first-class rows, audited, and checked by the retention worker before every deletion.

Purge

Purge is two-person, audited, and deliberately inconvenient: one platform admin requests with a reason, a different one approves (enforced by a database CHECK constraint, not convention). Execution destroys payload and manifest.json — filenames and per-file digests are frequently the sensitive material — and retains metadata.json, amendments, COMMITTED, a PURGED marker, and the audit trail. Idempotent and resumable. Invariant I: a committed envelope without payload is valid only with a PURGED or EXPIRED marker; anything else is data loss and is raised as DEGRADED.

9. Sweeper and reconciler

  • Sweeper (15 min): deletes .staging/{ingest_id} directories whose session is terminal or expired, and staging dirs with no session row older than 24 h. It never descends into orgs/ — its deletion scope is staging, full stop. A fraction guard refuses to run if it would delete more than a configured share of staging in one pass, and every run supports --dry-run.
  • Reconciler (nightly + on demand): walks revisions/ and compares with PostgreSQL. Orphan envelope → import the row from COMMITTED. Row without an envelope → DEGRADED, alert, never delete the row. Digest mismatch → DEGRADED. Payload missing without PURGED/EXPIRED → DEGRADED. Stale INDEX.json → regenerate. Torn CURRENT.json → repoint at the highest generation. It also verifies seal permissions and hardlink counts. The reconciler never silently rewrites catalog history — disagreements become findings, alerts, and report entries.
  • lakectl rebuild --from-storage reconstructs PostgreSQL structural rows from the NFS tree alone (orgs → datasets from generation documents, revisions from COMMITTED markers, release tags from releases/*.json), then the derived-layer registry from RGW snapshot metadata, then the LanceDB projection. RBAC, audit, idempotency records, and API keys are recoverable only from PostgreSQL backups — stated plainly so nobody assumes otherwise.

10. Upload modes

ModevMechanics
API streamingv1 Client streams file parts through the API; SHA-256 computed in flight (thread pool, never on the event loop); parts land in staging; resume via completed_parts.
Register-in-placev2 For data already on the raw filesystem (HPC jobs writing to a Huron-managed landing directory): the CLI requests a landing allocation inside .staging/, the job writes there directly (or the CLI moves files in), then ingest proceeds hash-verify → commit without a second copy. Requires same-filesystem, group-writable landing dirs; the API re-hashes everything it did not stream. The mode field in the upload plan is the seam this slots into.

What the scientist sees. None of this. They run huron upload ./run-0042 --project modeling-simulation --dataset run-0042 --infer --confirm, confirm the handful of human-owned assertions the extractor could not infer (campaign, run purpose, quality state), and get back a committed, checksummed, immutable revision with its Bronze build already queued. When that revision is the one they want cited, they tag it: huron release create --dataset run-0042 --revision 1 --tag v1.0.
