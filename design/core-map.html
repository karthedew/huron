huron/core

Where authenticated Huron operations coordinate domain rules, storage, database transactions, and retry behavior.

This is a source-linked map of src/huron/core/, including its integrity/ subpackage. It describes the inspected implementation; delivery status remains in the roadmap. Source links are relative to this repository, so keep the HTML in design/ when opening it locally.

1. Orientation

Core chooses the operation and its ordering. Injected adapters perform the I/O. For example, IngestService coordinates a Raw commit through RawStore and HierarchyStore; the POSIX and PostgreSQL implementations live in pkg/.

Actor-bound operations

CatalogCreation, CatalogService, RawIngestionService, RevisionReadService, and IdentityService use an AccessPolicy bound to an authenticated actor.

Internal workflow implementations

_catalog.py, _ingest.py, and _revision_reader.py implement the work behind those operations. Their methods are not substitutes for actor-bound authorization.

Interfaces and shared helpers

catalog_ports.py and ports.py define injected capabilities. Scope resolution, retry claims, fingerprints, and generation documents have focused helper modules.

Externally authorized maintenance

integrity/CutoverService uses external operator authority and continuous writer/database exclusion. It has a separate interface from normal scientist operations.

The root __init__.py re-exports exactly six names: AccessPolicy and the five actor-bound classes above. Other classes remain available from their defining modules. Injected interfaces connect the implementations; import-linter contracts enforce dependency direction and exclude concrete adapters from core.

applications  →  core  →  pkg  →  schema
      │                    ▲
      └─ constructs adapters┘

core imports domain values and protocols.
core does not import FastAPI, asyncpg, or concrete storage adapters.

4. Authorization: actor → discovery → capability

AccessPolicy owns the actor reference and uses injected catalog/RBAC facts. Its visibility(), require(), and bindings() calls use fresh local binding caches rather than retaining grants across operations.

  1. visibility_for_principal() combines current bindings, project classifications, and the parents of dataset-scoped grants through RoleBindingAuthorizer.visibility().
  2. scope() calls resource_scope(). Hidden and absent target resources fail discovery before a capability denial. Dataset scope resolves the owning project and organization from server records.
  3. require() calls check(), which accepts only Decision.ALLOW from pkg.rbac.decide().
  4. require_claim() separately checks that an idempotency claim belongs to the authenticated actor.

bindings_for_principal() reads stored human/group bindings. For service accounts, it resolves the account and synthesizes organization-scoped authority; missing or disabled accounts get no bindings.

Read the operation’s actual rule. Upload mutation methods use _owned() / _owned_file(). An owner can abort their session without the normal Raw-write check; a different actor needs project-update authority. The root package’s “authorized” intent is not proof of a check on every method: CatalogService.create_policy() and list_policies() currently delegate without an explicit AccessPolicy.require() call. This map records that behavior rather than implying universal capability checks.

5. Catalog operations

Create identities: CatalogCreation

create_organization(), create_project(), and create_dataset() authorize, validate configuration, and claim the operation. A dataset is a stable identity; creation alone does not produce a Raw revision.

CatalogCreation.create_dataset()
  AccessPolicy.require() + require_claim()
  validate slug / entry layer; resolve authoritative parents
  CreationStore.transaction():
    claimed_result() → existing record on a matching retry
    writer.insert_dataset()
    GenerationDocuments.write() → RawStore.write_generation()
    writer.remember()
  database transaction commits

CatalogService.datasets.describe(id, DescriptionChange)
  authorize → Dataset.describe(expected_version, ...)
  unchanged object? return without opening a transaction
  DescriptionStore.transaction():
    writer.datasets.describe() → compare-and-swap version check
    read committed ancestry → GenerationDocuments.write()
  database transaction commits

GenerationDocuments.write() adds the generation schema identifier and canonicalizes the record. Storage writes generations/NNNNNN.json, then atomically replaces CURRENT.json. DescriptionChange distinguishes omitted values from empty replacements; slug changes are refused.

Discover and govern: CatalogService

  • organizations, projects, datasets: typed get(), browse(), and describe(). Browse checks parent discovery and returns visibility-filtered keyset windows.
  • create_release(), release(), releases(): delegate to HierarchyRepository. Tag creation resolves an exact revision, inserts a release row, and writes RawStore.write_tag_once() within the open transaction.
  • grant_role(), revoke_role(), get_role_binding(), bindings_at(): scoped role administration through RbacStore.
  • create_service_account(), get_service_account(), list_service_accounts(), disable_service_account(): organization-scoped account administration.
  • create_policy(), attach_policy(), list_policies(): policy persistence; attachment checks the target’s policy-attach capability.
  • layers(): describes declared layer capabilities and current caller decisions. It does not execute Bronze, Silver, or Gold processing.

Two stores, ordered writes. Creation, description, and release-tag workflows perform filesystem I/O while a database transaction is open. A filesystem exception rolls back database work, but a database rollback cannot undo an already-durable filesystem write. This is different from the short, separated database transactions in Raw commit below.

     │

The crash seam: publication may be durable before transaction B succeeds. A matching retry uses the frozen CommitIntent, verifies the exact stored evidence, and finishes the database work. Existing final storage is verified on replay; an index-write failure is logged without failing an already successful commit.

Values crossing the interfaces: ManifestEntry, IngestFile, IngestSession, CommitIntent, and RevisionRecord belong to pkg/catalog. Core’s SessionLedger pairs a session with its file records. Clock is injected into IngestService; blocking Raw-store operations generally run through asyncify().

RevisionReadService.revision(id)
  → RevisionService.revision(id, visibility)
    → HierarchyStore.revision(id)
    → HierarchyStore.datasets.get(dataset_id, visibility)

RevisionReadService.payload_file(record, path)
  → _readable(record.id): freshly resolve identity + require Raw data.read
  → RevisionService.payload_file(authoritative_record, path)
    → validate_manifest_path(path)
    → RawStore.read_document(manifest.json) → decode_manifest()
    → compare manifest digest with database record
    → resolve a listed entry → RawStore.stat_document(payload path)
    → compare file size → PayloadFile(entry, location, stat)

manifest_file() returns a manifest location and stat after authorization. PayloadFile also contains a path and stat, not an open file descriptor or the payload bytes. The transport streams the returned location. Individual payload reads check the stored manifest digest and file size; they do not hash the full file on each download.

8. Identity operations

IdentityService consumes AccessPolicy, PrincipalStore, CredentialStore, SessionStore, ApiKeyWriter, and the actor-bound CatalogService.

  • create_user(): require system user-management capability, create identity, hash the initial password off-thread, and persist its credential.
  • set_password(): _user() resolves an authorized human identity; persist the new credential, then _revoke() browser sessions and API keys.
  • disable_user(): disable the principal, then revoke sessions and keys.
  • issue_key(): create a key for the authenticated actor and return the record plus its one-time cleartext token.
  • issue_service_account_key(): _account() checks management authority and exact organization membership; reject disabled accounts before storing a new key.
  • disable_service_account(): disable through the catalog, then revoke programmatic credentials, with an early return for an account disabled before this invocation.

These methods sequence calls to individual stores. There is no shared transaction spanning principal, credential, session, and API-key adapters in this class. Several timestamps use datetime.now(UTC) directly; clock injection is not uniform across core.

9. Integrity maintenance

CutoverService prepares legacy storage for a protocol transition. prepare(run_id) returns a ProtocolTransition; validate(transition) asks the live authority to admit the record under its current generation.

  1. MaintenanceAuthority.authenticate() supplies a root-scoped operator grant. WriterExclusion.establish() mints a new controller generation and returns fence evidence naming it, the run, the operator and the database identity; the returned actor/root must match the grant.
  2. LegacyStorage.claim() holds exclusive local ownership. DatabaseExclusion.exclude() compares the fence's database identity with the live database, then excludes application database roles. _Fence.check() and monitor() continuously verify both forms of exclusion.
  3. GenerationVerifier.verify() compares the exact control-file inventory, historical generation identities, current document contents, and CURRENT.json pointers against authoritative hierarchy records.
  4. Scan the union of filesystem and database revision paths. LegacyMaintenance.lookup() resolves trusted identity. RevisionVerifier.verify() inspects documents and delegates full payload inspection, producing VERIFIED or DEGRADED evidence; ambiguous identity is refused.
  5. LegacyMaintenance.resolve() persists trusted records and legacy-session resolution. Write the canonical inventory report and numbered transition record through _publish().
  6. Any failure after establish ends the epoch through WriterExclusion.abandon(). After releasing local ownership, WriterExclusion.validate() asks the controller to admit the record; it is admitted only while its fence names the live generation, and a lost reply is resolved by validating again.

_settled_write() waits for a started evidence write to settle even if the coroutine is cancelled. ProtocolInventory.certifies() checks exact verified membership; ProtocolTransition.bind() and validate_inventory() bind the receipt to the report’s digest, identities, counts, and findings.

Preparation is not activation. This workflow leaves application writers excluded. The existence of an immutable report or record does not establish admission; only the controller's live generation does. Protocol initialization, activation/startup enforcement, general recovery, and trash cleanup are separate planned capabilities in the Raw integrity design; the classes here do not establish their delivery.

11. Reading and test guide

“How does an upload become durable?”

Read raw.py → _ingest.py → pkg/rawstore/store.py and pkg/metastore/ingest.py. Start with IngestService.commit(), then trace file completion backward.

“Where is a dataset created or renamed?”

Read catalog_creation.py and catalog_collections.py → domain record describe() → catalog_documents.py → the hierarchy adapter. Titles/descriptions can change; storage slugs stay fixed.

“Why can this actor see this resource?”

Read access.py → scopes.py → pkg/rbac and the visibility-filtered metastore collections. Discovery and byte-read capability are separate decisions.

“What proves a legacy root was inspected?”

Read integrity/cutover.py → verifiers → evidence models → maintenance adapters. Follow both durable evidence and the controller's live generation checks.

Behavioral evidence to inspect

  • Core workflow unit tests: reusable operations independently of HTTP.
  • Catalog-store contract tests; catalog creation and description integration tests.
  • Verified Raw ingestion integration tests; process-death contract tests; Raw acceptance gate.
  • Cutover unit tests, generation verification tests, and protocol cutover integration tests.

These are source-navigation links, not a claim that the suites were run to produce this document. The Makefile and repository instructions define implementation gates.

Scope: observed core implementation, including preparatory integrity work. Search projection, Ray/Zarr execution, derived-snapshot publication, and full automated recovery are not implemented core workflows in this map.
