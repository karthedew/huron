Raw Layer — NFS Store

Immutable scientific evidence on a POSIX filesystem: envelopes, manifests, the atomic commit protocol, retention, and the machinery that keeps all of it honest.

Raw sections describe the engine being replaced by the Raw lake (RAW_LAKE_DESIGN.md).

Implementation status: P2 Raw ingestion and commit are complete; see the recorded acceptance evidence. This page also specifies later recovery, retention and governance capabilities; their status is tracked separately in the roadmap. The scientist SDK and Ray/Zarr workflows remain planned.

Polaris: the web has no Raw surface, and Raw is not registered in Polaris; see Raw stays outside Polaris.

1. Why NFS for raw

Raw's job is to be the evidence tier: byte-exact, immutable, navigable by a human with ls and jq even if every Huron service is gone. Two backends were considered:

NFS / POSIX (chosen)Object storage (rejected for raw)
Ingest cost Every submission uploads its complete files into private staging; publication is a same-filesystem move after verification. Every run — up to 1 TiB — copied through the API into the store.
Publish atomicity rename(2) is atomic within a filesystem: the whole envelope appears at once, marker included. Objects appear one by one; a marker-written-last protocol and reader discipline are needed to fake atomicity.
Revision independence Each revision owns a complete physical copy; unchanged bytes are uploaded again. No shared inodes or inherited files (§7). Separate objects per revision can also provide independent copies.
Direct access None — all raw byte access is API-mediated, which is the RBAC posture we want anyway (RBAC). Presigned URLs possible.
Consistency caveats Close-to-open cache consistency; contained by the single-writer service model and fsync discipline (§5). Strong read-after-write.
Capacity Filesystem quotas per project; site NFS scaling limits apply. Effectively unbounded.

The deciding facts: the data is already on NFS when it is born; raw access should be API-mediated regardless of backend; and rename gives a strictly simpler commit protocol. What is given up — presigned downloads and object-store capacity economics — is acceptable for the evidence tier, because Bronze onward lives on object storage and carries the read traffic.

One spine, four layers. The organization/…/project/…/dataset/… hierarchy is identical for every layer, and the layer is the leaf: a dataset's raw, Bronze, Silver and Gold all hang off the same dataset directory, so "everything about run-0042" is one prefix. The substrates still differ — raw is files on NFS rooted at /data/, while Bronze/Silver/Gold are Zarr + Icechunk repositories on S3-compatible object storage rooted at the bucket prefix — but the path shape below the root is the same in both, which is what lets one RBAC scope name one storage prefix (RBAC). The single exception is a Gold product fusing several datasets: it has no one dataset to sit under, so it lives at project/…/product/… instead (Gold §2).

  • Three entity levels, one version axis. Organization → Project → Dataset, and beneath a dataset a single linear history of revisions. A project is a programme of work (modeling-simulation); a dataset is one body of data belonging to it, typically one run or one contributor's deposit (run-0042); a revision is one immutable commit to that dataset.
  • IDs are UUIDv7, lowercase hex without dashes in paths, with dashes in JSON. Slugs match ^[a-z0-9][a-z0-9-]{1,N}$ (N=62; datasets N=80), never contain --, so slug--id splits unambiguously. Revision numbers are zero-padded to six digits so lexicographic order equals numeric order.
  • The single .staging/ at /data/ guarantees staging and every dataset's raw/ prefix are on the same filesystem, which is what makes rename(2) atomic. Where classification demands physical separation, a security domain becomes its own root (/data-restricted/) with its own staging directory; nothing ever links or renames across roots.
  • core.raw.paths owns staging and revision path construction; core.catalog.paths owns hierarchy, generation and cross-layer layout, and core.foundation.names owns lexical validation. Reconciler and sweeper workflows remain planned.

3. Core contracts

Metadata

metadata.json is a complete revision-time snapshot, never a pointer to current state: schema identifier, the full org/project/dataset reference chain (slug + id each), the revision number, title, creators, committed_by/committed_at (system-generated — a client-supplied value is 422 REQUEST_INVALID: the body model has no such member), classification, tags, source, coverage, manifest digest, and namespaced extensions per science profile (e.g. org.example.mcnp/1.0 carrying code version, input-deck path, parameter axes). Every schema involved — the core envelope (registered at platform scope from the repository seed at bootstrap), organization metadata standards, and per-project enrichments over them — lives in the schema registry: rows immutable per (namespace, name, semver) and mirrored to storage so recovery never depends on the database. At ingest, the envelope is validated against the effective schema — the org base composed with the project's enrichment — and records the exact schema references it validated against. Unknown extension namespaces are stored, not rejected; readers must preserve unknown keys round-trip.

Manifest

manifest.json lists every payload file with size, SHA-256, and media type, sorted by path. The document is canonicalized per RFC 8785 (JCS) and its SHA-256 is the revision's content identity; the stored file is the JCS form, so a recovering reader rehashes stored bytes directly. Integers in canonicalized documents are asserted below 253 so a future size-cap raise fails loudly instead of corrupting digests. Path rules, applied identically client-side and server-side (mismatch is a 400): relative, forward-slash, payload/ prefix, Unicode NFC normalization (macOS emits NFD), no ./../control characters/trailing slashes, ≤1024 bytes; only regular files; NFC- or case-colliding paths are 409 PATH_COLLISION; zero-byte files legal; empty revisions rejected. Identical manifests may appear in distinct revisions: content identity is not revision identity. A retry with the same upload identity returns the same revision.

Releases

Release tags were retired on 2026-10-15. Raw keeps only full, numbered revisions, so a dataset and a revision number name one immutable revision; no release routes, rows or tag documents exist.

Amendments

Amendments were retired on 2026-10-21. A committed revision is immutable, its metadata included: contributors who want different metadata commit a new revision. The amendment fold, its field allow-list and the AMENDMENT_FIELD_FORBIDDEN error code were removed, and no route or Huron code writes amendment documents. The legacy revision_amendments table, which nothing writes, remains until the legacy Raw tables are dropped.

Limits and concurrency

Defaults: 10 GiB/file, 10,000 files/revision, 1 TiB/revision (oversized single artifacts are pointed at the Zarr/Icechunk path in the error detail). Idempotency-Key is required on every mutating POST and replayed requests return the stored result; If-Match ETags guard every descriptive-document mutation. Raw part transfer, hashing and envelope publication run outside the short database transactions. Catalog generation writes are ordered filesystem operations inside their database transaction; a database rollback cannot undo an already-durable file. See the current transaction map.

4. Ingest session and locking

Sessions run a strict state machine — PREPARING → UPLOADING → VERIFYING → COMMITTING → COMMITTED, with ABORTED/FAILED terminal and every illegal transition raising.

  • The lock is per-dataset: one open ingest session per dataset (partial unique index in PostgreSQL), so run-0042 and run-0043 upload concurrently while successive commits to the same dataset serialize. The revision number is allocated at BeginIngest as max(published revision number)+1 across every lifecycle/health state under the lock — gap-free per dataset (invariant E), and the final path is known before any byte is written.
  • Dataset-scoped locking is the cost of collapsing the hierarchy. Two people depositing into one dataset queue behind each other. This is the right trade while a dataset is one run or one deposit; if datasets grow coarse enough that concurrent contributors are normal, the answer is finer-grained datasets, not a re-introduced level.
  • Creating a dataset is implicit in the first BeginIngest naming a new dataset slug (subject to dataset.create), or explicit via POST /projects/{id}/datasets.
  • The upload plan assigns every submitted file action: upload. Every revision is an independent complete submission: no parent-manifest comparison, inherited files, shared hardlinks, or cross-revision pointers. A file omitted from this submission is absent from this revision. Every file's bytes, including unchanged content, must be received and verified.
  • Session TTL 2 h, refreshed by heartbeat and by any successful part upload; a crashed pre-commit client releases the dataset lock within the TTL plus one sweep interval; a project admin can abort eligible pre-commit states (audited). COMMITTING and RECOVERING retain their claims until safe recovery. The RECOVERING domain state and schema constraints are implemented; recovery orchestration remains planned. Interrupted transfers resume via completed_parts.

5. The commit protocol

Verified completion is implemented and independently verified (M1a, 2026-09-11). Part requests write outside the publishable envelope. Completion copies to a fresh private inode, hashes the written bytes, fsyncs and closes it, then installs it without replacement into payload. An overlapping completion can only install the same verified content; it cannot delete a winner. No subsequent staging write may recreate a missing session root. Installation uses native exclusive rename (renameat2(RENAME_NOREPLACE) on Linux and renameatx_np(RENAME_EXCL) on Darwin), refusing unsupported filesystems. PostgreSQL stores the frozen canonical command and documents as immutable bytea, with generated SHA-256 digests, actor and commit instant. Its former deployment prerequisites — cutover, writer exclusion and startup gates — were retired on 2026-10-15 rather than delivered; this receipt does not certify deployment.

Verified completion defaults to one copy per API process with a 1 GiB free-space reserve. HURON_COMPLETION_MAX_CONCURRENT and HURON_COMPLETION_RESERVE_BYTES configure these limits. Admission counts each active copy's expected bytes until installation and cleanup finish; installed-file replay requires no new reservation. This does not coordinate capacity across processes or exclude other writers. Deployment sizing still accounts for uploads, retained descriptors and every replica.

Completion before installation / before COMPLETE rowPrivate candidate is invisible; installed-before-row retry verifies and records the existing file. No row attests an absent installation.
Commit before final renameSession retains its claim. Recovery fences RECOVERING and relocates staging. Valid marker evidence is copied and verified into fresh inodes before publication; no marker means fail only after safe relocation. Invalid or ambiguous evidence remains locked.

There is no distributed transaction between the filesystem and PostgreSQL, and the design does not pretend otherwise: ordering is chosen so every crash window is a state the reconciler can name. Storage leads; the catalog follows (invariant G) — a revision row is never published before the rename is durable.

Why keep a marker when rename is atomic? Because the envelope is complete by construction (invariant C), the COMMITTED file is not needed for visibility. It exists as the reconciler's catalog-reconstruction record — digests, counts, committer, timestamp in one small JCS document: urn:huron:committed:1 for legacy data and urn:huron:committed:2 for implemented verified materialization (under validation) — as the object site replication tools can key on, and as defense in depth if a partial copy ever lands under revisions/ by operator error.

NFS-specific discipline

  • Single-writer model: only Huron service identities write the filesystem. All API pods and workers mount the same export. P3 separates upload inodes from publishable inodes; a stale writable upload descriptor cannot alter published bytes. Verify publication primitives and exclusion on the actual NFS deployment; a heartbeat, database etag or chmod does not revoke an open descriptor.
  • fsync before rename on every file and the staging directory; fsync the rename target's parent after. NFS servers may otherwise acknowledge writes before stable storage.
  • No advisory locks on NFS. All coordination (sessions, dataset locks, generation numbering) lives in PostgreSQL. The filesystem is never used as a lock service.
  • Atomicity boundary checked at startup: staging and final trees must share a filesystem per raw root (st_dev compared); cross-device rename is a deploy-time error, not a runtime surprise.

6. Control flows

The flows below are the Raw layer's write and read paths as the code executes them today (Raw ingestion, Catalog creation, Raw revision reads; public construction is through RawRuntime and each domain root). Each step is tagged with the system it touches: [PG] PostgreSQL, [NFS] the raw filesystem, [core] the actor-bound authorization that runs before any store is reached. A [PG] ONE TRANSACTION block is one async with hierarchy.transaction(); nothing outside such a block holds a connection, and no block ever contains a part upload or a hash (invariant: storage leads, the catalog follows). Every mutating request carries an Idempotency-Key; "stake key" means the INSERT … ON CONFLICT arbitration of §3, which either wins the key, replays the earlier result for an identical request, or refuses with 409 IDEMPOTENCY_KEY_REUSED.

6.1 Adding a new dataset

Two doors reach the same creation: the explicit POST /projects/{project_id}/datasets, and the project-level POST /projects/{project_id}/ingest-sessions, which mints a raw dataset and then runs flow 6.2 on it under a key derived from the same Idempotency-Key, so a retry after a failure between the two writes replays the kept dataset rather than minting a second one.

6.2 Updating an existing dataset: a new Raw revision

A dataset is never edited in place. "Updating" it means adding revision n+1, a complete, independent submission. The session is the unit of work; the per-dataset lock is the session itself (one non-terminal session per dataset). The numbered steps are the HTTP calls the SDK hides behind dataset.upload(...).

6.3 Tagging a release (retired)

Retired on 2026-10-15. Nothing names a revision except its dataset and number, so there is no tag to create, resolve or withdraw, and no releases/ document is written.

6.4 Two people writing the same dataset

Three cases, one rule each: ingest is serialized by the dataset row lock; descriptive edits are serialized by a version compare-and-swap; and a writer who disappears releases the lock by lease expiry, not by anyone else's action.

  says which bytes are durable. If nobody resumes, the sweep aborts S1 and the next
  BeginIngest allocates the SAME revision number S1 held: no row was ever written for it.

stat/open on sealed files.

Why a revision can briefly exist on disk without being readable. Between 5b and 5c a crash leaves a sealed, complete directory and a COMMITTING session. The envelope is self-describing (manifest, metadata, COMMITTED marker, all digested), so recovery imports it once rather than re-publishing; until that import, readers are simply told the revision does not exist, which is the honest answer. See the crash table in §5.

7. Independent copies and sealing

Each Raw revision owns a complete physical copy of every submitted file. Separate submissions may contain identical bytes and still receive different revision IDs and numbers. Removing an older revision never removes bytes needed by a later revision. Sealing makes published payload files 0444 and directories 0555; only the Huron storage identity owns them.

The proposed Python interface is dataset = client.datasets.create(...) or client.datasets.get(...), followed by dataset.upload(source=..., metadata=...). The source may be one file, multiple files or a directory. Required descriptive metadata uses the shared MetadataSubmission Pydantic contract; the backend also validates the final canonical document and supplies dataset identity, classification and committing actor. The SDK hides staging, heartbeat, verification and commit, and returns only once publication succeeds. The current backend exposes these resumable steps over HTTP; this SDK convenience API is planned.

Migration 0010_independent_raw removes manifest uniqueness and parent references, and requires upload-only ledgers. It refuses existing hardlink ledger entries: an operator must copy or re-ingest legacy data before upgrading. It never silently relabels shared files as copies.

8. Descriptive documents

Mutable descriptive state — org, project, dataset — is stored as immutable numbered generations plus a small pointer: write generations/{n+1:06d}.json through atomic_replace (write-temp + fsync + rename) — a file already at that number can only be a crashed attempt that never reached the row commit, so replacing rather than refusing it is safe — then atomically replace CURRENT.json the same way. Generation numbers are allocated by the committed UPDATE … WHERE version = $expected compare-and-swap, so two concurrent edits cannot pick the same n. Recovery: if the pointer is missing or points at a nonexistent generation, the highest existing generation wins.

9. Retention: TTL expiration, holds, purge

Per-category TTL

The science profile classifies each expected file into a retention category; the project sets the policy:

retention:
  categories:
    essential_input:      retain          # input decks, includes, environment specs
    primary_output:       retain          # outp — small, scientifically primary
    bulk_intermediate:    ttl_days: 90    # runtpe, ptrac, large logs
    scratch:              ttl_days: 30
  starts: after_silver_published          # clock starts only once Bronze+Silver are verified

The retention worker expires payload files whose category TTL has elapsed and whose revision has a published Bronze and Silver materialization. Before deletion it writes a numbered, immutable expired/0001.json intent listing exact paths, sizes, digests, categories and reasons; later records select disjoint entries in a gap-free sequence. Start time describes intent; completion is observed separately. After removal it derives the PG revision state as EXPIRED_PARTIAL (or EXPIRED if all payload went), and emits audit + outbox events. Everything else survives: filenames, sizes, checksums, extracted parameters, manifest hash, sidecars, lineage. The upload confirmation and the dataset page both show the consequence before the fact:

Raw bulk files expire: 90 days after Silver publication
Native MCNP replay after expiration: unavailable (inputs retained; outputs regenerable by re-run)
Earliest retained representation: Bronze Icechunk snapshot

Pins and legal holds

retention.pin (project owner) exempts a revision from TTL; retention.legal_hold (governance authority) freezes TTL and purge for its scope. Holds are first-class rows, audited, and checked by the retention worker before every deletion.

Purge

Purge is two-person, audited, and deliberately inconvenient: one platform admin requests with a reason, a different one approves (enforced by a database CHECK constraint, not convention). Execution destroys payload and manifest.json — filenames and per-file digests are frequently the sensitive material — plus expiry records and their mirrored per-file database contents. It retains metadata.json, COMMITTED, a PURGED marker, and the audit trail. Idempotent and resumable. The canonical PURGED intent is durable before the first unlink and binds revision, dataset, manifest digest, distinct requester/approver, authorization reference and request/approval/start instants. It contains no per-file details. Audit retains operation evidence without copying deleted file details. A valid intent with files still present is pending removal; missing files without valid explaining evidence are DEGRADED. P3 recognizes these contracts; P5 originates governance workflows. Storage-only recovery never resumes deletion without restored current authority.

10. Sweeper and reconciler

Sweeper and reconciler workflows remain planned. The superseded P3_DESIGN.md and P3_IMPLEMENTATION_PLAN.md record their earlier design and implementation slices.

  • Sweeper every 15 minutes: terminal session trees after a 15-minute grace, or unknown trees older than 24 hours, only with an authoritative session ledger. COMMITTING and RECOVERING are never eligible. Recheck, rename into staging trash, fsync and delete without following links. No deletion during database-loss/rebuild ambiguity. Guard refuses more than max(10, floor(25% of managed session trees)); limits are configurable. Dry-run changes no state.
  • Reconciler nightly/on demand: validate identities, canonical documents/digests, expected presence/sizes, ownership, seals and independent regular files on every pass. Budgeted hashing defaults to 1 TiB per run and a 7-day verification target with durable progress and overdue reporting. Import validated missing records; never overwrite conflicting history. Reseal only known validated content, never automatically chown. Rebuild INDEX; repair CURRENT only from an unambiguous valid generation chain. Complete relevant checks resolve findings; acknowledgement alone does not.
  • Recovery: 30-second commit heartbeat and 5-minute grace identify candidates, not safety. CAS to RECOVERING retains both claims; relocation prevents original-path publication, and a fresh verified copy prevents stale handles mutating recovered payload. One owner; no timed recovery takeover. Default automatic-copy cap 100 GiB; larger copies require an explicit command and capacity reserve. Ambiguity stays locked for operator action.
  • Removal continuation: existing valid intents only, with current authorization, restored governance, holds/pins and shared mutation coordination. P5 owns new intent creation. Pending purge blocks new payload/manifest reads; pending expiry blocks its selected files. Already-authorized streams may finish. DEGRADED blocks every new payload read.
  • Rebuild: offline into a fresh migrated database, resumable only under the same run/root identity. Restore hierarchy and revisions; no invented parents or historical authority. Missing parents, identity conflicts and ambiguous access block activation; reported DEGRADED revisions need not. RBAC, credentials, audit, holds, idempotency and original outbox require backups. Search and derived-layer reconstruction remain later phases.

Retired protocol cutover and recovery evidence

Retired 2026-10-15 (owner decision). The one-time offline protocol cutover is no longer planned. Its controller-generation epoch, writer and database-role exclusion, legacy verification, protocol/ inventory reports and transition records were deleted together with the lakectl operator CLI, and its protocol initialization and API startup gating will not be built; the implementation history records what was removed. Migration 0011 still refuses nonterminal legacy sessions. V1 markers remain unchanged and decodable; with no cutover inventory to admit them, v1 envelopes are operator findings.

Governance records use the same single-writer trust root, with no signatures. JCS is canonical encoding, not tamper proof. Mirror digests support database comparisons. Filesystem-only recovery can recognize pending removals but cannot infer that lost hold rows never existed.

11. Upload modes

ModevMechanics
API streamingv1 Client streams file parts through the API; SHA-256 computed in flight (thread pool, never on the event loop); parts land in staging; resume via completed_parts.
Register-in-placev2 For data already on the raw filesystem (HPC jobs writing to a Huron-managed landing directory): the CLI requests a landing allocation inside .staging/, the job writes there directly (or the CLI moves files in), then ingest materializes a verified independent copy before commit: no second upload, not no second storage copy. The mode field in the upload plan is the seam this slots into.
