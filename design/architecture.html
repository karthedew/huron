System Architecture

Stores, services, and the flow from HPC run to published product.

Implemented backend boundaries

src/huron/applications/api owns FastAPI transport, credentials, configuration, lifecycle and composition. src/huron/core owns reusable authorized catalog, identity, Raw ingestion and revision-read workflows. src/huron/pkg owns domain objects and technical adapters, including metastore for PostgreSQL and in-memory persistence.

Core services bind an authenticated actor, resolve authoritative ancestry and current permissions, and coordinate domain behavior, transactions, storage and publication. HTTP guards provide early rejections; core checks remain authoritative for non-HTTP callers. Domain objects own immutable state and transitions; composition and consumer-owned protocols connect capabilities. Infrastructure adapters may depend on domain types, while domain packages never import their adapters or core.

Dependency direction: applications → core → pkg → schema. Applications may import concrete adapters for wiring. A remote Python client calls the API and shares document contracts; it does not run privileged server workflows locally. Bronze/Ray, Silver and Gold workflow services remain planned; their input identities and output lineage must be published atomically with catalog output records when implemented.

StoreAuthoritative forNever holds
NFS (POSIX) Raw revision envelopes: payload bytes, metadata.json, manifest.json, COMMITTED, amendments, generation documents, purge/expiry markers. A scientist with ls and jq can navigate it offline. Derived arrays; anything a pipeline can regenerate.
Object store (S3-compatible) Bronze/Silver/Gold Icechunk repositories and their snapshot history; Iceberg files for tabular Gold; LanceDB tables ({prefix}-index). Raw evidence; the catalog of record for identity.
PostgreSQL Structural state only: identity and uniqueness (orgs → revisions), revision-number sequencing, per-dataset ingest locks, release tags, snapshot and product registry, the schema registry (immutable published schema versions, org base + project enrichment), lineage edges, RBAC bindings, API keys, jobs, audit, outbox. Plus denormalized title columns for browse. Full metadata mirrors; any text search index (banned).
LanceDB All text, tag, and (later) semantic matching, across all four layers — datasets, revisions, snapshots and products — with layer as a facet rather than a system boundary. Rebuildable from NFS + object store + PostgreSQL; if down, /search is 503 and browse keeps working. Anything authoritative.

The query split, restated for four layers. Structural questions (list projects, revisions of a dataset, snapshots of a repo, products depending on snapshot S117) are PostgreSQL. Matching questions ("absorbed dose", tag filters, similarity) are LanceDB. Effective metadata for a revision is read from NFS sidecars (base + folded amendments). Array bytes are read from the object store by the client, never through the API. No question is answered from two stores.

The object store is a portability boundary. The deployment target is Red Hat OpenShift, with object storage supplied by the cluster (OpenShift Data Foundation — its gateway exposes an S3-compatible API that is a subset of Amazon S3, on the order of two-thirds of the surface). Huron therefore assumes only the portable S3 core every compatible gateway serves — HeadBucket/HeadObject, GET/PUT/DELETE object, ListObjectsV2, multipart upload, conditional requests — which is also all Icechunk, Zarr and LanceDB need. Nothing may depend on vendor extensions: no bucket notifications (the outbox is Huron's event source), no object lock or lifecycle rules (retention is Huron's own worker), no server-side inventory (the reconciler lists and compares itself), no ACL semantics beyond bucket-policy/prefix scoping. STS-style credential vending (AssumeRole with a session policy) is gateway-conditional behind the vending port (API §5): where the deployed gateway lacks it, grants fall back to API-proxied chunk reads — same client code, degraded transport — so no capability of the platform requires more than the core.

4. Consistency model

  • Raw: a revision is visible iff its directory was atomically renamed into place with COMMITTED inside. PostgreSQL rows follow storage (reconciler imports orphans). Read-your-writes for browse via PostgreSQL.
  • Derived layers: an Icechunk snapshot is visible iff the catalog records it as published. Icechunk's own commit protocol guarantees snapshot atomicity on the object store; Huron's catalog adds the published/candidate distinction on top.
  • Search: eventually consistent; responses carry projection_lag_seconds and projection_watermark.
  • Lineage: written in the same PostgreSQL transaction that records a snapshot or product publication — never reconstructed after the fact.

5. Invariants

An invariant is a property the system must never violate — a property of the system, not of any one store; several below are held by no database rule at all. Where a PostgreSQL rule is what holds an invariant — or where none does — Catalog §2, What the database enforces names it.

Invariant
ANo capability is served from two stores; there is no search fallback.
BNothing under a published revisions/ prefix is ever deleted except by the audited retention/purge code paths.
CAt publication a revision contains COMMITTED and verified payload matching its manifest. P3 requires verification with no writable payload handles remaining and no later write opens; stale upload inodes are never published. Lawful later removal is governed by I; observed violations are DEGRADED, not silently repaired.
DFrozen objects are written exactly once; amendments are appended, never edited.
ECommitted revision numbers within a dataset are contiguous 1..N.
MA release tag is written once and never repointed; a wrong tag is withdrawn, not moved. dataset@tag resolves to the same bytes forever.
FThe client never chooses the final path and never writes COMMITTED.
GA revision/snapshot/product row is never published in PostgreSQL before its storage state is durable. Storage leads; the catalog follows.
HNo search response contains an ID the caller is not authorized to discover.
IMissing payload requires valid PURGED or numbered expiry evidence matching physical state. Write-ahead intent distinguishes pending removal from completion. Storage-only recovery cannot continue deletion without restored current governance; purge removes expiry per-file details too.
JOnly Huron service identities hold write credentials to Bronze/Silver/Gold repositories; every published snapshot has a catalog row created by a pipeline service, with validation evidence attached.
KEvery Gold product version resolves to exact input snapshot IDs, a transform container digest, and parameters — sufficient to re-execute the derivation without consulting anything mutable.
LAccess grants are scoped to a single repo prefix, read-only for non-service principals, and expire; possessing a grant for a Gold product confers nothing on its upstream inputs.
NEvery published snapshot states its origin: a lower-layer reference (raw revision or upstream snapshot), an external-provenance block, or a Gold derivation record. A snapshot with none of the three is refused. Gold is never an entry layer.

6. Deployment

  • Platform: OpenShift. Arbitrary non-root UIDs, read-only root filesystems, NetworkPolicy so only the API is routed; PostgreSQL via HA operator (CloudNativePG); the object store and NFS reachable only from the namespace.
  • NFS mounts: API, bronze builder (read-only), retention worker, sweeper, and reconciler mount the raw filesystem. The mount is not exported to users; see RBAC — data-plane enforcement.
  • Identities: separate service accounts per service; the projection worker is the only identity with write access to {prefix}-index; pipeline services get per-job, short-lived object-store credentials scoped to the one repo they are building; the retention worker is the only identity that can delete under revisions/.
  • FIPS: every image starts and imports cleanly under FIPS, MD5-for-protocol uses usedforsecurity=False, approved TLS suites to the object store/PostgreSQL, hash algorithm recorded in every manifest.
  • Backup: PostgreSQL WAL + nightly base (RPO 5 min, monthly restore test); NFS raw via filesystem snapshots + replication per site policy (quarterly restore drill); object store replicated per the cluster storage layer (ODF/Ceph replication or EC); LanceDB not backed up — rebuilt (timed quarterly). Polaris metadata is re-syncable from Huron.

Blast radius by design. Losing LanceDB costs search until a rebuild. Losing PostgreSQL costs sequencing/RBAC/audit until restore — raw data and derived arrays remain readable and reconstructable. Losing the object store costs derived layers, all rebuildable from raw (at compute cost) except where raw payload has expired — which is exactly why the retention policy retains reproducibility-essential inputs. Losing the NFS raw store is the one unrecoverable loss; it gets the strongest storage guarantees and the most conservative code paths.
