Gold Layer

Scientifically derived, validated, published data products — new scientific meaning, with lineage exact enough to re-execute the derivation.

1. What makes something Gold

Gold begins where a transformation creates a new scientific result: raw counts → calibrated radiance, flux → dose, tallies → safety metric, ensemble → uncertainty distribution, model + observation → validation product, multiple Silver datasets → fused product. Gold describes Huron's product status; the scientific processing level (L1/L2/L3 or a domain scheme) is separate metadata on the product.

Gold is derivation-defined, not trust-defined. A framing in which Gold is "the pool of trusted datasets we ship to customers" was considered and rejected. It conflates two orthogonal axes — processing level and governance status — and the cost is concrete: a validated Silver dataset that is ready to ship would have to be copied into Gold through an identity transform, paying storage twice, inheriting staleness tracking on a copy that adds no meaning, and leaving the word "gold" saying nothing about what was done to the data. Trust and shippability are properties, not a tier, and the model already expresses them: contract validation is what makes Silver Silver; a published snapshot is immutable and citable by its id; classification, discoverability and lifecycle state gate who sees it; and shipping externally is an access decision — a prefix-scoped read grant, or Polaris for tabular products — applied to whichever snapshot earned it, Silver or Gold. The derivation record below is exactly what makes a Gold product defensible to an external consumer; a pool has no such record. A customer-facing shelf that mixes Silver datasets with Gold products is therefore a curation object over pinned snapshots — catalog metadata — and not a storage layer.

Gold is never an entry layer. Raw, Bronze and Silver each accept direct entry from outside the lake; Gold does not, because invariant K requires every product version to carry a derivation record. Data that arrives already canonical is Silver, however trusted it is. A derivation computed outside Huron can still be published as Gold, provided it is re-validated here and its record names its external inputs as such — the requirement is the record, not the location of the compute.

2. Product model

Project
└── Product  (slug immutable, e.g. shielding-dose-response)
    │         single-source → attached to its one dataset
    │         fused        → attached to the project
    └── ProductVersion  (semver, e.g. 1.0.0)
        └── exactly one published Icechunk snapshot (e.g. G021)
            [+ optional Iceberg table materialization for tabular products]
ResourceIdentityMutableImmutable
Productid (UUIDv7) + slugtitle, description, tags, lifecycle (ACTIVE / DEPRECATED / RETIRED), contractid, slug, project, source dataset (when single-source)
ProductVersion(product_id, semver)status (CANDIDATE → PUBLISHED → STALE / SUPERSEDED / WITHDRAWN), version notes inputs, transform, parameters, snapshot — the entire derivation record

One Icechunk repo per product; each version's snapshot is tagged v{semver}. Where the repo sits is decided by how many datasets the product derives from, so a product's path states its provenance scope:

single-source   {prefix}/organization/…/project/…/dataset/{dataset_slug}--{dataset_id}/gold/
                  {product_slug}--{product_id}/repo/
fused           {prefix}/organization/…/project/{project_slug}--{project_id}/product/
                  {product_slug}--{product_id}/repo/

Why Gold alone is split. Raw, Bronze and Silver each describe one dataset, so each sits under that dataset and the layer is simply the leaf (Raw §2). Fusion is Gold's defining act — "multiple Silver datasets → fused product" is in §1 — and a product combining run-0042 and run-0043 belongs under neither. Naming one of them the primary would put a lineage claim in the path that the derivation record contradicts, so a fused product attaches to the project instead. In PostgreSQL this is products.dataset_id: set for a single-source product, NULL for a fused one — the same nullable-attachment pattern snapshots.dataset_id already uses. Either way products.project_id stays required and (project_id, slug) stays unique, so a product's identity does not depend on which case it is.

3. The derivation record (invariant K)

Every product version stores, immutably, everything needed to re-run it:

{
  "product": "shielding-dose-response",
  "product_version": "1.0.0",
  "inputs": [
    {"dataset": "nuclear-engineering/huron-shielding-study/reactor-shielding-sweep",
     "layer": "silver", "snapshot_id": "S117"},
    {"dataset": "reference-data/icrp/icrp-flux-to-dose-coefficients",
     "layer": "silver", "snapshot_id": "S031"}
  ],
  "transformation": {
    "name": "flux-to-dose",
    "container_digest": "sha256:3e4f…",
    "entrypoint": "aether run flux_to_dose.py",
    "parameters": {"conversion_coefficients": "icrp-116", "integration_dim": "energy"}
  },
  "validation": {"suite": "dose-product-v1", "evidence_ref": "…", "passed_at": "…"},
  "produced_snapshot": "G021",
  "published_by": "ldap:karl", "published_at": "2026-08-23T19:02:41Z"
}

Snapshot IDs are pinned by Huron at submission time — the scientist names datasets and layers; the platform resolves and freezes the exact snapshots before the transform runs, so a concurrent Silver append cannot make the record ambiguous. Lineage edges (gold_version ← silver_snapshot ← bronze_snapshot ← Raw pins) land in PostgreSQL in the same transaction as publication.

4. Publication workflow

scientist (Aether) develops the transform against Silver read grants
   ▼
huron product publish --name shielding-dose-response --version 1.0.0
      --input reactor-shielding-sweep@silver
      --input icrp-flux-to-dose-coefficients@silver
      --transform registry/…/flux-to-dose@sha256:3e4f… --validation dose-product-v1
   ▼
API: authorize (scientist may CREATE candidates; see below) → pin snapshots → job
   ▼
Product runner executes the container with read grants for exactly the pinned inputs
   ▼  candidate snapshot, status CANDIDATE
Validator — product suite:
   ✓ required variables, units, dims        ✓ dose finite and nonnegative
   ✓ coordinate coverage matches inputs     ✓ no run unexpectedly missing
   ✓ reference-case agreement               ✓ uncertainty propagation present
   ✓ product metadata contract complete
   ▼
project_admin reviews evidence → PUBLISH
   ▼
status PUBLISHED · lineage edges committed · LanceDB indexed ·
tabular products → Iceberg materialization → Polaris sync
  • Separation of experiment and publication: any project developer can create candidates; only the project_admin can publish (see RBAC). Candidates are visible to the project, never to search-wide discovery.
  • Versioning: new inputs or parameters ⇒ new version. Republishing the same version is forbidden; a bad publication is WITHDRAWN and succeeded.

5. Staleness and recomputation

When a Silver snapshot is superseded by a correction, Huron walks the lineage graph and marks affected published versions STALE, with the reason attached ("input S117 superseded by S119: run-0042 region replaced"). Policy per product:

on_input_superseded: mark_stale          # default: humans decide
# or: auto_recompute                     # re-run the identical derivation record against
                                         # the successor snapshots → candidate for review

Stale versions stay readable — reproducibility outranks tidiness — but carry the flag in every API response, client warning, and UI badge. A recomputation is a new version whose record points at both its inputs and the version it supersedes.

6. Cross-project derivations

A Gold product may combine Silver inputs from multiple projects (simulation + experimental measurements → validation product). Requirements, enforced at submission: read access to every input snapshot, product-creation permission in the destination project, and classification compatibility (the product's classification is at least the maximum of its inputs unless a project admin explicitly downgrades with justification, which is audited). Lineage does not grant access: a reader of the product sees redacted lineage ("derived from 2 restricted upstream datasets") unless they can discover the inputs (invariant L).

7. Tabular products and Iceberg

Some Gold products are tables, not arrays — summary statistics per run, dose-response tables, QA registers. For products declared shape: tabular, the product runner additionally materializes an Apache Iceberg table beside the Icechunk repo:

{product_dir}/repo/         ← Icechunk (authoritative)
{product_dir}/iceberg/      ← Iceberg materialization (mirrored)

where {product_dir} is the product's directory from §2:
  dataset/{dataset_slug}--{id}/gold/{product_slug}--{id}      single-source
  project/{project_slug}--{id}/product/{product_slug}--{id}   fused

The Iceberg copy exists for external engines (Spark, Trino, DuckDB…) and is registered in Apache Polaris by the sync worker — this is the entire Polaris surface (details in Polaris). The Icechunk snapshot remains authoritative; the Iceberg snapshot records which product version it mirrors, and the sync is one-way.

8. Discovery and consumption

results = huron.search("absorbed dose", project="huron-shielding-study",
                       kind="product", filters={"quality": "validated"})

dose = huron.open_product("shielding-dose-response", version="1.0.0")   # tagged snapshot
dose = huron.open_snapshot("G021")                                      # exact pin

Products are the primary search citizens: title, description, tags, variable names, and the flattened derivation summary are all indexed in LanceDB. The product page in the UI shows the full lineage graph, validation evidence, staleness state, and a copyable pinned-open snippet.
