Authentication

How a request becomes a Principal: four credential kinds, one resolution order, and the server-side session that backs the web UI. Authorization — what a Principal may then do — is RBAC; this page stops at identity.

1. Four credentials, one principal

CredentialCarrierResolverAudience
API key (hk_…)Authorization: Bearer ApiKeyResolverProgrammatic clients — CLI, Python client, service integrations
OIDC bearer tokenAuthorization: Bearer OidcResolver, verified against the IdP's JWKS Programmatic callers already holding their own OIDC access or ID token

Dev headers (X-Huron-*)Request headers DevHeaderResolverDevelopment only — refuses to construct outside ENV=development, and ApiSettings refuses the combination at startup

Resolution is one ordered chain, in authorization.current_principal: an Authorization header is checked first — hk_ resolves as an API key, anything else as an OIDC bearer token — and only when there is no such header does a session cookie get a look, with dev headers as the last-resort fallback. Bearer credentials keep absolute priority so a programmatic caller that happens to be carrying a cookie jar is never silently downgraded to a session principal.

All four converge on one dataclass, auth.Principal (subject, groups, scopes, project_id, authentication_method, kind). Every require_* guard and rbac.decide() sees only this — authorization logic never learns, and never needs to learn, which of the four credentials produced it.

2. Sessions

The web UI is the one client that authenticates interactively rather than presenting a pre-issued token, so it gets a mechanism the others don't: a server-side session, not a Huron-issued JWT. Login writes a sessions row; the browser holds an opaque HttpOnly cookie. Revocation is a plain row update and takes effect on the very next request — no token blocklist, no refresh-token plumbing in the SvelteKit shell. Bearer credentials are untouched by any of this.

The cookie value is hs_{session_id}_{secret}, the same shape as an API key's hk_{key_id}_{secret}. Only sha256(secret) is persisted, so a leaked sessions table cannot mint cookies; lookup is by session_id, comparison is constant-time.

Expiry is double-bounded — two independent clocks, not one:

  • Idle timeout (12 hours): slides forward on activity — evaluated on every request that resolves the session, inside SessionResolver.resolve — but the new value is only persisted back to the store when more than TOUCH_INTERVAL (5 minutes) has passed since the session's last_seen_at.
  • Absolute lifetime (7 days): fixed at login; nothing extends it. Every idle slide is clamped to min(now + idle_ttl, absolute_expires_at), so the idle clock can never push past the absolute one, and the database enforces the same ordering independently with CHECK (idle_expires_at <= absolute_expires_at) — a stolen-but-unused cookie still dies on schedule even if the idle clock keeps sliding.

That throttle exists so a busy UI polling every few seconds does not turn every GET into a session-table write. A session carries a login-time snapshot of subject, groups, and authentication_method — group membership refreshes at the next login, not mid-session, the same tradeoff an OIDC access token already makes for its own lifetime.

Every session also carries its own random CSRF token, minted alongside the session secret and returned once in the login response and thereafter from GET /auth/session — see §3.

3. CSRF

A cookie is sent by the browser automatically on any request to the right origin, same-site or not, which is exactly what makes cookie authentication convenient and exactly what a cross-site form or script can abuse to make state-changing requests the victim never intended. The rule: every cookie-authenticated request that is not GET/HEAD/ OPTIONS must echo the session's CSRF token in an X-Huron-CSRF header, compared to the stored token in constant time. Missing or mismatched is a 401.

Bearer-authenticated requests are exempt: a cross-site page can induce the browser to send a cookie, but it cannot set an arbitrary Authorization header on a cross-origin request, so a bearer caller needs no separate proof. GET/HEAD/ OPTIONS are exempt because they are required to stay side-effect-free regardless.

The cookie itself also carries SameSite=Lax, HttpOnly, and Secure outside development. SameSite=Lax already blocks the cookie from riding along on a cross-site subrequest (an <img>, a background fetch) — the CSRF header is deliberate belt-and-braces on top of it, not a substitute, because SameSite=Lax alone still allows a top-level cross-site navigation to carry the cookie, and a naive reading of "SameSite protects against CSRF" undersells exactly that gap. See §7 for where this pair does not yet close the gap.

4. Admin-provisioned passwords

Password accounts exist for the case OIDC alone doesn't cover — a demo, an offline environment, a first login before an IdP is wired up — and are deliberately the smaller of the two login paths. There is no self-registration, no email verification, and no self-service password reset. An administrator creates the account and sets the password; the same administrator (or the user, through the admin) resets it. A password reset or an account disable both revoke every session the subject holds — a reset logs the user out everywhere, by design, not as a side effect worth suppressing.

This is a proportionality choice, not an oversight. A control plane for a scientific data lake has a small, known population of human users provisioned by the same administrators who provision projects and role bindings. The surface a self-registration flow would need to defend — open account creation, email delivery and verification, reset-token issuance and expiry, account-enumeration hardening — buys nothing here that the admin-provisioning path doesn't already give for free, and every one of those is a place a login system usually gets attacked. Keeping password accounts admin-provisioned-only keeps the surface proportional to what the control plane actually needs.

Provisioning is itself a guarded capability: user.manage, held by platform_owner alone. Creating a human account is a platform act, distinct from an organization admin's authority over service accounts within their own organization — an org admin can create and manage the service accounts their pipelines run as, but cannot mint a human login. Passwords are at least 12 characters (MIN_PASSWORD_LENGTH), hashed with argon2id at RFC 9106's second recommendation (time_cost=3, memory_cost=64 MiB, parallelism=4) — sized for human-frequency logins on a control plane, not a high-throughput consumer service. Verification always does the hash comparison, against a fixed dummy hash when no matching credential exists, so an unknown username, a disabled account, a service-account subject named by mistake, and a genuinely wrong password all cost the same wall-clock time and return the identical message.

5. Route surface: unversioned /auth

Login, logout, the OIDC redirect pair, and session introspection are mounted at /auth, outside /api/v1 — deliberately, and for a reason that doesn't apply to the rest of the API. Login is a protocol surface negotiated with browsers and identity providers, not a versioned resource API. An IdP's registered redirect URI is fixed configuration on the IdP side; it cannot silently follow whatever API version a client happens to be speaking, the way a resource endpoint safely can. Versioning a login flow gains nothing and adds a coordination burden between Huron's release cadence and the IdP's client registration.

The introspection route moved with it: GET /auth/session answers "who am I, and how was I authenticated" — subject, kind, groups, authentication method, and (for a cookie-authenticated caller only) the CSRF token and session expiry. It replaces what used to live under the versioned surface, on the same reasoning: identity introspection is a login concern, not a v1 resource.

API keys stay versioned, on the opposite side of the same reasoning: POST /api/v1/auth/api-keys is a resource creation call — an API key is a row a caller owns, lists, and revokes, exactly like any other resource the versioned API manages, so it lives there rather than being carved out with login.

/auth/login, /auth/oidc/start, /auth/oidc/callback, and /auth/providers (which the login page reads to know what to render, before any credential exists) are the only unauthenticated routes in the service besides /healthz and /readyz.

6. Local development: one issuer, one URL

OIDC breaks the moment the browser and the backend disagree about the issuer string — the ID token's iss claim, the discovery document's own self-description, and the value Huron is configured to expect must all match byte-for-byte, or verification fails. Local development runs Keycloak as the site IdP in the compose stack, pinned to a single hostname (KC_HOSTNAME) so its entire discovery document — issuer, authorization endpoint, token endpoint, JWKS URI — always resolves to the same http://keycloak:8081/… URLs, regardless of which address was used to reach discovery in the first place.

That makes one issuer URL, http://keycloak:8081/realms/huron, correct for every consumer of the realm — but the realm has two different consumers, and only one of them ever gets the name for free. The browser runs on the host in both modes (there is no in-network browser, however the API is deployed), so it needs keycloak to resolve on the host every time it is redirected to the authorization endpoint — one /etc/hosts entry, required in both modes. The API's own outbound discovery and token-exchange calls are the part that varies: keycloak already resolves for free when the API runs inside the compose network (make stack), and needs that same /etc/hosts entry when the API runs on the host instead (make api). There is no mode that gets to use localhost:8081 instead; a second issuer string is exactly the failure mode this topology exists to avoid.

7. Known gaps

Login CSRF has no purpose-built defense. POST /auth/login authenticates the request body (username and password), not the caller, so it takes no Principal and enforces none of §3's CSRF check on itself — that check exists only for cookie-authenticated requests, and a login request by definition carries no session cookie yet. What actually stops a cross-site login attempt today is incidental, not a designed control: the request body is a pydantic model, so FastAPI requires application/json, and a plain cross-site HTML form — which can only submit urlencoded, multipart, or text/plain bodies — is rejected with 422 before any session is minted; a cross-site script sending JSON instead is stopped by the browser's own CORS preflight, because create_app installs no CORSMiddleware and grants no origin permission. Neither barrier is a security decision — both stop being true the moment a form-encoded login body or a CORS allowance is added for some unrelated reason. A pre-session anti-CSRF token (issued unauthenticated, checked at login) is the purpose-built fix; it is not implemented.

Re-login does not revoke the prior session. A new successful login — password or OIDC — mints a fresh sessions row and overwrites the browser's cookie with the new token; it does not revoke whatever session the old cookie named. The previous session stays valid, on whatever device holds that cookie, until its own idle or absolute expiry runs out. Only an explicit logout, an admin password reset, or an admin disable revoke a session by name.
