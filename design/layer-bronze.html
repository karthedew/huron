Bronze Layer

Source-faithful Zarr on object storage: the same scientific values as Raw, reopenable as arrays, with nothing renamed, rescaled, or reinterpreted.

1. Purpose and non-goals

Bronze answers one question: "give me the numbers that are in those files, as arrays, without making me parse the format." It preserves source-specific meaning — tally_4, mesh_104, relative_error, MCNP unit notation, original energy bins — and records exactly which raw bytes each array came from. It does not standardize names, units, or coordinates (that is Silver), and it does not merge datasets: one Bronze snapshot corresponds to one raw revision.

2. Storage model

{prefix}/
  organization/{org_slug}--{org_id}/
    project/{project_slug}--{project_id}/
      dataset/{dataset_slug}--{dataset_id}/
        bronze/
          repo/                   ← ONE Icechunk repository per dataset
  • One Icechunk repo per dataset. Snapshots within it are per raw revision. This keeps grant scoping (one prefix = one dataset's bronze), keeps repo count proportional to datasets, and lets Icechunk's history hold the full audit trail of rebuilds.
  • Branch/tag model. Builders commit on a working branch build/{revision_id}; after validation the publisher fast-forwards main and tags raw/{revision_number}. Consumers resolve tags through the catalog, never by guessing.
  • Group layout inside a snapshot is defined by the science profile. For mcnp-run@1.0:
/
├── tallies/tally_4/{value, relative_error, energy_bounds}
├── tallies/tally_14/{…}
├── mesh_tallies/mesh_104/{value, relative_error, x_bounds, y_bounds, z_bounds}
└── run/{histories_completed, keff, completion_state}

Every array carries source references as attributes, and the snapshot metadata carries the full provenance record:

{
  "source_revision_id": "rev-0001-uuid",
  "source_dataset": "run-0042",
  "source_revision_number": 1,
  "source_files": {"meshtal": "sha256:…", "outp": "sha256:…"},
  "profile": "mcnp-run@1.0.0",
  "extractor_digest": "sha256:9a1c…",
  "built_at": "2026-08-23T17:40:12Z"
}

3. Science profiles and extractors

A science profile is the versioned, installable definition of a data kind. It is the single artifact that teaches Huron a format:

profile: mcnp-run
version: 1.0.0
required_files: [input_deck, primary_output]
optional_files: [meshtal, runtpe, mctal, ptrac, logs]
file_categories:                      # feeds Raw retention
  input_deck: essential_input
  primary_output: primary_output
  runtpe: bulk_intermediate
extract:                              # metadata extraction at ingest time
  [mcnp_version, nps, kcode, materials, tallies, source_definition,
   completion_status, warnings, scheduler_provenance]
bronze:
  extractor_image: registry/huron/mcnp-extractor@sha256:9a1c…
  layout: mcnp-source-faithful/1
validations: [bronze-mcnp-v1]         # see §4
silver:
  canonicalizer_image: registry/huron/mcnp-canonicalizer@sha256:44d0…
  contract: mcnp-transport/1          # see Silver §3
  • Profiles are published by org stewards through the admin API; a published (name, version) is immutable — fixes are new versions. Rows are mirrored to object storage (_platform/profiles/…) so recovery does not depend on PostgreSQL.
  • Extractor and canonicalizer images are referenced by digest. The digest is recorded in every snapshot's provenance; "which parser produced these numbers" is always answerable.
  • The same extractor serves double duty: at ingest it populates the metadata envelope's extensions block (so the scientist confirms rather than types); at Bronze build it produces the arrays.

4. Build pipeline and validation

raw revision COMMITTED (outbox event)
   │
   ▼
Bronze builder claims job (PG jobs table, SKIP LOCKED)
   │  reads NFS payload read-only; extractor container, no network
   ▼
candidate snapshot on branch build/{revision_id}
   │
   ▼
Validator runs profile's bronze validations:
   ✓ required outputs found            ✓ run completed successfully
   ✓ all expected tallies extracted    ✓ energy-bin bounds valid & monotonic
   ✓ mesh dims match array shapes      ✓ relative-error arrays match tally arrays
   ✓ NaN/missing-value behavior known  ✓ sampled values agree with source text
   ✓ snapshot reopens through the client read path
   │
   ├─ pass → publish: fast-forward main, tag, catalog row (state PUBLISHED),
   │         outbox → LanceDB index + Silver canonicalization queued
   └─ fail → catalog row state FAILED with structured findings;
             raw retained for diagnosis; dataset page shows
             "Raw: committed / Bronze: failed"; retry after profile fix
  • Idempotent builds: a rebuild for the same revision replaces the working branch and produces a new snapshot; the catalog records the latest published snapshot per revision and keeps prior ones addressable (they are Icechunk history, not deleted state).
  • Corrections: a new raw revision of the dataset triggers a fresh Bronze snapshot; the previous revision's snapshot remains tagged and readable. Downstream impact is handled in Silver (region replacement) and Gold (staleness), not by mutating Bronze.
  • Failure is not publication: Huron never publishes a broken Bronze snapshot. Validation evidence (pass or fail) is stored as structured JSON on the catalog row and shown in the UI.

5. Access

Bronze is readable by the project's scientist role and above (see RBAC layer matrices) through the standard grant flow: huron.open_dataset(..., layer="bronze") or huron.open_snapshot("B182"). Most scientists skip Bronze and read Silver; Bronze exists for extractor debugging, for auditing canonicalization, and as the earliest retained representation once raw bulk files expire.

Sizing note. Bronze roughly doubles stored bytes for array-heavy sources (raw + bronze) until raw TTL expiration, which is the economic argument for per-category raw TTL: after 90 days a typical MCNP run costs raw-inputs + bronze + silver, not two full copies of bulk outputs. The unchanged-byte and layer-size metrics from the instrumentation list make this visible per project.
