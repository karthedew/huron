Svelte Frontend

SvelteKit application: the browse, search, governance, and publication surface, shaped like a workspace rather than an admin console. Everything it shows comes through the REST API with the user's own OIDC session — the UI holds no privileged credentials and can render nothing the API would not serve that user.

1. Stack and principles

  • SvelteKit + TypeScript, API client generated from openapi/v1.json (compile break on contract drift).
  • OIDC against the site IdP; session cookie; no tokens in localStorage. The UI never uses API keys; it manages them.
  • Server-side rendering for browse/search pages (shareable deep links like /nuclear-engineering/modeling-simulation/run-0042@v1.0 — slug paths are stable because slugs are immutable, and @tag resolves to one revision forever).
  • Honest staleness: every search view shows the projection watermark ("index 12 s behind"); every stale product wears its badge with the reason; candidate vs published is always visually distinct.
  • 404-not-403 rendering mirrors the API: resources the user cannot discover simply do not exist in the UI.
  • Workspace shape, deliberately Databricks-like. A persistent left rail (Search · Catalog · Jobs · Admin) beside a three-pane catalog explorer — organization → project → dataset in a navigable tree, detail on the right — because that layout is what scientists arriving from Databricks already know how to drive. Layer badges take the place of table/view icons.
  • Permissions edited like Grafana's. Each org, project and dataset has a Permissions tab: one row per binding (principal → role), an "Add permission" row that resolves users, groups and service principals, and an explicit indicator of what is inherited from the level above versus set here. Roles are the fixed vocabulary in RBAC — the UI never invents a permission the API cannot express.
  • Notebooks are out of scope for v1. A "Workspace" area is reserved in the rail for marimo notebooks and deliberately not built yet: nothing in the API, the grant model, or the page inventory assumes it, and nothing blocks on it.

3. Flows worth specifying

  • Steward activation: DRAFT dataset → checklist (identity, kind, ownership, contract, retention, classification, duplication) → activate; every unchecked item links to the place it gets fixed.
  • Retention choice with consequences: selecting a TTL policy shows the generated consequence text ("native MCNP replay unavailable after 90 days; earliest retained representation: Bronze") before saving — the retention design makes this a UI requirement.
  • Correction: "upload corrected revision" on a dataset pre-fills the CLI command (corrections are CLI/client operations; the UI explains and hands off), then shows the downstream impact as it propagates: new bronze → silver region replace → stale products.
  • Grant visibility: "who can read this?" panel on datasets/products for owners and auditors — resolved from bindings, rendered per layer.

4. Non-functional

  • Big-table virtualization for manifests (10k files) and audit streams; keyset pagination end-to-end (the versioned keyset cursor contract).
  • Lineage graph rendered client-side from the /lineage API (typed nodes/edges); depth-limited with expand-on-demand.
  • No embedded array visualization in v1 — the open-in-Python snippet is the deliberate hand-off. (A later phase may add thumbnail plots rendered by a service, never in-browser Zarr reads, which would require broad storage credentials in the browser.)
  • Accessibility and dark mode from the start; the design system mirrors these documents' palette.
