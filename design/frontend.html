Svelte Frontend

The Huron beta frontend organizes Polaris catalogs within Huron organizations. Catalog and Browse use live upstream metadata; Huron provides human login, manual onboarding and administration.

1. Stack and principles

Current delivery: each organization binds a separate Polaris realm root and owns its catalogs, with Huron membership and administration above realm-scoped Polaris grants. Catalogs group scientific programs or data domains; Raw, Iceberg and Icechunk are dataset types and can share namespaces. The main catalog and browse routes, username/password login, catalog settings and global administration use real persisted state. The Raw ingest wizard uploads actual files, commits immutable Huron revisions and registers managed datasets in Polaris. Legacy scientific fixture routes redirect to Browse. This beta contract supersedes the earlier fixture page inventory and OIDC-only frontend proposal; derived scientific publication and compute capabilities remain planned. See the authority and integration contract.

  • SvelteKit + strict TypeScript: typed Polaris/Huron account contracts live in the API seam; server-only clients perform upstream requests.
  • Identity: salted password hashes, encrypted individual Polaris secrets, opaque HttpOnly sessions. Tokens never enter localStorage. Accounts persist, sessions end on server restart.
  • Direct URLs and SSR: /browse?organization=…&catalog=…&namespace=…&table=… preserves exact nested namespace identifiers and pagination.
  • Authorization: Huron organization membership and Polaris catalog grants are both required for discovery. Polaris decides dataset permissions. Huron global admin controls account provisioning and catalog creation. Catalog admins manage their own catalog. Undiscoverable resources render 404.
  • Accessibility: semantic forms, visible keyboard focus, light/dark themes, mobile and compact workspace layouts are acceptance criteria.
  • Honest state: real mutations report Polaris outcomes; credential checks conceal secrets. Raw upload reports separate transfer, verification, commit and Polaris registration outcomes; pending registration remains retryable. Unbuilt jobs, derived publication, quota and API-key controls are absent from the beta navigation.

3. Planned scientific flows

The scientific workflow sketches below describe future integration, not beta frontend delivery.

The end-to-end scientist journey — dataset creation, entry-layer choice, raw upload, manual bronze intake, publication, release, open — is specified step-by-step, web UI and Python client side by side, in Scientist Workflows. The flows below are the governance and edge flows the journey doc does not cover.

  • Policy administration: an org admin attaches organization policies (schemas, retention defaults, classification), a project admin attaches project policies; every policy editor shows the effective composition — what is inherited, what this scope refines — before saving (RBAC §3). Datasets are active on creation; there is no activation flow.
  • Retention choice with consequences: selecting a TTL policy shows the generated consequence text ("native MCNP replay unavailable after 90 days; earliest retained representation: Bronze") before saving — the retention design makes this a UI requirement.
  • Correction: "upload corrected revision" on a dataset pre-fills the CLI command (corrections are CLI/client operations; the UI explains and hands off), then shows the downstream impact as it propagates: new bronze → silver region replace → stale products.
  • Grant visibility: "who can read this?" panel on datasets/products for owners and auditors — resolved from bindings, rendered per layer.

4. Non-functional

  • Big-table virtualization for manifests (10k files) and audit streams; keyset pagination end-to-end (the versioned keyset cursor contract).
  • Lineage graph rendered client-side from the /lineage API (typed nodes/edges); depth-limited with expand-on-demand.
  • No embedded array visualization in v1 — the open-in-Python snippet is the deliberate hand-off. (A later phase may add thumbnail plots rendered by a service, never in-browser Zarr reads, which would require broad storage credentials in the browser.)
  • Accessibility and dark mode from the start; the design system mirrors these documents' palette.
