Catalog & Search

PostgreSQL for structure, LanceDB for matching across all four layers, lineage as first-class structural data. One store per capability, one index for the whole lake.

1. The split, restated

QuestionServed by
List orgs / projects / datasets / revisions / release tags / snapshots / productsPostgreSQL (read-your-writes)
Resolve any resource by ID or slug pathPostgreSQL → storage sidecars
Effective metadata of a revision (base + amendments)NFS sidecars
What snapshots exist for dataset X, layer Y; which is latest publishedPostgreSQL
What does product version P depend on; what depends on snapshot SPostgreSQL (lineage edges — structural graph traversal)
Free-text / tag / faceted search across all four layers — datasets, revisions, snapshots, productsLanceDB (eventually consistent, lag reported)
Semantic similarity (later)LanceDB

Standing bans, still standing. No tsvector/GIN/pg_trgm anywhere. No q= or ILIKE on browse endpoints. No fallback from LanceDB to PostgreSQL: LanceDB down ⇒ /search returns 503 PROJECTION_UNAVAILABLE, browse keeps working. Lineage traversal is a structural query and therefore PostgreSQL — asking "similar products" is matching and therefore LanceDB. Classify every new query before writing it; never serve one question from two stores.

One index, all four layers

Layer is a facet, not a system boundary. A scientist searching "absorbed dose" does not know whether the answer is a raw revision or a published Gold product, and must not have to. Splitting the index by layer would mean two rankings, two authorization models, two consistency stories, and a merge step that can never be justified. One LanceDB projection covers raw, Bronze, Silver and Gold, with layer as a filterable column.

OpenMetadata: considered, rejected. It was evaluated as the catalog for the raw layer and as a possible source of RBAC. Both fail, the second decisively: OpenMetadata policies govern operations inside OpenMetadata — who may ViewAll or EditTags on assets in its own catalog — and have no mechanism to authorize a read of bytes on NFS or a prefix-scoped grant against RGW. Adopting it would mean building Huron's data-plane authorization anyway and then running a second RBAC system that must agree with the first, whose failure mode is silent over-permission. As a catalog it also mismatches: its Container entity models buckets and folders on S3/GCS/Azure, its versioning tracks metadata edits rather than data revisions, and its real value — connectors to a hundred sources you do not control — buys nothing for a system that produces every byte it holds.

If it is ever wanted, it is Polaris-shaped. The same posture as Polaris: a one-way mirror fed from the outbox for discovery outside Huron, never authoritative, never in the authorization path, never consulted by Huron's own /search, failing in a way that degrades external consumers only. A late phase if the demand appears — never the critical path, and never the RBAC.

2. PostgreSQL schema (delta)

Skeleton — the Alembic migrations are the source of truth. Conventions: UUIDv7 generated in the application, timestamptz everywhere, CHECK-enforced slugs, optimistic version columns:

Conventions pinned now because they are contracts: UUIDv7 is generated in the application (implemented per RFC 9562 on the Python 3.12 floor). Pagination cursors are versioned base64url keyset tuples matching the sort index — offset pagination is unsafe under an authorization predicate. Optimistic concurrency is SET version = version + 1 … WHERE version = :expected with rowcount 0 → 412, never a trigger. The domain layer imports only allowlisted pure libraries (rfc8785, jsonschema): no I/O, no global state, no foreign types in entity fields — enforced by import-linter in CI.

3. Lineage

Lineage is written transactionally at publication time (never reconstructed), with typed nodes (raw_revision, bronze_snapshot, silver_snapshot, gold_version) and optional region qualifiers for per-run precision. Two traversals are the workhorses, both plain recursive CTEs at the scale Huron targets:

  • Provenance (upstream): product version → every input snapshot → bronze → raw revisions, rendered as the lineage panel and exported as a JSON provenance document with the product.
  • Impact (downstream): superseded snapshot → affected silver regions → dependent gold versions, driving staleness marking and recompute scheduling.

Authorization filters lineage rendering per node: nodes the caller cannot discover are collapsed into "N restricted upstream datasets" (invariant L).

4. LanceDB projection

Topology: tables in {prefix}-index on RGW, exactly one writer (the projection worker, single replica, Recreate), API replicas read-only, outbox consumption, idempotent upserts, atomic pointer-flip rebuild, v1 is Tantivy FTS + scalar filters with the embedding column reserved and null.

TableRow perNotable columns
datasetsdataset org/project/dataset slugs + ids, title, description (FTS), tags, classification, profile + contract version, owner, layer availability flags (has_bronze/has_silver), latest silver snapshot, latest revision number, release tags (FTS), extension_text (FTS), created/updated, embedding (null)
revisionsraw revision ids + slugs up the chain, revision number, release tags pointing at it, title, purpose, campaign (FTS), extracted-parameter text (e.g. shield_thickness=30 material=concrete-b mcnp=6.3.1), quality state, state (COMMITTED/EXPIRED/PURGED), file count, total bytes
snapshotspublished Bronze/Silver snapshot ids + slugs up the chain, layer, contract version, variable names (FTS), dimension names, source revision, validation summary, published_at
productsproduct ids + slugs, title, description (FTS), tags, shape, latest published semver, staleness flag, variable names, derivation summary text (FTS), classification

Every table carries a layer column (raw/bronze/silver/gold) and the same project_id authorization column, so a single query spans the lake and the caller filters by layer only if they want to.

Search authorization is unchanged and doubled-up by design: resolve visible_project_ids from PostgreSQL, push as a hard pre-ranking filter into LanceDB, then re-authorize returned IDs against PostgreSQL before serialization (invariant H). Responses carry projection_lag_seconds + projection_watermark.

5. Rebuild and reconciliation

  • lakectl projection rebuild — walks NFS (datasets, revisions, release tags, effective metadata) and PostgreSQL (snapshot/product registry), writes fresh tables under a new prefix, verifies row counts, flips the pointer. Routine, not exceptional.
  • lakectl rebuild --from-storage — reconstructs PostgreSQL structural rows from NFS generation documents and COMMITTED markers, then the layer registry from Icechunk repo metadata on RGW (each snapshot's provenance block names its sources), then lineage from derivation records, then the projection. RBAC, audit, idempotency, and API keys come from PostgreSQL backups only.
  • The reconciler (see Raw §9) also cross-checks the layer registry: every PUBLISHED snapshot row must resolve to a live Icechunk ref, and every repo main branch must be recorded — disagreement is DEGRADED + alert, never silent repair.
