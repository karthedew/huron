Silver Layer

The canonical, validated representation scientists actually analyze: standard names, explicit coordinates, canonical units — each run in its own repo, shaped by a shared contract so families of runs combine cleanly when asked for.

1. Purpose

Silver standardizes existing scientific meaning. It translates source-specific Bronze structures into Huron's canonical array model so that a scientist can compare a hundred runs with one .sel() instead of parsing a hundred meshtal files. Nothing new is derived — the values are the same physics the source produced, re-expressed.

The contract defines Silver, not the descent. A snapshot is canonical because it satisfies its canonical contract — required variables present, dims and units exact, coordinates validated — and for no other reason. Most Silver is canonicalized from Bronze, but data that is already canonical when it reaches Huron enters Silver directly: a streaming feed from an instrument or an external service, or a published reference dataset such as the ICRP coefficients cited in the Gold derivation record. Such a dataset has no Raw and no Bronze and never will — that is a fact about where it came from, not a gap to be backfilled — so its snapshots carry an external-provenance block where the raw-revision and Bronze-snapshot references would otherwise be (§4). Entry is allowed at Raw, Bronze or Silver; Gold alone cannot be an entry layer, because a product without a derivation record is not a product.

2. Storage model

{prefix}/organization/…/project/…/dataset/{dataset_slug}--{dataset_id}/silver/repo/

What scopes a Silver array. The dataset — one Icechunk repo per dataset, the same scoping Bronze uses, holding that dataset's canonical, contract-validated arrays. This replaces an earlier design in which one repo per (project, profile, contract_version) held every run declaring that contract in a single shared array space. Three things forced the change, in order of weight:

  • Authorization could not be expressed honestly. RBAC bindings are scoped to an organization, project or dataset (RBAC). A dataset-scoped data.write@silver binding had no matching storage prefix — the shared repo spans datasets — so a credential minted for it would grant strictly more than the binding authorized. Silent over-permission is the same failure mode that disqualified an external policy engine (decision 6); it is not acceptable in our own design either. Per-dataset repos make the binding scope and the storage prefix the same string.
  • Deletion was a partial write. Purging or expiring a dataset meant region-deleting its slab out of an array other datasets were still reading, inside a repo whose history is meant to be an audit trail. It is now a repo deletion.
  • Publication serialized. Every dataset in a contract committed to one repo, so concurrent canonicalization contended on a single Icechunk branch.

What this costs, and where it went. Comparability across runs is no longer a property of storage. A contract still defines what makes runs comparable — that part is unchanged, and it is still declared by the dataset rather than implied by its position — but combining them is now a read-time or product-time act: either a virtual view over the member repos (open_mfdataset across a contract's datasets, resolved through the catalog), or, when the combination is worth publishing and citing, a Gold product (Gold). The second is usually the honest answer: a fused multi-run array is a derived artifact with its own provenance, inputs and validation, which is the definition of Gold rather than Silver.

Like Bronze, a Silver repo covers exactly one dataset, and each publication is a snapshot of that dataset's canonical view: a new revision of run-0042 re-canonicalizes and commits a new snapshot in run-0042's own repo, touching nothing another run can read. The dataset still carries a run coordinate — sized one — so that concatenating member repos along it needs no reshaping. Every snapshot remains addressable forever: an analysis pinned to S117 reproduces byte-identically regardless of later publications.

Combining runs. A contract's members are found through the catalog — the datasets in a project declaring that (profile, contract_version) — and combined at read time by concatenating their Silver repos along run. When a particular combination is worth publishing, validating and citing, it is promoted to a Gold product rather than being maintained as standing storage.

3. The canonical contract

Per science profile, a versioned canonical contract defines the Silver shape. It is the admin-approved agreement that makes cross-run analysis possible — the contract is what decides which runs are comparable, and therefore which repos may be concatenated:

contract: mcnp-transport/1
variables:
  particle_flux:
    dims: [run, energy, x, y, z]
    units: "1/cm^2/source-particle"
    from: mesh_tallies/*                  # bronze mapping
  particle_flux_relative_uncertainty:
    dims: [run, energy, x, y, z]
    from: mesh_tallies/*/relative_error
  keff:        {dims: [run], from: run/keff}
coordinates:
  energy: {units: MeV, from: energy_bounds → lower/upper/midpoint}
  x, y, z: {units: cm, from: *_bounds → explicit centers + bounds}
  run: {identity: dataset_slug}
  shield_thickness, shield_material, random_seed:   # sweep parameters as
    from: metadata extensions                       # auxiliary coordinates on run
attrs:
  provenance: huron standard provenance block per run
  • Naming follows a per-domain canonical vocabulary (CF-style where CF applies; a registry table where it does not). New variable names require project-admin approval — that is the "approve canonical contract" act in RBAC.
  • Units are canonical expressions validated with a units library; Bronze→Silver conversion factors are recorded in the snapshot provenance.
  • Sweep parameters become coordinates. Values confirmed at ingest (shield_thickness: 30) attach to the run axis, which is what makes ds.particle_flux.sel(shield_thickness=[20,30,40]) work with no file wrangling.
  • Contract versions: additive changes (new variable) extend the same repo; breaking changes (renamed dims, changed units) bump contract_version, which by construction starts a successor repo — and the catalog records the succession so old pins keep resolving. Datasets migrate to the successor by re-canonicalization, never by editing history.

4. Canonicalization pipeline and validation

bronze snapshot published (outbox)
   ▼
Canonicalizer job (digest-pinned container; reads bronze via scoped read grant)
   ▼  candidate snapshot on branch build/{bronze_snapshot_id}
Validator — silver checks:
   ✓ contract-required variables present, dims/units exact
   ✓ coordinate monotonicity and coverage; no unexplained NaN regions
   ✓ conservation/consistency checks the profile defines
     (e.g. mesh-integrated flux vs tally totals within tolerance)
   ✓ per-run provenance block complete (raw revision, bronze snapshot, converter digest)
   ✓ round-trip: sampled Silver values map back to Bronze values under the recorded conversion
   ▼
publish: fast-forward main, tag silver/{Snnn}, catalog row + lineage edges
         (silver snapshot ← bronze snapshot ← raw revision), outbox → search index,
         gold staleness evaluation

Lineage is recorded per run region, not just per snapshot: snapshot S119 knows that the run-0042 slab came from Bronze B187 (revision 2) while every other slab is unchanged from S118. That is what lets Gold staleness be computed precisely — a product that never touched run-0042 is not stale.

Direct entry: canonical data from outside the lake

A dataset declares an entry layer — raw (the default), bronze or silver. Entry above Raw means the lake is not the origin of these bytes: no ingest session, no manifest, no Bronze extraction, and the retention clock (Raw §9, starts: after_silver_published) has nothing to count. The publication path is otherwise identical — candidate on a working branch, the same validator, fast-forward and tag — because the contract check is the same check. Direct entry has two intake forms: manual upload by a scientist or engineer — the v1 path, specified with Bronze's mechanics in Bronze §4a and applying at Silver with the contract check swapped in as the validator — and an automated feed run by a pipeline service account, shown here:

external source (streaming feed, instrument, published reference data)
   ▼
Organization service account (digest-pinned container; roleless — intrinsic silver/gold authority)
   ▼  candidate snapshot on branch build/{batch_id}
Validator — the same silver checks, with one substitution:
   ✓ contract-required variables present, dims/units exact
   ✓ coordinate monotonicity and coverage; no unexplained NaN regions
   ✓ conservation/consistency checks the profile defines
   ✗ round-trip against Bronze — not applicable, there is no Bronze
   ✓ external-provenance block complete and attested (below)
   ▼
publish: fast-forward main, tag silver/{Snnn}, catalog row, lineage root

The external-provenance block is what makes such a snapshot auditable, and it is required — a Silver snapshot with neither a Bronze reference nor an external source is refused. (On manual intake, ingested_by names the human who initiated the upload and owns its assertions — user:… rather than sa:… — and uploaded_files carries the digests of what they sent; the storage writer is still the intake service account, so invariant J is untouched.)

  "kind": "external",
  "source_system": "npl-neutron-monitor",
  "source_uri": "https://feed.example.org/monitor/v2",
  "source_digest": "sha256:0b71…",          # when the source offers one

Lineage roots at the entry layer. A direct-entry Silver snapshot is a lineage root exactly as a raw revision is: Gold products built on it record it as a pinned input in the normal way, and staleness propagates from it normally. What downstream consumers lose is the ability to re-derive it — the source is outside Huron's custody, which is precisely what the provenance block records rather than conceals.

5. What scientists see

ds = huron.open_dataset("nuclear-engineering/huron-shielding-study/reactor-shielding-sweep",
                        layer="silver")            # latest published snapshot
comparison = ds["particle_flux"].sel(shield_thickness=[20, 30, 40],
                                     energy=slice(1e-3, 20.0))

ds_pinned = huron.open_snapshot("S117")            # exact reproducibility

The returned object is a lazy Xarray dataset over Icechunk/Zarr — chunked reads go straight to object storage under a scoped read grant (client doc). Scientists request canonicalization parameters and contract changes through the project admin; they never write Silver storage (invariant J).

Consistency stance. Silver is eventually consistent with Raw by design — the dataset page shows per-revision materialization state (raw: committed · bronze: published · silver: S118) rather than pretending the layers move atomically. "Latest" always means latest published and validated, never a candidate.
