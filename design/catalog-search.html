Catalog & Search

PostgreSQL for structure, LanceDB for matching across all four layers, lineage as first-class structural data. One store per capability, one index for the whole lake.

Explore the current implementation: Catalog UML class atlas — searchable, zoomable diagrams of the domain classes, authorized workflows, persistence interfaces and adapters, with implemented behavior distinguished from planned capabilities.

Current source ownership: Catalog owns hierarchy identity, descriptions, discovery collections and layer vocabulary; Raw owns uploads and revisions; Security owns authority and governance; Foundation owns shared values and pure primitives. Rules and complete workflows are colocated. The atlas attributes the former catalog model across these owners rather than treating it as one package. Search projection, credential vending, compute and lineage publication remain planned; unused placeholder ports were retired. The Core map describes the migrated working tree, not final gate completion.

1. The split, restated

QuestionServed by

Effective metadata of a revision (base + amendments)NFS sidecars

Standing bans, still standing. No tsvector/GIN/pg_trgm anywhere. No q= or ILIKE on browse endpoints. No fallback from LanceDB to PostgreSQL: LanceDB down ⇒ /search returns 503 PROJECTION_UNAVAILABLE, browse keeps working. Lineage traversal is a structural query and therefore PostgreSQL — asking "similar products" is matching and therefore LanceDB. Classify every new query before writing it; never serve one question from two stores.

One index, all four layers

Layer is a facet, not a system boundary. A scientist searching "absorbed dose" does not know whether the answer is a raw revision or a published Gold product, and must not have to. Splitting the index by layer would mean two rankings, two authorization models, two consistency stories, and a merge step that can never be justified. One LanceDB projection covers raw, Bronze, Silver and Gold, with layer as a filterable column.

OpenMetadata: considered, rejected. It was evaluated as the catalog for the raw layer and as a possible source of RBAC. Both fail, the second decisively: OpenMetadata policies govern operations inside OpenMetadata — who may ViewAll or EditTags on assets in its own catalog — and have no mechanism to authorize a read of bytes on NFS or a prefix-scoped grant against the object store. Adopting it would mean building Huron's data-plane authorization anyway and then running a second RBAC system that must agree with the first, whose failure mode is silent over-permission. As a catalog it also mismatches: its Container entity models buckets and folders on S3/GCS/Azure, its versioning tracks metadata edits rather than data revisions, and its real value — connectors to a hundred sources you do not control — buys nothing for a system that produces every byte it holds.

If it is ever wanted, it is Polaris-shaped. The same posture as Polaris: a one-way mirror fed from the outbox for discovery outside Huron, never authoritative, never in the authorization path, never consulted by Huron's own /search, failing in a way that degrades external consumers only. A late phase if the demand appears — never the critical path, and never the RBAC.

What the database enforces

The skeleton above states rules. Some are installed in PostgreSQL today, some are committed to a named migration, and some are held by nothing at all — and until this notation existed all three were written identically, which is how five CHECK IN (…) vocabularies sat here across seven migrations with not one of the five installed. Every line above that states a rule carries a marker naming who refuses the violating write. A rule with no marker is a defect in this section, not a fact about the database. Plain column lists are not rules and carry nothing.

MarkerMeansA reader may concludeA reader may not conclude
[db] A named database object refuses the violating write, and it is installed at the revision migrations/schema.sql's Reflects: line names. Every client is refused — API, worker, migration, psql alike. The named object exists in migrations/versions/. That the rule is sufficient for the invariant it serves. For a trigger, that it fires on operations its annotation does not name — ingest_commit_intents_immutable is BEFORE UPDATE OR DELETE and never sees an INSERT.
[app: module] No database rule. The named module under src/huron/ is the only thing that maintains the property, and the marker says in one clause why the database does not. A hand-written UPDATE breaks it silently; reconciliation, not the engine, is the recovery path. That a test covers it. That the module is the only writer, unless the marker says so.
[spec] Nothing enforces it and no writer exists. The property is a requirement on whoever builds the writer. Nothing today prevents a violation and there is no code to blame. This is a specification, not a status report. That the property is aspirational or negotiable — it binds the future author exactly as a signature does.

The mechanism is named, never categorised. A [db] marker must carry its mechanism: either the DDL spelled inline, as in the skeleton, or the object named, as in migrations/schema.sql and the table below. A [db] marker with neither is not a legal marking. Naming the object beats naming a mechanism class — CHECK, trigger, partial unique index — because the reader can then go and read it.

The landing point. This document leads the schema and wins where the two disagree, so §2 will always state rules the database does not have yet. That is the design record working, provided it says so. Two qualifiers cover it: [db 0008], committed to a named Alembic revision and not yet installed, legal while migrations/versions/0008_*.py is the revision being written; and [db P5], scheduled with no revision written, where the qualifier is a phase id from roadmap §2. When a revision lands, every marker carrying its number drops the qualifier — here, in the residue table below, and in migrations/schema.sql. Nothing mechanical catches a stranded one.

Currency. §2 leads the schema; it states what must be true. It is not stamped to an Alembic head and is not expected to track migrations. Its obligation is different: every rule it states carries a marker naming who refuses a violation today, and every landing point names a revision under migrations/versions/ or a phase in the roadmap. Stamping this section to the current head would turn the design record's legitimate lead over the schema into a build failure, inverting "where code and design disagree, the design wins".

The record claims enforcement, not correctness. [db] says a violating write is refused. It does not say the rule is the right rule, that it is sufficient for the invariant it serves, or that its vocabulary is complete: snapshots_provenance_states_an_origin refuses a provenance document that states no origin, and does not check that anything it references exists. Nor does a marker claim a test — the set of unqualified [db] markers is exactly the set of properties for which a "prove it with a write that must fail" contract test can be written, and is where new ones belong.

The schema registry

Every structured document Huron writes or accepts — the metadata envelope, the manifest, the snapshot provenance block, extension metadata, science profiles, canonical contracts — is validated against a schema, and every one of those schemas is a row in one registry. One table, one lifecycle, one recovery story, rather than a core schema "versioned in the repository" plus a separate extension registry plus profile rows: the repository copy of the core schemas becomes the seed the platform registers at bootstrap, not a second authority.

  • Three scopes, layered. PLATFORM rows are the envelope, manifest, and provenance schemas every deployment shares. ORGANIZATION rows are an org's metadata standards — the fields every dataset in the org must carry (org.example.core/2.0). PROJECT rows enrich an org schema for one programme of work: a project schema names the org schema it builds on via extends_id, and the effective schema at ingest is the composition (allOf: [org base, project enrichment]) resolved by walking the extends chain. A project schema may only extend a schema of its own organization (enforced by a composite FK), and chains are short by construction — platform schemas extend nothing, org schemas extend nothing, a project schema extends at most one org schema.
  • Published rows are immutable per (namespace, name, semver) — fixes are new versions, exactly the science-profile rule generalized. A revision's envelope records the schema references it validated against, so re-validation years later resolves the identical documents.
  • Deprecation, not deletion. DEPRECATED stops new ingests from declaring the version; existing documents keep resolving it forever. WITHDRAWN is the audited tombstone for a schema published in error.
  • Governance: organization admins publish organization schemas (and science profiles); project admins publish project enrichments; platform schemas ship with releases and are registered by migration. All writes go through the admin API and are audited.
  • Mirrored to storage. Rows are mirrored to _platform/schemas/{namespace}/{name}/{semver}.json on object storage (the science-profile mirroring rule, applied uniformly), so document validation is reconstructible without a PostgreSQL restore. Unknown extension namespaces remain stored-not-rejected (Raw §3); the registry governs what is validated, never what is preserved.

Conventions pinned now because they are contracts: UUIDv7 is generated in the application (implemented per RFC 9562 on the Python 3.12 floor). Pagination cursors are versioned base64url keyset tuples matching the sort index — offset pagination is unsafe under an authorization predicate. Optimistic concurrency is SET version = version + 1 … WHERE version = :expected with rowcount 0 → 412, never a trigger. The domain layer imports only allowlisted pure libraries (rfc8785, jsonschema): no I/O, no global state, no foreign types in entity fields — enforced by import-linter in CI.

3. Lineage

Lineage is written transactionally at publication time (never reconstructed), with typed nodes (raw_revision, bronze_snapshot, silver_snapshot, gold_version) and optional region qualifiers for per-run precision. Two traversals are the workhorses, both plain recursive CTEs at the scale Huron targets:

  • Provenance (upstream): product version → every input snapshot → bronze → raw revisions, rendered as the lineage panel and exported as a JSON provenance document with the product.
  • Impact (downstream): superseded snapshot → affected silver regions → dependent gold versions, driving staleness marking and recompute scheduling.

Authorization filters lineage rendering per node: nodes the caller cannot discover are collapsed into "N restricted upstream datasets" (invariant L).

4. LanceDB projection

Topology: tables in {prefix}-index on the object store, exactly one writer (the projection worker, single replica, Recreate), API replicas read-only, outbox consumption, idempotent upserts, atomic pointer-flip rebuild, v1 is Tantivy FTS + scalar filters with the embedding column reserved and null.

Every table carries a layer column (raw/bronze/silver/gold) and the same project_id authorization column, so a single query spans the lake and the caller filters by layer only if they want to.

Search authorization is unchanged and doubled-up by design: resolve visible_project_ids from PostgreSQL, push as a hard pre-ranking filter into LanceDB, then re-authorize returned IDs against PostgreSQL before serialization (invariant H). Responses carry projection_lag_seconds + projection_watermark.

5. Rebuild and reconciliation

P3 persistence plan, not applied schema: add frozen ingest commit intents, recovery ownership, governance document/digest mirrors, revision integrity/lifecycle observations and resumable run receipts. Findings separate INFO/WARNING/ERROR severity from repair/resolution outcome; acknowledgement never clears damage. Purge removes mirrored expiry per-file details. Latest revision means highest published number across all states. The superseded P3 design records the earlier constraints; the protocol cutover it required was retired on 2026-10-15.

  • Projection rebuild (a planned operator command; the lakectl CLI that was to host it was retired on 2026-10-15) — walks NFS (datasets, revisions, effective metadata) and PostgreSQL (snapshot/product registry), writes fresh tables under a new prefix, verifies row counts, flips the pointer. Routine, not exceptional.
  • Storage rebuild (a planned operator command) — P3 reconstructs Raw structural inventory offline: generation hierarchy, revisions/governance observations and amendments. A fresh target is claimed by a run identity; that same run may resume. Missing parents and identity conflicts block activation; reported payload corruption remains DEGRADED and need not block healthy inventory. Access policy must be restored and unambiguous before activation; governance readiness separately gates removal. No placeholder parents, synthetic approvals or deletion during rebuild. With the cutover inventory retired, v1 envelopes are operator findings, never admitted by timestamp. Derived-layer registry, lineage and projection rebuilds follow in their owning phases. RBAC, credentials, audit, holds, original outbox and idempotency require backups.
  • The reconciler (see Raw §10) also cross-checks the layer registry: every PUBLISHED snapshot row must resolve to a live Icechunk ref, and every repo main branch must be recorded — disagreement is DEGRADED + alert, never silent repair.
